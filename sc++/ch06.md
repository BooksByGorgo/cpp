
# Functions

\index{function}

As your programs grow, stuffing everything into `main` becomes unmanageable.
Functions let you break a program into smaller, reusable pieces.
Each function has a name, takes some input, does some work, and optionally returns a result.

You have already been using functions without thinking about it --- `std::cout <<` calls operator functions behind the scenes, and `main` is itself a function.
In this chapter you will learn how to write your own functions, how C++ passes data to and from them, and some powerful features like overloading and function pointers.

## Declarations vs. Definitions

\index{function!declaration}
\index{function!definition}

A function **declaration** (also called a prototype) tells the compiler the function's name, return type, and parameter types.
A function **definition** provides the actual body --- the code that runs when the function is called.

```cpp
// Declaration (prototype) --- no body, just a semicolon
int add(int a, int b);

// Definition --- includes the body
int add(int a, int b) {
    return a + b;
}
```

The declaration tells the compiler "this function exists and here is its signature."
The definition tells the compiler "here is what the function actually does."

The parameter names in a declaration are optional --- the compiler only needs the types, so `int add(int, int);` declares the same function.
They do not even have to match the names used in the definition.
Write them anyway, because a declaration is often all another programmer reads.
Compare `int area(int, int);` with `int area(int width, int height);` --- the second answers the "which argument comes first?" question before anyone has to ask it.

### Forward Declarations

\index{function!forward declaration}

The compiler reads your source file from top to bottom.
If you call a function before the compiler has seen its definition, it does not know what the function looks like and reports an error.
A **forward declaration** solves this by placing the declaration above the call:

```cpp
#include <iostream>
#include <string>

// Forward declaration
void greet(const std::string &name);

int main() {
    greet("Mack");
    return 0;
}

// Definition comes after main
void greet(const std::string &name) {
    std::cout << "Return of the " << name << "!\n";
}
```

Without the forward declaration, the compiler would not know about `greet` when it encounters the call in `main`.

::: {.tip}
**Tip:** You can usually avoid forward declarations by placing function definitions above where they are called (mutually recursive functions are the one case where you cannot).
However, forward declarations are essential in larger programs where functions call each other, and they are the foundation of header files.
:::

### Header Files and the One-Definition Rule

\index{translation unit}
\index{one-definition rule}

When your program grows beyond a single file, you split it into multiple `.cpp` files.
Each `.cpp` file, after all its `#include` directives are expanded, is called a **translation unit**.
The compiler compiles each translation unit independently, and the linker combines them into a single program.

C++ enforces the **one-definition rule** (ODR): a function (or variable) can be *defined* only once across all translation units.
Declarations can appear as many times as you like, but there must be exactly one definition.
A declaration is only a description --- it produces nothing in the compiled program, so ten identical copies are as harmless as one.
A definition produces actual machine code (or, for a variable, actual storage), and if the linker found two bodies for the same function it would have no honest way to choose between them.

\index{header file}

This is why forward declarations exist --- they let you declare a function in a header file so multiple `.cpp` files can call it, while the definition lives in exactly one `.cpp` file.

But what if you want to put a small helper function's *definition* directly in a header file?
If two `.cpp` files both include that header, the linker sees two definitions and reports an error.

\index{inline}

The `inline` keyword solves this:

```cpp
// helpers.h
inline int max_volume() {
    return 11;
}
```

`inline` tells the compiler "this definition may appear in multiple translation units --- treat them as the same definition."
Now any `.cpp` file can include `helpers.h` without causing a linker error.

::: {.tip}
**Tip:** If you define a function in a header file (outside of a class body), mark it `inline` to avoid ODR violations.
When you learn about classes in Chapter 11, you will see that member functions defined inside the class body are implicitly `inline`.
:::

::: {.tip}
**Wut:** `inline` does not mean "the compiler will inline this function" (i.e., paste its body at each call site).
It means "this definition may appear in multiple translation units."
Modern compilers decide on their own whether to inline a call, regardless of the keyword.
:::

### `static` Functions

\index{static}
\index{internal linkage}

Sometimes you want a helper function that is used inside one `.cpp` file but is not meant to be called from anywhere else --- it is purely an implementation detail of that file.
Imagine two `.cpp` files that each need their own small `clamp` helper, each with a range that makes sense for that file:

```cpp
// audio.cpp
int clamp(int v) {
    return v < 0 ? 0 : (v > 100 ? 100 : v);    // volume: 0..100
}

void set_volume(int v) {
    int safe = clamp(v);
    // ... apply safe volume
}
```

```cpp
// video.cpp
int clamp(int v) {
    return v < -90 ? -90 : (v > 90 ? 90 : v);  // tilt angle: -90..90
}

void tilt_camera(int v) {
    int safe = clamp(v);
    // ... tilt the camera
}
```

Each file has its own `clamp` with a range that makes sense for *that* file's purpose.
The problem is that at link time the linker sees two functions both named `clamp`, both with the signature `int(int)`, and reports a duplicate definition error.
Even if the linker somehow picked one, `audio.cpp`'s `clamp` would still be callable from `video.cpp`, which defeats the idea that each `clamp` is a private helper.

The fix is the `static` keyword:

```cpp
// audio.cpp
static int clamp(int v) {
    return v < 0 ? 0 : (v > 100 ? 100 : v);
}
```

```cpp
// video.cpp
static int clamp(int v) {
    return v < -90 ? -90 : (v > 90 ? 90 : v);
}
```

A `static` function has **internal linkage**: the function is only visible inside the translation unit where it is defined, and its name is never exported to the linker.
Each `.cpp` file gets its own private copy of `clamp`, so the two no longer collide, and nothing outside `audio.cpp` can accidentally call `audio.cpp`'s version --- that version does not exist as far as the linker is concerned.

Use `static` on any file-scope function that is a helper for the current `.cpp` file and should not be part of the file's public interface.
It is the C++ way of saying "private to this file."

::: {.tip}
**Wut:** The `static` keyword has another, completely unrelated meaning when applied to a variable *inside* a function: it makes that variable persist across calls instead of being recreated each time.
That is local `static`, and it has nothing to do with linkage --- it is just a name collision in the grammar.
:::

::: {.tip}
**Tip:** Modern C++ offers a second way to get the same "private to this file" effect --- put the helper inside an **anonymous namespace**:

```cpp
namespace {
    int clamp(int v) { /* ... */ }
}
```

Anonymous namespaces apply to functions, variables, and types, while file-scope `static` only applies to functions and variables.
For a single helper function, either style is fine.
:::

### `extern` Declarations

\index{extern}

The mirror image of `static` is `extern`: it tells the compiler "the thing I am naming here is *defined* in another translation unit --- trust me that the linker will find it."

You have already been using an implicit form of `extern` without knowing it.
Every **function declaration** (the forward-declaration syntax you saw earlier in this chapter) is already `extern` by default:

```cpp
int max_volume();          // declaration; implicitly extern
extern int max_volume();   // exact same thing, extern made explicit
```

For functions you almost never write `extern` explicitly --- just use the plain forward declaration.

Where `extern` actually matters is **global variables**.
Suppose you want a global `master_volume` that every file in the program can read:

```cpp
// audio.cpp
int master_volume = 5;
```

```cpp
// video.cpp
int master_volume;   // BUG: this DEFINES a second master_volume
```

Writing `int master_volume;` in `video.cpp` does not reference the one from `audio.cpp` --- it creates a brand-new variable with its own storage inside `video.cpp`.
The linker now sees two `master_volume`s, an ODR violation, and refuses to link.

`extern` fixes the problem by turning that line into a *declaration* instead of a definition:

```cpp
// video.cpp
extern int master_volume;   // declaration only; storage in audio.cpp
```

Now `video.cpp` can read and write `master_volume`, the actual storage lives in `audio.cpp`, and there is exactly one `master_volume` across the whole program.
The usual pattern is to put the `extern` declaration in a header that every file includes, with the real definition in exactly one `.cpp` file:

```cpp
// globals.h
extern int master_volume;
```

```cpp
// audio.cpp
#include "globals.h"
int master_volume = 5;
```

```cpp
// video.cpp
#include "globals.h"
// master_volume is now visible --- no new definition created
```

**When you need `extern`:**

- To share a global variable across `.cpp` files.
Put the `extern` declaration in a header, and put the real definition (with an initializer) in exactly one `.cpp` file.

**When you do not need `extern`:**

- For function declarations --- they are already `extern` by default, so `int clamp(int v);` and `extern int clamp(int v);` are identical.
Just write the plain forward declaration.
- For global variables that are only used inside one `.cpp` file.
Mark those `static` (or put them in an anonymous namespace) so they stay private to that file.
- For local variables inside a function.
They live on the stack and have no linkage to begin with.

::: {.tip}
**Trap:** Forgetting `extern` on a shared-global declaration in a header is the classic way to accidentally define a fresh copy of the variable in every translation unit that includes that header.
Everything compiles cleanly, but at link time you get a duplicate definition error (on older toolchains that defaulted to `-fcommon`, the program would even link, with every file silently operating on its own private copy of what was supposed to be a shared global).
Always write `extern` on global-variable declarations in headers.
:::

## Parameters and Return Values

\index{return}

A function can take zero or more parameters and return a single value.
The return type appears before the function name:

```cpp
int multiply(int x, int y) {
    return x * y;
}
```

You call the function by passing arguments that match the parameter types:

```cpp
int result = multiply(6, 7);
std::cout << result << "\n";   // 42
```

### `void` Functions

\index{void}

If a function does not return a value, its return type is `void`:

```cpp
void print_chorus() {
    std::cout << "I want it that way\n";
}
```

You can still use `return;` (with no value) inside a `void` function to exit early, but you are not required to.

```cpp
void check_age(int age) {
    if (age < 0) {
        std::cout << "Invalid age\n";
        return;   // exit early
    }
    std::cout << "Age: " << age << "\n";
}
```

## Pass-by-Value

\index{pass-by-value}

By default, C++ passes arguments **by value**.
This means the function receives a *copy* of the argument, not the original.
Modifying the parameter inside the function does not affect the caller's variable:

```cpp
#include <iostream>

void try_to_change(int x) {
    x = 999;   // modifies the local copy only
    std::cout << "inside:  " << x << "\n";    // 999
}

int main() {
    int num = 42;
    try_to_change(num);
    std::cout << "outside: " << num << "\n";  // still 42
    return 0;
}
```

The function `try_to_change` modified its own copy of `x`, but `num` in `main` was never touched.

## Pass-by-Reference

\index{pass-by-reference}

If you want a function to modify the caller's variable, pass it **by reference** using `&`:

```cpp
#include <iostream>

void make_it_louder(int &volume) {
    volume = 11;   // modifies the original
}

int main() {
    int vol = 5;
    make_it_louder(vol);
    std::cout << "Volume: " << vol << "\n";   // 11
    return 0;
}
```

The `&` after the type means `volume` is a reference --- an alias for the caller's variable, not a copy.
Any changes to `volume` are changes to `vol`.

A classic use of pass-by-reference is a swap function:

```cpp
#include <iostream>

void swap(int &a, int &b) {
    int temp = a;
    a = b;
    b = temp;
}

int main() {
    int x = 10, y = 20;
    swap(x, y);
    std::cout << x << " " << y << "\n";   // 20 10
    return 0;
}
```

::: {.tip}
**Tip:** Use pass-by-value for small types like `int`, `char`, and `double`.
Use pass-by-reference for larger types like `std::string` and structures to avoid the cost of copying [@CppCoreGuidelines, rule F.16].
:::

## `const` Parameters

\index{const!parameters}

Sometimes you want to pass by reference for efficiency (to avoid copying) but you do not want the function to modify the argument.
Mark the parameter `const`:

```cpp
void print_song(const std::string &title) {
    std::cout << "Now playing: " << title << "\n";
    // title = "something else";   // ERROR: title is const
}
```

The `const` reference gives you the best of both worlds: no copy is made, and the compiler guarantees the function cannot modify the original.

::: {.tip}
**Tip:** A good rule of thumb: if a function does not need to modify a parameter, make it `const`.
For small types like `int`, pass by value.
For larger types like `std::string`, pass by `const` reference.
This communicates your intent clearly and lets the compiler catch accidental modifications.
:::

::: {.tip}
**Wut:** A `const` reference can bind to a temporary value, but a non-const reference cannot:

```cpp
void print_song(const std::string &title);
void modify_song(std::string &title);

print_song("Semi-Charmed Life");  // OK: binds to temporary
// ERROR: non-const ref cannot bind to temporary
modify_song("Semi-Charmed Life");
```

This is why `const` references are so useful for function parameters that only read their argument.
:::

## Rvalue References and Pass-by-Rvalue-Reference

\index{rvalue reference}
\index{rvalue}
\index{lvalue}

So far you have seen two ways to pass data: by value (a copy) and by reference (an alias).
C++ has a third way: **pass-by-rvalue-reference**, written with `&&`.
To understand it, you first need to know the difference between lvalues and rvalues.

The names come from assignment: an **lvalue** is what can appear on the *left* of `=`, and an **rvalue** is what can appear on the *right*.
That is a nice starting point, but it is not perfectly accurate.
An lvalue is welcome on the right side too --- in `int y = x;`, the variable `x` is an lvalue.
And some lvalues cannot appear on the left at all: `const int max = 11;` makes `max` an lvalue, yet `max = 5;` will not compile.

A better way to think about it: an lvalue identifies a location in memory --- something that still exists after the expression, something you can take the address of.
An rvalue is just a value: it is read, used, and gone, with no persistent location once the expression finishes.
A variable like `volume` is an lvalue.
The literal `42` is an rvalue, and so is the result of `a + b`.

```cpp
int volume = 11;    // volume is an lvalue
int sum = 3 + 4;    // 3 + 4 produces an rvalue (7)
```

A regular (lvalue) reference `&` can bind to an lvalue.
A `const` reference `const &` can bind to both lvalues and rvalues.
An **rvalue reference** `&&` can only bind to rvalues --- temporaries that are about to disappear:

```cpp
int x = 10;
int &ref = x;         // OK: lvalue reference binds to lvalue
// int &ref2 = 42;    // ERROR: lvalue reference cannot bind to rvalue
const int &cref = 42; // OK: const reference can bind to rvalue
int &&rref = 42;      // OK: rvalue reference binds to rvalue
// int &&rref2 = x;   // ERROR: rvalue reference cannot bind to lvalue
```

The last line fails for a good reason.
An rvalue reference is a promise that whatever it binds to is disposable --- nobody else will miss it.
But `x` is an lvalue: it has a persistent location, and the code after this line is entitled to keep using it.
Letting `rref2` bind to `x` would invite functions to steal the guts of a variable that is still in use, so the compiler refuses.
When you genuinely want to hand over an lvalue as if it were disposable, you must say so explicitly with `std::move`, which is coming in Chapter 13.

### Why Rvalue References Matter

Why would you want to accept only temporaries?
Because if a value is temporary --- about to be destroyed --- you can safely *steal* its guts instead of copying them.
This is the basis of **move semantics**, which you will see in Chapter 13.

Consider a function that accepts a `std::string`.
If the caller passes a temporary, you know nobody else needs that string anymore, so you can transfer its internal buffer directly instead of allocating new memory and copying every character:

```cpp
#include <iostream>
#include <string>
#include <utility>

void archive(std::string &&song) {
    std::cout << "Archiving: " << song << "\n";
    // song's contents can be moved from --- the caller
    // does not need them anymore
}

int main() {
    archive("Lovefool");                    // OK: creates a temporary
    archive(std::string("6 Underground"));  // OK: explicit temporary

    std::string fav = "Steal My Sunshine";
    // archive(fav);                        // ERROR: fav is an lvalue
    archive(std::move(fav));                // OK: fav cast to rvalue
    // treat fav as moved-from from here on
    return 0;
}
```

`std::move` does not actually move anything --- it simply casts its argument to an rvalue reference, signaling "I am done with this, you may steal from it."
The actual moving happens inside the function or constructor that receives the rvalue reference.
You will see the full story in Chapters 13 and 14.

### When to Use Each Passing Style

Here is a summary of when to use each:

| Style | Syntax | When to use |
|-------|--------|-------------|
| Pass by value | `int x` | Small, cheap-to-copy types (`int`, `double`, `char`) |
| Pass by `const` reference | `const std::string &s` | Large types you only need to read |
| Pass by reference | `std::string &s` | When the function needs to modify the caller's variable |
| Pass by rvalue reference | `std::string &&s` | When the function will take ownership of a temporary |

::: {.tip}
**Tip:** Pass-by-rvalue-reference is most useful when you are writing functions that *consume* or *store* their argument.
If a function just needs to read data, `const &` is still the right choice --- it accepts both lvalues and rvalues.
:::

::: {.tip}
**Wut:** An rvalue reference *variable* is itself an lvalue.
*This deserves a double Wut; am I right?!?*
Inside a function that takes `std::string &&s`, the name `s` is an lvalue --- it has a name and an address.
The temporary rvalue that was passed in is now given the name `s` --- and anything with a name is an lvalue.
If you want to pass `s` along to another function as an rvalue, you need `std::move(s)` again.
This trips up nearly everyone the first time they encounter it.
:::

## Structures and Pass-by-Value

When you pass a structure by value, the entire structure is copied.
For small structures this is fine, but for large ones the copy can be expensive:

```cpp
struct Album {
    std::string title;
    std::string artist;
    int year;
    int tracks;
};

// BAD: copies the entire Album struct
void print_album_bad(Album a) {
    std::cout << a.title << " by " << a.artist << "\n";
}

// GOOD: passes a const reference --- no copy, no modification
void print_album(const Album &a) {
    std::cout << a.title << " by " << a.artist << "\n";
}
```

::: {.tip}
**Tip:** Pass structures by `const` reference unless the function needs its own copy to modify.
Copying a structure that contains strings or vectors copies all that data, which can be surprisingly slow.
:::

## Default Parameters

\index{default parameter}

You can give function parameters default values.
If the caller does not provide an argument for that parameter, the default is used:

```cpp
#include <iostream>
#include <string>

void play(const std::string &song, int volume = 5) {
    std::cout << "Playing " << song
              << " at volume " << volume << "\n";
}

int main() {
    play("Return of the Mack");         // volume defaults to 5
    play("Return of the Mack", 11);     // volume is 11
    return 0;
}
```

Default parameters must appear at the end of the parameter list.
You cannot put a defaulted parameter before a non-defaulted one:

```cpp
// OK
void play(const std::string &song, int volume = 5);

// ERROR: default parameter not at the end
void play(int volume = 5, const std::string &song);
```

::: {.tip}
**Trap:** Default values are specified in the declaration, not the definition (if they are separate).
Specifying defaults in both places is an error:

```cpp
// declaration with default
void play(const std::string &song, int volume = 5);

// definition --- no default here
void play(const std::string &song, int volume) {
    std::cout << song << " at " << volume << "\n";
}
```
:::

## Function Overloading

\index{function!overloading}

C++ lets you define multiple functions with the same name as long as their parameter lists differ.
This is called **function overloading**:

```cpp
#include <iostream>
#include <string>

void display(int value) {
    std::cout << "Integer: " << value << "\n";
}

void display(const std::string &value) {
    std::cout << "String: " << value << "\n";
}

void display(double value) {
    std::cout << "Double: " << value << "\n";
}

int main() {
    display(42);
    display("I want it that way");
    display(3.14);
    return 0;
}
```

The compiler decides which version to call based on the types of the arguments you pass.
The functions must differ in the number or types of parameters --- you cannot overload based on return type alone.

\index{overload resolution}

When an argument matches one overload exactly, the choice is obvious.
It gets complicated when nothing matches exactly, because the compiler is allowed to convert the argument and then picks the overload reachable through the *best* conversion.
The ranking is roughly: exact match first, then promotions (like `char` to `int`, or `float` to `double`), then other built-in conversions (like `long` to `int`), and last, conversions defined by user code.
The example above already leans on that last rung: `"I want it that way"` is not a `std::string`, it is an array of characters that decays to a pointer, and the compiler built a `std::string` from it because no other overload can accept a pointer.

Small changes to an argument's type can therefore land in different overloads --- or in none at all:

```cpp
display('A');    // char promotes to int: "Integer: 65"
display(3.14f);  // float promotes to double: "Double: 3.14"
// display(5L);  // ERROR: ambiguous --- long to int and
                 // long to double rank equally well
```

The `long` call does not compile: both conversions sit on the same rung of the ladder, so the compiler refuses to guess and reports an ambiguity.
The full rulebook, called **overload resolution**, runs to many pages in the C++ standard.
When the winner is not obvious to you, it will not be obvious to the next reader either --- convert the argument explicitly to the type you mean, like `display(static_cast<double>(n))`.
And yes, we are simplifying here: even more rules come into play with keywords like `explicit`, which can forbid an overload from being reached by conversion at all --- we will save those for a later book.

## Recursive Functions

\index{recursion}

A function that calls itself is called a **recursive function**.
Recursion is a powerful technique for problems that can be broken down into smaller versions of themselves.

The classic example is computing a factorial.
The factorial of `n` (written `n!`) is `n * (n-1) * (n-2) * ... * 1`:

```cpp
#include <iostream>

int factorial(int n) {
    if (n <= 1) {
        return 1;         // base case
    }
    return n * factorial(n - 1);  // recursive case
}

int main() {
    std::cout << "5! = " << factorial(5) << "\n";   // 120
    return 0;
}
```

Every recursive function needs two things:

1. A **base case** --- a condition that stops the recursion.
2. A **recursive case** --- where the function calls itself with a "smaller" problem.

Without a base case, the function calls itself forever until the program crashes with a stack overflow.

::: {.tip}
**Trap:** Forgetting the base case is the most common recursion mistake.
Always ask yourself: "Under what condition does this function *not* call itself?"
If you cannot answer that clearly, you have an infinite recursion.
:::

Let's trace through `factorial(3)` to see how it works:

```
factorial(3)
  → 3 * factorial(2)
        → 2 * factorial(1)
              → returns 1     (base case)
        → returns 2 * 1 = 2
  → returns 3 * 2 = 6
```

\index{call stack}
\index{stack frame}
\index{stack overflow}

Notice that while `factorial(1)` runs, `factorial(3)` and `factorial(2)` are still alive, each waiting for its result --- and each with its own separate `n`.
C++ keeps track of these pending calls on the **call stack**.
Every function call pushes a **stack frame** holding that call's parameters and local variables, plus a note of where to resume in the caller; when the function returns, its frame is popped and execution picks up where the note says.
Recursion works because each call gets its own frame: the `n` in `factorial(3)`'s frame is untouched while `factorial(2)` does its work.
The call stack also explains the crash mentioned above: the stack has a fixed amount of memory, every unfinished call occupies a frame, and infinite recursion piles up frames until the program dies with a **stack overflow**.

## Lambdas: Functions Without a Name

\index{lambda}

Sometimes you need a small helper --- two or three lines, used in one spot --- and defining a full function for it feels heavy: the definition sits far from its only call, and the name becomes visible to the whole file.
C++ offers a shortcut: the **lambda**, a function you write right where you need it, with no name required.

```cpp
auto banner = [](const std::string &title) {
    std::cout << "=== " << title << " ===\n";
};

banner("Side A");
std::cout << "I Want It That Way\n";
banner("Side B");
std::cout << "Return of the Mack\n";
```

The pieces of a lambda, left to right:

- `[]` is the **capture list** --- more on it in a moment.
- `(const std::string &title)` is a parameter list, exactly like a normal function's.
- `{ ... }` is a body, exactly like a normal function's.
- There is no name and no return type --- the compiler figures out the return type, and the whole lambda is a *value*, stored here in a variable with `auto` and called through that variable like any function.

Because the helper lives inside `main`, it is invisible to the rest of the file, and the definition sits right next to its calls.

The capture list is what makes lambdas more than a syntax shortcut: it lets the body use variables from the surrounding scope.

```cpp
std::string dj = "Mack";
auto tag = [dj](const std::string &song) {
    std::cout << dj << " spins " << song << "\n";
};
tag("Return of the Mack");   // Mack spins Return of the Mack
```

`[dj]` copies `dj` into the lambda; `[&dj]` would let the body use (and modify) the original instead.

Captures have many more options --- capture-everything shorthands, mutable state, `std::function` for storing any callable --- and *Gorgo Continuing C++* chapter 4 covers them.
For now: a lambda is a small function you define in place.
Where lambdas really shine is as arguments --- passing behavior *into* another function --- which is exactly where the next section picks up.

## Function Pointers

\index{function pointer}

In C++, functions have addresses in memory just like variables do.
A **function pointer** stores the address of a function so you can call it indirectly.

Here is the basic syntax:

```cpp
#include <iostream>

int add(int a, int b) { return a + b; }
int subtract(int a, int b) { return a - b; }

int main() {
    // Declare a function pointer
    int (*operation)(int, int);

    operation = add;
    std::cout << operation(10, 3) << "\n";   // 13

    operation = subtract;
    std::cout << operation(10, 3) << "\n";   // 7

    return 0;
}
```

The declaration `int (*operation)(int, int)` means: `operation` is a pointer to a function that takes two `int` parameters and returns an `int`.
The parentheses around `*operation` are required --- without them, you would be declaring a function that returns an `int *`.

### Simplifying with `using`

The function pointer syntax is admittedly ugly.
You can clean it up with a `using` alias:

```cpp
using MathOp = int (*)(int, int);

MathOp operation = add;
std::cout << operation(10, 3) << "\n";
```

### Callbacks

\index{callback}

Function pointers are commonly used as **callbacks** --- you pass a function to another function, which calls it at the right time:

```cpp
#include <iostream>
#include <string>

void process_songs(const std::string songs[], int count,
                   void (*action)(const std::string &)) {
    for (int i = 0; i < count; i++) {
        action(songs[i]);
    }
}

void announce(const std::string &song) {
    std::cout << "Now playing: " << song << "\n";
}

void shout(const std::string &song) {
    std::cout << ">> " << song << "!! <<\n";
}

int main() {
    std::string playlist[] = {
        "I Want It That Way",
        "Return of the Mack",
        "Semi-Charmed Life"
    };

    std::cout << "--- Chill mode ---\n";
    process_songs(playlist, 3, announce);

    std::cout << "--- Fiesta mode ---\n";
    process_songs(playlist, 3, shout);

    return 0;
}
```

The function `process_songs` does not know or care what `action` does --- it just calls it for each song.
This lets you change the behavior by passing a different function, without modifying `process_songs` itself.

This is where lambdas pay off: you do not even need to define `announce` and `shout`.
Write the behavior directly at the call site:

```cpp
process_songs(playlist, 3, [](const std::string &song) {
    std::cout << "Up next: " << song << "\n";
});
```

This works because a lambda with an empty capture list converts to a plain function pointer.
A lambda that *captures* anything cannot --- the captured data has to live somewhere, so a capturing lambda is secretly an object rather than a bare function.

::: {.tip}
**Tip:** Modern C++ callbacks are usually lambdas, with `std::function` (a *Gorgo Continuing C++* topic) to store capturing ones.
You will still encounter raw function pointers in older code and C libraries, so it is important to understand them.
:::

## `[[nodiscard]]`

\index{nodiscard}

Sometimes a function's return value is the whole point of calling it --- ignoring it is almost certainly a bug.
The `[[nodiscard]]` attribute tells the compiler to warn the caller if they discard the return value:

```cpp
[[nodiscard]] int find_track(const std::string &playlist);
```

If someone calls `find_track("90s Jams")` without using the result, the compiler produces a warning:

```cpp
find_track("90s Jams");           // warning: ignoring return value
                                  // of a 'nodiscard' function
int pos = find_track("90s Jams"); // OK --- return value is used
```

C++20 lets you add a reason that appears in the warning:

```cpp
[[nodiscard("track index needed for playback")]]
int find_track(const std::string &playlist);
```

Occasionally you really do want to ignore the result.
Assigning it to a throwaway variable does not help --- that just trades the warning for an "unused variable" warning.
The escape hatch is to make the discard explicit:

```cpp
static_cast<void>(find_track("90s Jams"));   // discard, explicitly
(void)find_track("90s Jams");                // C-style cast
std::ignore = find_track("90s Jams");        // needs <tuple>
```

Casting the call to `void` tells the compiler "I know there is a result, and I am throwing it away on purpose," which silences the warning.
`std::ignore` says the same thing as an assignment; C++26 officially blessed it for exactly this job [@Sommerlad2024], and the major compilers already handle it today.
Whichever you choose, the point is that a deliberate discard should *look* deliberate to the next reader.

::: {.tip}
**Tip:** Use `[[nodiscard]]` on functions where ignoring the return value is almost certainly a bug --- error codes, computed results, or newly allocated resources.
:::

## Operator Functions

\index{operator function}
\index{operator overloading}

Whew, there is a lot to functions in C++, right?
Well, there is more: operator functions.
To some they are an abomination, but to others, especially those writing core C++ APIs, they are fun ways to expand the semantics of language operators in new and unimagined ways.

You have actually been using operator overloading since Chapter 1.
The `<<` and `>>` operators are built into C++ for shifting the bits of an integer left and right (previewed in Chapter 4; Chapter 7 works through what they do to bits).
But visually they look like they are pushing data in a direction --- and the iostream library used that intuition to overload them for stream I/O [@Stroustrup1994].
The compiler only knows how to use `<<` and `>>` with integers.
The iostream library defined operator functions that taught the compiler how to apply `<<` and `>>` to `std::ostream`, `std::istream`, and other types.
Every time you write `std::cout << "hello"`, you are calling an operator function.

An **operator function** lets you do the same thing for your own types --- define what an operator like `+`, `==`, or `<<` does when applied to them.
You write it as a regular function named `operator` followed by the symbol.

Here is a `Score` struct with overloaded `+`, `==`, and `>`:

```cpp
#include <iostream>
#include <string>

struct Score {
    std::string player;
    int points;
};

Score operator+(const Score &a, const Score &b) {
    return Score{a.player + " & " + b.player, a.points + b.points};
}

bool operator==(const Score &a, const Score &b) {
    return a.points == b.points;
}

bool operator>(const Score &a, const Score &b) {
    return a.points > b.points;
}
```

Now you can use these operators naturally:

```cpp
int main() {
    Score a{"Fly", 95};
    Score b{"Intergalactic", 88};

    Score combined = a + b;
    std::cout << combined.player << ": "
              << combined.points << std::endl;

    if (a > b) {
        std::cout << a.player << " wins" << std::endl;
    }

    return 0;
}
```

Output:

```
Fly & Intergalactic: 183
Fly wins
```

The compiler sees `a + b` and looks for an `operator+` that takes two `Score` parameters.
It finds yours and calls it like any other function.

### Rules

There are a few rules that the compiler enforces:

- **You cannot create new operators.**
You can overload `+`, `-`, `*`, `/`, `==`, `!=`, `<`, `>`, `<=`, `>=`, `<<`, `>>`, `()`, `[]`, and many others, but you cannot invent `operator@` or `operator**`.
- **You cannot change arity** (the number of operands an operator takes).
Binary operators stay binary (two operands), unary operators stay unary (one operand).
You cannot make `+` take three operands.
- **You cannot change precedence or associativity.**
Even if you overload `+` and `*`, the compiler still evaluates `*` before `+` just like it does with built-in types.
- **At least one operand must be a user-defined type.**
You cannot redefine what `+` means for two `int`s.
- **Some operators cannot be overloaded at all:** `::`, `.`, `.*`, `?:`, and `sizeof`.

### The `<<` Operator for Output

\index{operator!<< (stream insertion)@\texttt{<<} (stream insertion)}

You can overload `<<` so that `std::cout` works with your types.
The left operand is an `std::ostream &` and the right operand is your type:

```cpp
std::ostream &operator<<(std::ostream &os, const Score &s) {
    os << s.player << ": " << s.points;
    return os;
}
```

Returning the `os` reference is what lets you chain calls: `std::cout << a << " vs " << b`.

```cpp
Score a{"Fly", 95};
std::cout << a << std::endl;  // prints: Fly: 95
```

::: {.tip}
**Tip:** Make your operators behave the way people expect.
`+` should combine things, `==` should compare them, `<<` should print them.
If `a + b` deleted `b`, your coworkers would not be amused.
:::

::: {.tip}
**Trap:** Do not overload `&&`, `||`, or `,` [@Meyers1996].
The built-in versions of `&&` and `||` use **short-circuit evaluation** --- the right side is only evaluated if the left side does not already determine the result.
When you overload them, both sides are *always* evaluated because the compiler treats them as regular function calls.
This can break logic that depends on short-circuiting, like `ptr != nullptr && ptr->valid()`.
:::

In Chapter 11 you will learn how to write operator functions as **member functions** of a class, which gives them access to private data.
The operator functions shown here are free functions that work with structs whose members are public.

## Try It: Functions Starter

```cpp
#include <iostream>
#include <string>

// Forward declaration
void play(const std::string &song, int volume = 5);

// Pass by value vs pass by reference
void double_value(int x) {
    x *= 2;   // only modifies the copy
}

void double_ref(int &x) {
    x *= 2;   // modifies the original
}

// Recursive countdown
void countdown(int n) {
    if (n <= 0) {
        std::cout << "Vamos!\n";
        return;
    }
    std::cout << n << "... ";
    countdown(n - 1);
}

// Function pointer
using Formatter = void (*)(const std::string &);

void upper_announce(const std::string &s) {
    std::cout << ">> " << s << " <<\n";
}

void quiet_announce(const std::string &s) {
    std::cout << "(" << s << ")\n";
}

// Definition of play
void play(const std::string &song, int volume) {
    std::cout << "Playing " << song
              << " at volume " << volume << "\n";
}

int main() {
    // Default parameters
    play("Semi-Charmed Life");
    play("Semi-Charmed Life", 11);

    // Pass by value vs reference
    int num = 10;
    double_value(num);
    std::cout << "After double_value: " << num << "\n";   // 10
    double_ref(num);
    std::cout << "After double_ref: " << num << "\n";     // 20

    // Recursion
    countdown(5);

    // Function pointer
    Formatter fmt = upper_announce;
    fmt("Return of the Mack");
    fmt = quiet_announce;
    fmt("Return of the Mack");

    return 0;
}
```

## Key Points

- A function declaration tells the compiler about a function's signature.
  A definition provides the body.
- Forward declarations let you call a function before its definition appears in the file.
- The one-definition rule (ODR) requires exactly one definition of each function across all translation units.
  Use `inline` for functions defined in header files.
- C++ passes arguments by value by default --- the function gets a copy.
- Use `&` to pass by reference when you need the function to modify the caller's variable or to avoid copying large objects.
- Mark parameters `const` when the function should not modify them.
  Use `const` references for large types you only need to read.
- An **rvalue reference** (`&&`) binds to temporaries.
  Use it when a function will take ownership of a value that the caller no longer needs.
- `std::move` casts an lvalue to an rvalue reference so it can be passed to a function expecting `&&`.
- Default parameters provide fallback values and must appear at the end of the parameter list.
- Function overloading lets you define multiple functions with the same name but different parameter lists.
- Recursive functions call themselves.
  Always ensure there is a base case to stop the recursion.
- Lambdas define small unnamed functions in place: `[capture](params){ body }`.
  Capture copies a variable (`[x]`) or references it (`[&x]`).
- Function pointers store the address of a function and enable callbacks --- passing behavior as a parameter.
  A captureless lambda converts to a function pointer; a capturing one does not.
- Operator functions let you define what operators like `+`, `==`, and `<<` mean for your own types.
- You cannot create new operators, change arity, or change precedence.
- Do not overload `&&`, `||`, or `,` --- it breaks short-circuit evaluation.
- `[[nodiscard]]` warns the caller if they ignore a function's return value.
