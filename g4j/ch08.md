# Maps and Structs

\index{map}
\index{struct}
If you have been writing Java for a while, you have used `HashMap<K,V>` and plain objects (classes with fields) constantly.
Go's maps and structs cover the same ground, but with enough differences to trip you up if you assume they work the same way.
This chapter covers both: how to create and use maps, the idioms that prevent common mistakes, and how structs serve as Go's primary data-grouping mechanism --- complete with methods, tags, and composition through embedding.

## Maps

A map in Go is an unordered collection of key--value pairs.
The Java equivalent is `HashMap<K,V>`.
Like `HashMap`, Go maps offer O(1) average-case lookup, insertion, and deletion.
Unlike `HashMap`, Go maps are a built-in type with dedicated syntax.

### Map Type and Declaration

\index{map!declaration}
The type of a map with keys of type `K` and values of type `V` is written `map[K]V`.

```go
var plays map[string]int // nil map --- not yet initialized
```

`K` must be **comparable**: any type that supports `==` and `!=`.
Strings, integers, floats, booleans, pointers, arrays, and structs whose fields are all comparable are valid key types.
Slices, maps, and functions are **not** comparable and cannot be used as keys.

::: {.tip}
**Wut:** Java lets you use any object as a `HashMap` key as long as it implements `hashCode()` and `equals()`.
Go requires the key type to support `==` at the language level.
You cannot use a `[]byte` as a Go map key; convert it to `string` first.
:::

There are two ways to create a non-nil map.

**Map literal:**

```go
streams := map[string]int{
    "Blinding Lights":   4_000_000_000, // The Weeknd
    "Shape of You":      3_600_000_000, // Ed Sheeran
    "Stay":              2_200_000_000, // The Kid LAROI & Justin Bieber
}
```

**`make`:**

```go
plays := make(map[string]int) // empty, ready to use
```

\index{make}
`make(map[K]V)` returns an initialized, empty map.
You can also pass a size hint --- `make(map[K]V, 100)` --- which pre-allocates internal buckets but does not set a maximum size.

::: {.tip}
**Trap:** A `var` declaration without an initializer gives you a **nil map**.
Reading from a nil map is safe and returns the zero value.
**Writing to a nil map panics at runtime.**

```go
var m map[string]int
fmt.Println(m["key"]) // fine --- prints 0
m["key"] = 1          // panic: assignment to entry in nil map
```

Always initialize with a literal or `make` before writing.
:::

### Map Operations

\index{map!operations}
The four basic operations on a map are read, write, delete, and count.

```go
m := map[string]int{
    "cumbia":  92,
    "reggaeton": 98,
    "afrobeats": 120,
}

fmt.Println(m["cumbia"])   // 92       --- read
m["drill"] = 140           //          --- write
delete(m, "reggaeton")     //          --- delete
fmt.Println(len(m))        // 3        --- count: cumbia, afrobeats, drill
```

The signatures of the relevant built-in functions are:

```go
func delete(m map[K]V, k K)  // remove the entry with key k; no-op if k is absent
func len(v Type) int          // number of entries in a map (or length of slice/string/channel)
```

Reading a key that is not in the map does **not** panic or throw.
It returns the zero value for the value type:

```go
bpm := m["classical"] // 0 --- key not present, zero value returned
```

This is safe but can hide bugs: you cannot tell whether `bpm` is `0` because classical music has no tempo entry, or because someone explicitly stored `0`.
The comma-ok idiom (next section) resolves that ambiguity.

### The Comma-ok Idiom

\index{comma-ok idiom}
\index{map!existence check}
To test whether a key is actually present in a map, use the two-value assignment form:

```go
v, ok := m[k] // v is the value (or zero), ok is true only if k exists
```

`ok` is a `bool`.
It is `true` if the key was found, `false` if it was not.
This is idiomatic Go; you will see it everywhere.

```go
catalog := map[string]string{
    "Creepin'":   "Metro Boomin & The Weeknd",
    "Bad Habit":  "Steve Lacy",
    "good 4 u":   "Olivia Rodrigo",
}

if artist, ok := catalog["Bad Habit"]; ok {
    fmt.Println("Found:", artist) // Found: Steve Lacy
} else {
    fmt.Println("Not in catalog")
}
```

::: {.tip}
**Tip:** The Java idiom is `if (map.containsKey(k)) { v = map.get(k); }` --- two lookups.
The Go comma-ok form is a single lookup that returns both the value and the presence flag.
Prefer the comma-ok form over comparing the value to its zero value; the zero value might be a legitimate stored value.
:::

### Iteration Order

\index{map!iteration order}
Ranging over a map with `for range` visits every key--value pair, but **in a random order that changes on every run**.

```go
bpm := map[string]int{
    "amapiano": 112,
    "hyperpop": 160,
    "lo-fi":    85,
}

for genre, b := range bpm {
    fmt.Printf("%s: %d\n", genre, b) // order varies every run
}
```

This is a deliberate design choice.
Go randomizes map iteration to make it immediately obvious if your code accidentally depends on order.
Java's `HashMap` also makes no ordering guarantee, but it tends to be stable in practice within a single run, which can mask order dependencies.

::: {.tip}
**Trap:** Never depend on map iteration order.
If you need sorted output, collect the keys into a slice and sort it first.

```go
import "sort"

keys := make([]string, 0, len(bpm))
for k := range bpm {
    keys = append(keys, k)
}
sort.Strings(keys)

for _, k := range keys {
    fmt.Printf("%s: %d\n", k, bpm[k])
}
```
:::

### Clearing a Map

\index{map!clear}
\index{clear}
Since Go 1.21, the `clear` built-in deletes all entries from a map:

```go
func clear(m map[K]V) // delete all entries; map remains non-nil and usable
```

```go
m := map[string]int{"a": 1, "b": 2, "c": 3}
clear(m)
fmt.Println(len(m)) // 0
m["d"] = 4          // fine --- map is still usable
```

After `clear`, the map is empty but not nil.
This is different from assigning `m = make(map[K]V)`, which allocates a new map and abandons the old one.
`clear` reuses the existing map, which can be useful when the map is shared or when you want to avoid a reallocation.

## Structs

\index{struct}
A struct is a composite type that groups named fields together.
In Java, you use a class; in Go, you use a struct.
The critical difference is that structs are **value types** in Go --- assigning a struct copies all its fields --- whereas in Java every object variable is a reference.

### Struct Definition

\index{struct!definition}
Define a struct type with `type T struct { ... }`:

```go
type Track struct {
    Title    string
    Artist   string
    BPM      int
    Duration float64 // seconds
}
```

The zero value of a `Track` has `Title = ""`, `Artist = ""`, `BPM = 0`, and `Duration = 0.0`.
You can use a zero-value struct immediately; there is no constructor required.

Fields can have the same type listed once, separated by commas:

```go
type Point struct {
    X, Y float64 // two fields, both float64
}
```

### Struct Literals

\index{struct!literal}
There are two forms of struct literal.

**Named form (preferred):**

```go
t := Track{
    Title:    "Timeless",
    Artist:   "The Weeknd & Playboi Carti",
    BPM:      138,
    Duration: 208.0,
}
```

**Positional form (fragile):**

```go
t := Track{"Timeless", "The Weeknd & Playboi Carti", 138, 208.0}
```

::: {.tip}
**Trap:** The positional form breaks silently if you ever add, remove, or reorder fields.
The named form is explicit and resilient to future changes.
Use positional form only for tiny, stable types like `Point{1.0, 2.0}` where the meaning is immediately obvious.
:::

**Anonymous structs** are useful for one-off data shapes, especially in tests and temporary groupings:

```go
entry := struct {
    Title  string
    Plays  int
}{"Save Your Tears", 1_800_000_000}

fmt.Println(entry.Title, entry.Plays)
```

### Struct as a Value Type

\index{struct!value type}
Assigning a struct creates an independent copy:

```go
a := Track{Title: "Agora Hills", Artist: "Doja Cat", BPM: 126}
b := a           // b is a copy; a and b are independent
b.BPM = 130
fmt.Println(a.BPM) // 126 --- a is unchanged
fmt.Println(b.BPM) // 130
```

In Java, `a = b` for an object would make both variables point to the same object.
In Go, you get two distinct structs.

When you want shared mutation --- so that changes through one variable are visible through another --- use a pointer:

```go
pa := &Track{Title: "Agora Hills", Artist: "Doja Cat", BPM: 126}
pb := pa           // both point to the same Track
pb.BPM = 130
fmt.Println(pa.BPM) // 130 --- shared!
```

::: {.tip}
**Tip:** Passing large structs to functions by value copies every field.
For structs with many fields or large fields, pass a pointer (`*Track`) to avoid the copy cost and to allow the function to mutate the original.
The rule of thumb from Chapter 6 applies: use pointer receivers when the struct is large or when mutation is required.
:::

### Methods on Structs

\index{struct!methods}
\index{method}
You attach behavior to a struct by defining methods with a **receiver**:

```go
func (t Track) String() string {                    // value receiver
    return fmt.Sprintf("%s by %s (%d BPM)", t.Title, t.Artist, t.BPM)
}

func (t *Track) ScaleBPM(factor float64) {          // pointer receiver
    t.BPM = int(float64(t.BPM) * factor)
}
```

The receiver appears between `func` and the method name.
A **value receiver** gets a copy; a **pointer receiver** gets a pointer to the original and can modify it.

Chapter 6 covers the receiver rules in detail.
The short version: use a pointer receiver when the method needs to mutate the struct, or when the struct is large enough that copying is expensive.
Use a value receiver when the method only reads and the struct is small.

```go
t := Track{Title: "Messy", Artist: "Lola Young", BPM: 118}
fmt.Println(t.String())   // Messy by Lola Young (118 BPM)
t.ScaleBPM(1.1)
fmt.Println(t.BPM)        // 129
```

### Struct Tags

\index{struct!tags}
\index{struct tags}
A struct tag is a raw string literal attached to a field declaration after the type:

```go
type Track struct {
    Title    string  `json:"title"`
    Artist   string  `json:"artist"`
    BPM      int     `json:"bpm,omitempty"`
    Duration float64 `json:"duration_sec,omitempty"`
}
```

Tags are metadata for the field.
The tag string has no effect at runtime unless a package reads it via reflection.
The `encoding/json` package reads `json` tags to control serialization:

- `json:"title"` uses `title` as the JSON key instead of the Go field name.
- `omitempty` omits the field from the JSON output when its value is the zero value.
- `json:"-"` tells the encoder to skip the field entirely.

The same mechanism is used by other packages:
- `xml:"..."` for `encoding/xml`
- `db:"..."` for database/ORM packages (e.g., `sqlx`, `gorm`)
- `validate:"..."` for validation libraries

\index{reflect.StructTag}
Packages parse tags through the `reflect.StructTag` type, which provides a `Lookup(key string) (value string, ok bool)` method.
You do not need to use reflection yourself to benefit from struct tags --- you just write the tag and the library handles it.

```go
package main

import (
    "encoding/json"
    "fmt"
)

type Playlist struct {
    Name   string  `json:"name"`
    Owner  string  `json:"owner"`
    Tracks int     `json:"track_count,omitempty"`
}

func main() {
    p := Playlist{Name: "Late Night Vibes", Owner: "bcr33d", Tracks: 42}
    data, _ := json.Marshal(p)
    fmt.Println(string(data))
    // {"name":"Late Night Vibes","owner":"bcr33d","track_count":42}

    empty := Playlist{Name: "Empty Queue", Owner: "bcr33d"}
    data, _ = json.Marshal(empty)
    fmt.Println(string(data))
    // {"name":"Empty Queue","owner":"bcr33d"}  --- Tracks omitted (zero)
}
```

::: {.tip}
**Tip:** Tag syntax is strict: backtick string, `key:"value"` pairs separated by spaces, no commas between pairs.
A malformed tag compiles fine but `go vet` will flag it.
Run `go vet ./...` as part of your build.
:::

### Embedding

\index{struct!embedding}
\index{embedding}
Go has no inheritance, but it has **embedding**: you include one struct type inside another by naming only the type, with no field name.

```go
type Artist struct {
    Name    string
    Country string
}

type Song struct {
    Artist           // embedded --- not a named field
    Title  string
    BPM    int
}
```

`Artist` is embedded in `Song`.
The fields and methods of `Artist` are **promoted** to `Song`: you can access them directly on a `Song` value as if they were declared on `Song` itself.

```go
s := Song{
    Artist: Artist{Name: "Rosalía", Country: "Spain"},
    Title:  "MOTOMAMI",
    BPM:    130,
}

fmt.Println(s.Name)    // Rosalía    --- promoted from Artist
fmt.Println(s.Country) // Spain      --- promoted from Artist
fmt.Println(s.Title)   // MOTOMAMI
```

You can still access the embedded struct directly by its type name:

```go
fmt.Println(s.Artist.Name) // Rosalía --- explicit path also works
```

\index{embedding!method promotion}
Method promotion works the same way.
If `Artist` has a method `Label() string`, then `Song` also has `Label()` via promotion, without any code on `Song`'s side.

```go
func (a Artist) Label() string {
    return fmt.Sprintf("%s (%s)", a.Name, a.Country)
}

fmt.Println(s.Label()) // Rosalía (Spain) --- promoted method
```

::: {.tip}
**Wut:** Embedding looks like inheritance but it is not.
A `Song` is not an `Artist`; it simply contains one and exposes its fields and methods as a convenience.
There is no polymorphism here: you cannot pass a `Song` where an `Artist` is expected.
That is what interfaces are for --- covered in Chapter 9.
:::

You can embed a pointer to a type as well:

```go
type Song struct {
    *Artist          // embedded pointer
    Title string
    BPM   int
}
```

With a pointer embedding, a zero-value `Song` has a nil `Artist` pointer.
Accessing a promoted field on a nil embedded pointer panics.
Make sure the embedded pointer is initialized before use.

Multiple types can be embedded in the same struct.
If two embedded types have a field or method with the same name, the outer struct must access them explicitly through the embedded type name to resolve the ambiguity; otherwise the compiler reports an error.

### The `cmp` Package

\index{cmp package}
\index{cmp.Compare}
\index{cmp.Ordered}
Go 1.21 added the `cmp` package in the standard library.
It provides generic comparison utilities that are useful when sorting slices of structs.

```go
// package cmp
func Compare[T Ordered](x, y T) int // -1 if x < y, 0 if x == y, +1 if x > y
```

`cmp.Ordered` is a type constraint satisfied by all integer types, floating-point types, and `string`.

The practical use case is sorting a slice of structs by a numeric or string field:

```go
import (
    "cmp"
    "fmt"
    "slices"
)

type Track struct {
    Title  string
    BPM    int
}

func main() {
    playlist := []Track{
        {Title: "Gata Only",       BPM: 170},
        {Title: "Starboy",         BPM: 186},
        {Title: "Golden Hour",     BPM: 136},
        {Title: "Until I Found You", BPM: 124},
    }

    slices.SortFunc(playlist, func(a, b Track) int {
        return cmp.Compare(a.BPM, b.BPM)
    })

    for _, t := range playlist {
        fmt.Printf("%s: %d\n", t.Title, t.BPM)
    }
}
// Until I Found You: 124
// Golden Hour: 136
// Gata Only: 170
// Starboy: 186
```

`cmp.Compare` replaces the classic three-way comparison pattern and is safe for floats (it handles NaN consistently).

### The `maps` Package

\index{maps package}
Go 1.21 added the `maps` package to the standard library with utility functions for working with maps.

```go
import "maps"

func Keys[Map ~map[K]V, K comparable, V any](m Map) iter.Seq[K]     // yields each key
func Values[Map ~map[K]V, K comparable, V any](m Map) iter.Seq[V]   // yields each value
func Clone[Map ~map[K]V, K comparable, V any](m Map) Map            // shallow copy of m
```

The most common use is combining `maps.Keys` with `slices.Sorted` to iterate a map in sorted key order without manually building a key slice:

```go
import (
    "fmt"
    "maps"
    "slices"
)

func main() {
    bpm := map[string]int{
        "amapiano": 112,
        "hyperpop": 160,
        "lo-fi":    85,
    }

    for _, genre := range slices.Sorted(maps.Keys(bpm)) {
        fmt.Printf("%s: %d\n", genre, bpm[genre])
    }
}
// amapiano: 112
// hyperpop: 160
// lo-fi: 85
```

`maps.Clone` makes a shallow copy of a map --- useful when you want to mutate a map without affecting the original.

## Key Points

- A map's type is `map[K]V`; `K` must be comparable (supports `==`).
- Declare a map with a literal or `make`; a nil map panics on write.
- Reading a missing key returns the zero value; use `v, ok := m[k]` to distinguish "absent" from "stored zero."
- Map iteration order is randomized by design; sort keys explicitly for deterministic output.
- `clear(m)` (Go 1.21) removes all entries but leaves the map non-nil.
- Structs are value types; assigning a struct copies it; use pointers for shared mutation.
- Prefer named struct literal syntax over positional; positional form breaks on field reordering.
- Methods use value or pointer receivers; pointer receivers allow mutation (Chapter 6 rules apply).
- Struct tags are metadata strings read by libraries via `reflect.StructTag`; `json:"..."` is the most common.
- Embedding promotes fields and methods of the embedded type; it is composition, not inheritance.
- `cmp.Compare` (Go 1.21) provides a generic three-way comparison for ordered types.
- The `maps` package (Go 1.21) provides `Keys`, `Values`, and `Clone`; combine `maps.Keys` with `slices.Sorted` for sorted map iteration without a manual key slice.

1. **Think about it:** In Java, you can use any object as a `HashMap` key as long as you override `hashCode()` and `equals()`.
   In Go, map key types must be **comparable** --- they must support `==` at the language level.
   What are the advantages and disadvantages of Go's approach compared to Java's?
   Give one example of a Java key type that you cannot use directly as a Go map key, and explain how you would work around it.

2. **What does this print?**

    ```go
    package main

    import "fmt"

    func main() {
        type Artist struct {
            Name string
        }
        type Song struct {
            Artist
            Title string
        }

        s := Song{
            Artist: Artist{Name: "Peso Pluma"},
            Title:  "La Bebé",
        }

        s.Name = "Natanael Cano"
        fmt.Println(s.Title, "by", s.Name)
        fmt.Println(s.Artist.Name)
    }
    ```

3. **Calculation:** Given the following map and operations, what does `len(m)` return after the final line?

    ```go
    m := map[string]int{
        "pop":       1,
        "rock":      2,
        "jazz":      3,
        "classical": 4,
    }
    delete(m, "rock")
    delete(m, "country") // key does not exist
    m["hip-hop"] = 5
    m["jazz"] = 99
    ```

4. **Where is the bug?** The function `countFast` is correct, but the call at the bottom always prints `0`.
   Why does `countFast(nil, 100)` always return `0` even though `catalog` is populated?

    ```go
    package main

    import "fmt"

    func countFast(catalog map[string]int, threshold int) int {
        var count int
        for track := range catalog {
            if catalog[track] > threshold {
                count++
            }
        }
        return count
    }

    func main() {
        catalog := map[string]int{
            "Gasoline":        148,
            "Industry Baby":   160,
            "Numb":             72,
        }
        fmt.Println(countFast(nil, 100)) // bug is here: passing nil, not catalog
    }
    ```

   Build a slice of at least four `Song` values representing real or fictional songs.
   Then write a function `topN(songs []Song, n int) []Song` that returns the `n` most-played songs in descending order by `Plays`.
   Use `slices.SortFunc` and `cmp.Compare` to sort.
   Print the title and play count of each song in the result.
