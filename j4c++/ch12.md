# Exceptions

C++ programmers are used to exceptions being entirely optional.
You throw what you want, catch what you want, and `noexcept` is a promise to the compiler, not a guarantee the compiler enforces on callers.
Java takes a fundamentally different stance: the type system is involved in exception handling, and the compiler actively enforces that certain exception types are either caught or declared.
If you have never encountered **checked exceptions** before, they are going to feel strange at first.

This chapter covers Java's exception hierarchy, the checked/unchecked split, `try/catch/finally`, multi-catch, and try-with-resources --- Java's answer to RAII for non-memory resources.

## Checked vs Unchecked --- Unique to Java

\index{exception}
\index{checked exception}
\index{unchecked exception}

Java's exception hierarchy starts at `Throwable` and branches immediately into two families:

```
Throwable
├── Error                       (JVM-level, do not catch)
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   └── AssertionError
└── Exception
    ├── IOException             (checked)
    ├── SQLException            (checked)
    ├── ParseException          (checked)
    └── RuntimeException        (unchecked)
        ├── NullPointerException
        ├── IllegalArgumentException
        ├── IllegalStateException
        ├── ArrayIndexOutOfBoundsException
        ├── ClassCastException
        └── NumberFormatException
```

The split that matters for you is this: **checked vs unchecked**.

### Checked Exceptions

\index{checked exception!definition}

A **checked exception** is any subclass of `Exception` that is **not** a subclass of `RuntimeException`.
`IOException`, `SQLException`, `InterruptedException`, and `ParseException` are all checked.

The compiler **enforces** that you handle checked exceptions.
If a method can throw a checked exception, it must either:

1. Declare it in a `throws` clause, or
2. Catch it in a `try/catch` block.

```java
// This method throws a checked exception: callers must deal with it.
public String readFirstLine(String path) throws IOException {
    BufferedReader br = new BufferedReader(new FileReader(path));
    return br.readLine();
}
```

If you call `readFirstLine` without catching `IOException` and without adding `throws IOException` to your own method, the code does **not compile**.

This is unlike anything in C++.
C++ has no concept of checked exceptions.
Every exception in C++ is unchecked --- you may catch it or not; the compiler does not care either way.

### Unchecked Exceptions

\index{unchecked exception!definition}

An **unchecked exception** is any subclass of `RuntimeException`.
`NullPointerException`, `IllegalArgumentException`, `ArrayIndexOutOfBoundsException`, `ClassCastException`, and `NumberFormatException` are all unchecked.

The compiler does not require you to declare or catch unchecked exceptions.
They represent programming errors --- bugs that callers should not be expected to recover from.

```java
public int divide(int a, int b) {
    if (b == 0) throw new IllegalArgumentException("divisor cannot be zero");
    return a / b;
}
```

Callers of `divide` are not forced to catch `IllegalArgumentException`.

::: {.tip}
**Tip:** Use `RuntimeException` subclasses for programming errors: bad arguments, illegal state, failed preconditions.
Use checked `Exception` subclasses for recoverable conditions that callers genuinely need to handle: file not found, network error, parse error.
:::

::: {.tip}
**Wut:** The Java community has been arguing about checked exceptions since Java 1.0.
Modern Java frameworks (Spring, Kotlin, Scala on the JVM) largely avoid checked exceptions, wrapping them in unchecked wrappers.
You will see both styles in industry.
:::

### Error: Do Not Catch

\index{Error}

`Error` and its subclasses (`OutOfMemoryError`, `StackOverflowError`, `AssertionError`) represent JVM-level failures.
Do not catch them.
Do not throw them.
When the JVM is out of memory, there is nothing useful your code can do; catching `OutOfMemoryError` usually makes things worse.

::: {.tip}
**Trap:** Never catch `Error` or `Throwable` directly.
Catching `Throwable` catches both exceptions and `Error`s, which can mask JVM failures and leave your application in an undefined state.
If you really need to catch the broadest possible exception, catch `Exception` --- that leaves `Error`s alone.
:::

## `try`/`catch`/`finally`

\index{try}
\index{catch}
\index{finally}

Basic exception handling looks similar to C++:

```java
try {
    String line = readFirstLine("/tmp/today.txt");
    System.out.println(line);
} catch (IOException e) {
    System.err.println("Could not read file: " + e.getMessage());
}
```

`finally` introduces a block that runs regardless of how the `try` block exits --- normal completion, exception, or even `return`:

```java
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("/tmp/today.txt"));
    System.out.println(br.readLine());
} catch (IOException e) {
    System.err.println("Error: " + e.getMessage());
} finally {
    if (br != null) {
        try { br.close(); } catch (IOException ignored) {}
    }
}
```

The `finally` block above runs whether `readLine()` succeeds or throws.
This is how Java programmers managed resource cleanup before Java 7.
It is verbose and error-prone (notice the nested `try` inside `finally`).
Try-with-resources, covered below, replaced this pattern.

### Multi-Catch

\index{multi-catch}
\index{catch!multi-catch}

Java 7 added multi-catch: catching multiple exception types in a single `catch` clause using `|`:

```java
try {
    processFile(path);
} catch (IOException | SQLException e) {
    // "Today" - Smashing Pumpkins (1993)
    System.err.println("Today is a good day to fix bugs: " + e.getMessage());
}
```

Multi-catch is syntactic sugar.
The compiler turns it into separate catch blocks.
The catch variable `e` is implicitly `final` --- you cannot reassign it inside a multi-catch block.

::: {.tip}
**Trap:** Exception types in a multi-catch clause must not be in a subtype relationship.
`catch (Exception | IOException e)` is a compile error because `IOException` is a subtype of `Exception` --- the `IOException` branch would be unreachable.
:::

### Rethrowing Exceptions

\index{rethrowing}
\index{exception chaining}

You can catch an exception, do some logging or cleanup, then rethrow it:

```java
try {
    riskyOperation();
} catch (IOException e) {
    log.error("Operation failed", e);
    throw e;   // rethrow the same exception
}
```

Or wrap it in another exception (exception chaining):

```java
try {
    riskyOperation();
} catch (IOException e) {
    throw new ServiceException("Could not complete operation", e);
}
```

The second argument to the constructor is the **cause** --- the original exception.
This preserves the full stack trace chain and is the right thing to do when you translate a low-level exception into a higher-level one.
`getCause()` retrieves the original:

```java
Throwable getCause()
String     getMessage()
String     toString()
void       printStackTrace()
```

::: {.tip}
**Tip:** Always pass the original exception as the cause when wrapping exceptions.
Without the cause, you lose the original stack trace and debugging becomes much harder.
:::

## Try-with-Resources

\index{try-with-resources}
\index{AutoCloseable}

Try-with-resources (Java 7+) is Java's closest equivalent to RAII for non-memory resources.
Any object that implements `AutoCloseable` can be used in a try-with-resources block, and its `close()` method is called automatically when the block exits --- whether by normal completion, exception, or `return`.

The `AutoCloseable` interface has one method:

```java
public interface AutoCloseable {
    void close() throws Exception;
}
```

`Closeable` (used by I/O streams) is a more specific subinterface:

```java
public interface Closeable extends AutoCloseable {
    void close() throws IOException;
}
```

A try-with-resources statement:

```java
try (BufferedReader br = new BufferedReader(new FileReader("/tmp/lyrics.txt"))) {
    // "1979" - Smashing Pumpkins (1996)
    System.out.println(br.readLine());
}   // br.close() is called here, always
```

Compare this to the pre-Java-7 version with `finally` shown in the previous section --- try-with-resources eliminates the boilerplate entirely.

Multiple resources are separated by semicolons.
They are closed in **reverse order** of declaration (last opened, first closed):

```java
try (FileReader fr  = new FileReader("input.txt");
     BufferedReader br = new BufferedReader(fr)) {
    System.out.println(br.readLine());
}   // br.close() called first, then fr.close()
```

### Suppressed Exceptions

\index{suppressed exception}

A subtle but important detail: if the `try` block throws an exception *and* `close()` also throws, the exception from `close()` is **suppressed** --- attached to the primary exception --- rather than replacing it.
This is different from a traditional `finally` block, where an exception thrown in `finally` replaces the original exception (losing it entirely).

You can retrieve suppressed exceptions with `getSuppressed()`:

```java
Throwable[] getSuppressed()
```

::: {.tip}
**Tip:** For C++ programmers: try-with-resources is the Java idiom for RAII applied to any resource that has a `close()` method.
File handles, database connections, network sockets, locks --- if it has `close()`, put it in a try-with-resources block.
The syntax is more explicit than C++ RAII (you must write the `try` keyword), but the guarantee is the same: `close()` always runs.
:::

::: {.tip}
**Trap:** Resources declared in a try-with-resources block are closed when the block exits, even if you need them after the block.
Do not declare a resource with try-with-resources if you intend to use it outside the `try`.
:::

## Exception Hierarchy --- When to Use Each Tier

\index{exception hierarchy}

Here is a practical decision tree for throwing exceptions:

- **Programming error** (bad argument, null where not allowed, method called in wrong state): throw a `RuntimeException` subclass.
  Callers should not catch these; fix the bug.
- **Recoverable condition** (file not found, network timeout, malformed input): throw a checked `Exception` subclass.
  Callers must decide whether to handle or propagate.
- **Never throw** `Error` or `Throwable` directly.

### Custom Exceptions

\index{custom exception}

Creating a custom exception is straightforward.
Extend `RuntimeException` for unchecked or `Exception` for checked:

```java
public class TrackNotFoundException extends RuntimeException {
    public TrackNotFoundException(String message) {
        super(message);
    }

    public TrackNotFoundException(String message, Throwable cause) {
        super(message, cause);
    }
}
```

Always provide at minimum a message-only constructor and a message-plus-cause constructor.
That covers the two most common usages and preserves chained stack traces.

### Common Exception Types to Know

\index{NullPointerException}
\index{IllegalArgumentException}
\index{IllegalStateException}
\index{UnsupportedOperationException}
\index{IndexOutOfBoundsException}
\index{ClassCastException}
\index{NumberFormatException}
\index{IOException}
\index{FileNotFoundException}
\index{InterruptedException}

| Exception | Kind | When thrown |
|:----------|:-----|:------------|
| `NullPointerException` | unchecked | Dereferencing `null` |
| `IllegalArgumentException` | unchecked | Invalid argument passed to method |
| `IllegalStateException` | unchecked | Object in wrong state for the operation |
| `UnsupportedOperationException` | unchecked | Operation not supported (e.g., `List.of().add(...)`) |
| `IndexOutOfBoundsException` | unchecked | Array or list index out of range |
| `ClassCastException` | unchecked | Invalid cast at runtime |
| `NumberFormatException` | unchecked | String cannot be parsed as a number |
| `ArithmeticException` | unchecked | Integer division by zero |
| `IOException` | checked | I/O failure (base class) |
| `FileNotFoundException` | checked | File does not exist (subclass of `IOException`) |
| `InterruptedException` | checked | Thread interrupted while waiting or sleeping |
| `SQLException` | checked | Database access error |

::: {.tip}
**Tip:** When writing a method that validates its arguments, throw `IllegalArgumentException` for bad values and `NullPointerException` (or `Objects.requireNonNull(...)`) for unexpected null arguments.
The distinction matters: `IllegalArgumentException` says "the value is wrong," while `NullPointerException` says "null is not allowed here."
:::

The `Objects` utility class provides a convenience method for null checking:

```java
public static <T> T Objects.requireNonNull(T obj, String message)
```

Usage:

```java
public void setTitle(String title) {
    this.title = Objects.requireNonNull(title, "title must not be null");
}
```

This throws `NullPointerException` with the given message if `title` is `null`, and returns `title` otherwise.

## A Complete Example

Putting it all together: a class that reads a playlist from a file, with proper exception handling, try-with-resources, and a custom exception:

```java
import java.io.*;
import java.util.*;

public class PlaylistReader {

    public static class PlaylistException extends RuntimeException {
        public PlaylistException(String message, Throwable cause) {
            super(message, cause);
        }
    }

    public List<String> load(String path) {
        List<String> tracks = new ArrayList<>();

        try (BufferedReader br = new BufferedReader(new FileReader(path))) {
            String line;
            while ((line = br.readLine()) != null) {
                line = line.strip();
                if (!line.isEmpty()) tracks.add(line);
            }
        } catch (FileNotFoundException e) {
            throw new PlaylistException("Playlist file not found: " + path, e);
        } catch (IOException e) {
            throw new PlaylistException("Error reading playlist: " + path, e);
        }

        return tracks;
    }

    public static void main(String[] args) {
        PlaylistReader reader = new PlaylistReader();
        try {
            List<String> tracks = reader.load("playlist.txt");
            tracks.forEach(System.out::println);
        } catch (PlaylistException e) {
            System.err.println("Failed: " + e.getMessage());
        }
    }
}
```

Notice:
- `BufferedReader` is in a try-with-resources block --- `close()` is guaranteed.
- `FileNotFoundException` (a specific subclass of `IOException`) is caught first; more specific before more general.
- The checked `IOException` is wrapped in the unchecked `PlaylistException` --- a common pattern in frameworks that do not want callers burdened with checked exceptions.
- The original exception is always passed as the cause.

::: {.tip}
**Trap:** Always catch more specific exceptions before more general ones.
If you catch `IOException` before `FileNotFoundException`, the `FileNotFoundException` catch is unreachable and the compiler will flag it as an error.
:::

## Key Points

- Java exceptions split into **checked** (must be declared or caught, compiler-enforced) and **unchecked** (no compiler requirement).
  C++ has only unchecked exceptions.
- `Error` subclasses (`OutOfMemoryError`, `StackOverflowError`) represent JVM failures; do not catch or throw them.
- `RuntimeException` subclasses are unchecked and represent programming errors; `Exception` subclasses that are not `RuntimeException` are checked and represent recoverable conditions.
- `finally` always runs, even if an exception is thrown or `return` is executed.
- Multi-catch (`catch (IOException | SQLException e)`) catches multiple types in one clause; types must not be in a subtype relationship.
- **Try-with-resources** automatically calls `close()` on `AutoCloseable` resources --- this is Java's idiom for RAII on non-memory resources.
- Multiple resources in try-with-resources are closed in reverse declaration order; exceptions from `close()` are suppressed, not replacing the primary exception.
- Always pass the original exception as the cause when wrapping (`throw new MyException("msg", e)`).
- Custom exceptions: extend `RuntimeException` for unchecked, `Exception` for checked; provide at minimum message-only and message-plus-cause constructors.
- Catch more specific exceptions before more general ones.
