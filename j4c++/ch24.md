# JVM Internals and GC Tuning

As a C++ programmer you have hands-on experience with the full compilation pipeline: preprocessing, compilation to object files, link-time optimization, and static or dynamic linking to a native binary.
Memory is yours to manage --- `malloc`/`free`, stack discipline, RAII --- and when things go wrong you reach for `valgrind`, `perf`, or `gdb`.
The JVM is a different kind of machine.
It runs bytecode, compiles hot methods to native code on the fly, manages all memory through a garbage collector, and comes with its own suite of diagnostic tools.
Understanding how the JVM works under the hood lets you tune it intelligently instead of guessing at flags.

This chapter covers class loading, JIT compilation, the generational heap, the available garbage collectors, the most important tuning flags, how to read GC logs, and the diagnostic tools that replace `valgrind`, `perf`, and `pstack` in the Java world.

## Class Loading

\index{class loader}
\index{class loading}

In C++ the dynamic linker (`dlopen`/`dlsym`) loads shared libraries at runtime.
In Java, **class loaders** play the analogous role: they find `.class` files (or their equivalents inside JARs and modules) and load them into the running JVM on demand --- the first time a class is actually needed.

### The Built-in Loader Hierarchy

\index{class loader!bootstrap}
\index{class loader!platform}
\index{class loader!application}

Three class loaders form a delegation chain:

| Loader | What it loads | Implementation |
|:-------|:--------------|:---------------|
| **Bootstrap** | `java.lang`, core JDK classes (`rt.jar` / `java.base` module) | Written in C++; no Java `ClassLoader` object |
| **Platform** (formerly Extension) | JDK platform modules beyond `java.base` | `jdk.internal.loader.ClassLoaders.PlatformClassLoader` |
| **Application** (System) | Your classpath / modulepath entries | `jdk.internal.loader.ClassLoaders.AppClassLoader` |

The **parent delegation model** defines how they cooperate.
When your application asks the Application loader to load `com.example.Foo`, it does not immediately search the classpath.
Instead it asks its parent --- the Platform loader --- which in turn asks the Bootstrap loader.
Only if the Bootstrap loader cannot find the class does control return to Platform, and only if Platform also fails does Application finally search your classpath.

This prevents your code from accidentally (or maliciously) replacing core JDK classes: a rogue `java.lang.String` on the classpath is never found because Bootstrap always wins for that package.

### Custom Class Loaders

\index{class loader!custom}
\index{ClassLoader}

You can write your own loader by extending `java.lang.ClassLoader` and overriding `findClass`:

```java
public class UrlClassLoader extends ClassLoader {
    private final URL source;

    public UrlClassLoader(URL source, ClassLoader parent) {
        super(parent);                    // always pass a parent
        this.source = source;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            byte[] bytes = downloadBytecode(name); // fetch .class bytes somehow
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }

    private byte[] downloadBytecode(String name) throws IOException {
        String path = name.replace('.', '/') + ".class";
        try (InputStream in = new URL(source, path).openStream()) {
            return in.readAllBytes();
        }
    }
}
```

Application servers like Tomcat and Wildfly, and OSGi containers, use custom class loaders to give each deployed application its own isolated namespace --- two webapps can each bundle a different version of the same library without conflict.
That is something the C++ dynamic linker cannot do without `dlmopen` or process isolation.

::: {.tip}
**Trap:** Every class loader defines its own namespace.
Two `Class<?>` objects are equal only if they were loaded by the same loader.
If classloader A and classloader B each load `com.example.Foo`, `instanceof` checks and casts between them will fail even though the bytecode is identical.
This is the source of the dreaded "ClassCastException: Foo cannot be cast to Foo" that bites every developer who writes their first plugin system.
:::

## Bytecode Execution --- Interpretation and JIT

\index{JIT compilation}
\index{HotSpot}
\index{bytecode}
\index{tiered compilation}

The `javac` compiler does not produce native machine code.
It produces **bytecode** --- a compact, platform-neutral instruction set for a stack-based virtual machine.
The JVM starts executing bytecode by **interpreting** it: fetch an instruction, dispatch to a handler, repeat.
Interpretation is safe and requires no warmup, but it is roughly 10--100x slower than equivalent native code.

HotSpot (the JVM shipped with the Oracle/OpenJDK distributions) addresses this with **tiered compilation**.
A method passes through up to five levels as it accumulates invocations:

| Level | Description | Cost | Quality |
|:------|:------------|:-----|:--------|
| 0 | Interpreter | None | Slowest |
| 1 | C1 (client) --- simple code gen, no profiling | Fast | Moderate |
| 2 | C1 with call/backedge counters | Fast | Moderate |
| 3 | C1 with full profiling instrumentation | Moderate | Moderate + data |
| 4 | C2 (server) --- aggressive optimization | Slow | Fastest |

A method becomes a candidate for C2 compilation after approximately 10,000 invocations (the "compilation threshold," controlled by `-XX:CompileThreshold`).
The profiling data gathered at levels 2 and 3 feeds C2's optimizations.

### What C2 Does

\index{JIT compilation!C2}
\index{inlining}
\index{escape analysis}
\index{devirtualization}

C2 applies the kind of optimizations you would expect from `g++ -O3` --- and then some:

- **Aggressive inlining:** small hot methods are inlined at their call sites, eliminating call overhead and enabling further optimization across the expanded body.
- **Devirtualization:** if profiling shows that a virtual call always dispatches to the same concrete type, C2 compiles it as a direct call (or inlines it entirely), with a guard that falls back to the virtual dispatch if the assumption is ever violated.
This is something C++ AOT compilation cannot do in the general case, because the compiler does not know at compile time which subclass will be used.
- **Escape analysis:** if an object never escapes the allocating method, C2 can allocate it on the stack instead of the heap, eliminating both the allocation and the GC pressure entirely.
- **Loop unrolling and vectorization:** standard AOT-style loop transforms, applied to the hot loop bodies identified by the profiler.

The trade-off vs C++ AOT: C2 compiles late (during the warmup period), so short-lived programs never reach peak JIT performance.
Long-running server processes eventually reach native-code speeds and can surpass AOT because JIT has runtime profile data that static compilers do not.

### Watching JIT in Action

\index{PrintCompilation}

The flag `-XX:+PrintCompilation` logs each JIT event to stdout:

```
    100   17       3       java.lang.String::equals (65 bytes)
    101   18       4       java.lang.String::hashCode (55 bytes)
    102   19       3  n    java.lang.Object::clone (native)
```

Columns: timestamp (ms), compilation ID, tier (3 = C1, 4 = C2), method signature, bytecode size.
The `n` flag marks native methods.
You will rarely need this in production, but it is useful when diagnosing warmup latency.

::: {.tip}
**Wut:** A C2-compiled method can be **deoptimized** back to the interpreter if an optimistic assumption (e.g., "this virtual call always hits subclass Foo") turns out to be wrong at runtime.
Deoptimization is correct and transparent, but if it happens in a hot loop it causes a visible latency spike.
You can spot deoptimizations in the `-XX:+PrintCompilation` output as lines ending in `made not entrant` or `made zombie`.
:::

## Heap Structure

\index{heap!generational}
\index{generational hypothesis}

The JVM heap is divided into regions that reflect the **generational hypothesis**: most objects die young.
Studies of real programs consistently show that the vast majority of objects become unreachable within milliseconds of allocation.
Organizing the heap around this observation lets the GC spend most of its effort in a small, fast-to-collect region.

### Young Generation

\index{heap!young generation}
\index{Eden}
\index{survivor space}

The young generation consists of three spaces:

- **Eden:** all new objects are allocated here.
Allocation is a simple pointer bump --- essentially free, much faster than `malloc`'s free-list search.
- **Survivor S0 and S1:** two equal-sized spaces, one always empty.

When Eden fills up, a **minor GC** fires.
The collector copies all live objects from Eden and the active survivor space into the empty survivor space (or directly into old gen if they are large or old enough), then resets Eden to empty.
Dead objects are simply abandoned --- no free-list bookkeeping required.
Objects that survive a configurable number of minor GCs (`-XX:MaxTenuringThreshold`, default 15) are **promoted** to the old generation.

::: {.tip}
**Tip:** Minor GCs are intentionally fast --- typically under 10 ms even on a large heap --- because the young generation is small and most objects in it are already dead.
If minor GC pause times are spiking, the usual cause is too many long-lived objects cluttering the survivor spaces, triggering premature promotion.
:::

### Old Generation (Tenured)

\index{heap!old generation}
\index{major GC}

Long-lived objects live in the old generation.
When it fills up, a **major GC** (or full GC) runs.
Major GCs are more expensive because they must trace a much larger live set.
Depending on the collector, they may also compact the heap, which takes more time but eliminates fragmentation.

### Metaspace

\index{metaspace}
\index{PermGen}

Before Java 8, class metadata (the JVM's internal representation of every loaded class) lived in a fixed-size heap region called **PermGen**.
Running out of PermGen --- `java.lang.OutOfMemoryError: PermGen space` --- was a rite of passage for Java developers.

Java 8 replaced PermGen with **Metaspace**, which lives in native memory (outside the Java heap) and grows automatically.
You can still cap it:

```
-XX:MaxMetaspaceSize=256m
```

Without a cap, a class-loader leak (typically from hot-redeploy in an application server) will consume all native memory.

### Sizing the Heap

\index{-Xms}
\index{-Xmx}

```
java -Xms512m -Xmx4g MyApp
```

`-Xms` sets the **initial** heap size; `-Xmx` sets the **maximum**.
Setting them equal eliminates the overhead of heap resize operations (the JVM resizes the heap at GC time when usage is far from either bound).
For production servers, `-Xms` = `-Xmx` is a common tuning starting point.

## Garbage Collectors

\index{garbage collector}

Java ships five production-grade collectors.
Choosing among them means choosing your trade-off between throughput and pause latency.

| GC | Flag | Pauses | Best for |
|:---|:-----|:-------|:---------|
| Serial | `-XX:+UseSerialGC` | Stop-the-world, single-threaded | Small heaps, embedded, single CPU |
| Parallel | `-XX:+UseParallelGC` | Stop-the-world, multi-threaded | Batch throughput |
| G1 | `-XX:+UseG1GC` | Mostly concurrent, short pauses | General purpose, heaps 4 GB+ |
| ZGC | `-XX:+UseZGC` | Sub-millisecond, concurrent | Latency-sensitive, any heap size |
| Shenandoah | `-XX:+UseShenandoahGC` | Sub-millisecond, concurrent | Latency-sensitive (OpenJDK) |

### Serial GC

\index{Serial GC}

The simplest collector: a single thread stops the world to collect both young and old generations.
Use it when you have a small heap (under 100 MB), a single-core environment, or a CLI tool where GC pause time is irrelevant.
It is the C equivalent of a simple bump allocator with periodic `free`-everything.

### Parallel GC

\index{Parallel GC}

Multiple GC threads work in parallel to collect the young and old generations, but all of them stop the world while doing so.
Parallel GC was the default before Java 9.
It maximizes throughput (ratio of application time to GC time) at the cost of potentially long pause times.
If your job runs overnight and finishes in 4 hours instead of 6, Parallel GC may be the right tool.
If your users are waiting for responses, it probably is not.

### G1 GC (Garbage-First)

\index{G1 GC}

G1 has been the default since Java 9.
It divides the heap into a grid of equal-sized **regions** (1--32 MB each, chosen automatically based on heap size).
Any region can play the role of Eden, survivor, or old gen --- the classification is dynamic.

G1 runs most of its work concurrently with the application, collects the regions with the most garbage first (hence "Garbage-First"), and aims to meet a configurable pause target:

```
-XX:MaxGCPauseMillis=200
```

This is a **goal**, not a hard guarantee, but G1 uses it to decide how many regions to collect per pause.
G1 is the right default for heaps from 4 GB upward and applications that need balanced throughput and latency.

### ZGC

\index{ZGC}

ZGC (available in production since Java 15, default in some distributions) performs almost all its work concurrently with the application.
Pauses are typically under 1 ms regardless of heap size --- ZGC has been measured with terabyte heaps and sub-millisecond pauses.
It uses **load barriers** and colored pointers to perform concurrent compaction: the application keeps running while ZGC relocates live objects and updates references.

ZGC is the right choice for latency-sensitive applications --- real-time trading systems, game servers, interactive services --- where a 200 ms stop-the-world pause is unacceptable.

Enable it:

```
java -XX:+UseZGC -Xmx16g MyApp
```

### Shenandoah

\index{Shenandoah GC}

Shenandoah has similar goals to ZGC: concurrent compaction and sub-millisecond pauses.
It is developed by Red Hat and is available in OpenJDK distributions.
The implementation approach differs from ZGC (Shenandoah uses a forwarding pointer scheme rather than colored pointers), but the operational story is the same: enable it and your long pauses go away at the cost of some throughput overhead from the barriers.

::: {.tip}
**Wut:** GC pause time and GC throughput are inversely related.
Concurrent collectors like ZGC and Shenandoah keep the application running during most GC work, which eliminates long pauses --- but the concurrent work still consumes CPU cycles that your application could otherwise use.
On a heavily loaded system, you may need more cores to compensate.
:::

## Key JVM Flags

\index{JVM flags}

A quick reference of the flags you will use most often:

| Flag | Example | Effect |
|:-----|:--------|:-------|
| `-Xms<size>` | `-Xms512m` | Initial heap size |
| `-Xmx<size>` | `-Xmx4g` | Maximum heap size |
| `-XX:+UseZGC` | | Select ZGC |
| `-XX:+UseG1GC` | | Select G1 (default since Java 9) |
| `-XX:+UseParallelGC` | | Select Parallel GC |
| `-XX:MaxGCPauseMillis=N` | `-XX:MaxGCPauseMillis=100` | G1 pause goal (ms) |
| `-XX:MaxMetaspaceSize=<size>` | `-XX:MaxMetaspaceSize=256m` | Cap metaspace |
| `-XX:+HeapDumpOnOutOfMemoryError` | | Write heap dump on OOM |
| `-XX:HeapDumpPath=<path>` | `-XX:HeapDumpPath=/tmp/heap.hprof` | Heap dump location |
| `-Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=20m` | | GC log to rotating file |
| `-XX:+PrintCompilation` | | Log JIT compilations |
| `-XX:CompileThreshold=N` | `-XX:CompileThreshold=5000` | Invocations before C2 |

Size suffixes: `k` (kilobytes), `m` (megabytes), `g` (gigabytes).

A production-ready command line for a G1-based service might look like:

```
java \
  -Xms2g -Xmx2g \
  -XX:+UseG1GC \
  -XX:MaxGCPauseMillis=100 \
  -XX:MaxMetaspaceSize=256m \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/var/log/myapp/heap.hprof \
  -Xlog:gc*:file=/var/log/myapp/gc.log:time,uptime:filecount=5,filesize=20m \
  -jar myapp.jar
```

## Reading GC Logs

\index{GC log}
\index{-Xlog:gc}

Modern JVM GC logging uses the unified logging framework (`-Xlog:gc*`).
Here is a representative G1 Young collection log line:

```
[2.345s][info][gc] GC(4) Pause Young (Normal) (G1 Evacuation Pause)
    Eden: 256M->0B(256M) Survivors: 32M->32M Heap: 512M->288M(2048M) 8.234ms
```

Breaking it down:

| Field | Value | Meaning |
|:------|:------|:--------|
| `[2.345s]` | 2.345 seconds | JVM uptime at GC start |
| `GC(4)` | 4 | GC event sequence number |
| `Pause Young (Normal)` | | Minor GC, not triggered by unusual pressure |
| `G1 Evacuation Pause` | | G1 evacuated live objects to survivor/old |
| `Eden: 256M->0B(256M)` | 256 MB → 0 | Eden before→after (capacity) |
| `Survivors: 32M->32M` | 32 MB | Survivor usage before→after |
| `Heap: 512M->288M(2048M)` | 512 → 288 MB | Heap before→after (max) |
| `8.234ms` | 8.2 ms | Pause duration |

A **Mixed** collection label (`Pause Mixed`) means G1 is also collecting some old-generation regions alongside young.
A **Full GC** label is a warning sign: it means G1 could not keep up with promotion pressure and fell back to a stop-the-world full collection.

What to look for in GC logs:

- **Pause spikes:** occasional long pauses (> your `MaxGCPauseMillis` target) indicate G1 is being forced to collect more regions than planned, often due to high allocation rates or large objects bypassing the young generation.
- **Frequent Full GCs:** the heap is too small, the old generation is filling faster than concurrent marking can reclaim it, or you have a memory leak.
- **Heap not shrinking after major GC:** live objects are accumulating; suspect a leak.

::: {.tip}
**Tip:** GCeasy (https://gceasy.io) is a free web tool that parses GC logs and produces visualizations.
Upload your `gc.log` and it will show you pause distributions, allocation rates, and promotion rates without you having to parse the log by hand.
:::

## JVM Diagnostic Tools

\index{JVM!diagnostic tools}

The JDK ships a suite of command-line tools.
Here they are, with the closest C++ equivalent in parentheses.

### `jps`

\index{jps}

```
jps -l
```

Lists running JVM processes with their PID and main class or JAR name.
(Equivalent: `ps aux | grep java`.)

```
12345 com.example.MyApp
12390 org.apache.catalina.startup.Bootstrap
12401 sun.tools.jps.Jps
```

### `jstack`

\index{jstack}

```
jstack <pid>
```

Prints a thread dump: every thread in the JVM with its current stack trace and lock status.
(Equivalent: `pstack <pid>` or `gdb -p <pid>` then `thread apply all bt`.)
Thread dumps are invaluable for diagnosing deadlocks (`jstack` will call out "Found one Java-level deadlock" and show the threads involved) and for identifying threads stuck in I/O or waiting on a lock.

### `jmap`

\index{jmap}

```
jmap -heap <pid>          # print heap summary
jmap -dump:format=b,file=heap.hprof <pid>   # write heap dump
```

`jmap -heap` shows heap region sizes and GC configuration.
The heap dump is a binary snapshot of every live object on the heap at that instant --- load it in VisualVM or Eclipse MAT to find memory leaks.
(Equivalent: `valgrind --tool=massif` for heap profiling; heap dumps are more powerful for finding leak suspects.)

::: {.tip}
**Trap:** Taking a heap dump with `jmap -dump` requires a brief stop-the-world pause on older JVMs.
On Java 17+ you can use `jcmd <pid> GC.heap_dump filename=heap.hprof` which is slightly safer.
Either way, do not use `jmap` on a latency-sensitive production process without understanding the pause implications.
:::

### `jstat`

\index{jstat}

```
jstat -gcutil <pid> 1000
```

Prints GC utilization statistics every 1000 ms (1 second).
(Equivalent: `vmstat` / `perf stat`.)

```
  S0     S1     E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
  0.00  12.50  34.21  45.67  94.32  90.11     42    0.834     1    0.210    1.044
```

Column key: `S0`/`S1` = survivor space utilization (%), `E` = Eden %, `O` = old gen %, `M` = metaspace %, `YGC`/`YGCT` = young GC count/time, `FGC`/`FGCT` = full GC count/time, `GCT` = total GC time.
Watch `O` climbing steadily --- that is a memory leak in progress.

### `jcmd`

\index{jcmd}

`jcmd` is the Swiss Army knife of JVM diagnostics.
Start with:

```
jcmd <pid> help
```

Key sub-commands:

| Command | Effect |
|:--------|:-------|
| `VM.flags` | Print all active JVM flags |
| `GC.heap_info` | Heap summary (like `jmap -heap`) |
| `GC.heap_dump filename=heap.hprof` | Write heap dump |
| `Thread.print` | Thread dump (like `jstack`) |
| `JFR.start duration=60s filename=recording.jfr` | Start a JFR recording |
| `JFR.stop` | Stop a running recording |

### VisualVM

\index{VisualVM}

VisualVM is a graphical profiler and heap analyzer available at https://visualvm.github.io.
It connects to a running JVM (local or remote via JMX) and shows live CPU usage, heap usage, thread activity, and GC behavior.
You can take heap dumps and browse the object histogram interactively.
(Closest C++ equivalent: Valgrind Massif Visualizer for heap data; Instruments on macOS for CPU.)

### Java Flight Recorder and Java Mission Control

\index{Java Flight Recorder}
\index{JFR}
\index{Java Mission Control}
\index{JMC}

**Java Flight Recorder (JFR)** is a low-overhead, always-on profiling framework built into the JDK (fully open-sourced since Java 11).
It records CPU samples, GC events, class loading, lock contention, I/O wait, and dozens of other event types continuously, with overhead typically around 1--2% --- low enough to run in production.

Start a 60-second recording:

```
jcmd <pid> JFR.start duration=60s filename=/tmp/nothing-else-matters.jfr
```

Or from the command line at startup:

```
java -XX:StartFlightRecording=duration=60s,filename=/tmp/recording.jfr MyApp
```

Open the resulting `.jfr` file in **Java Mission Control (JMC)** (available at https://adoptium.net/jmc) for a rich GUI that shows flame graphs, GC pause timelines, heap allocation profiles, lock contention hot spots, and more.

(Equivalent: `perf record -g java ...` + `perf report` for CPU; `async-profiler` is a popular alternative that attaches to a running JVM and produces flamegraphs without the JMC GUI.)

::: {.tip}
**Tip:** `async-profiler` (https://github.com/async-profiler/async-profiler) is worth keeping in your toolbox alongside JFR.
It uses `perf_events` and `AsyncGetCallTrace` to profile both Java frames and native frames (JVM internals, JNI calls) in the same flamegraph.
JFR is broader and lower overhead; `async-profiler` gives you the full native stack when you need to see what the JVM itself is doing.
:::

## Key Points

- Class loaders form a three-tier delegation chain: Bootstrap (core JDK, written in C++) → Platform → Application (your classpath).
  The parent is always tried first, which prevents rogue classes from shadowing core JDK types.
- Custom class loaders enable isolation (OSGi, app servers); each loader defines its own class namespace --- the same bytecode loaded by two different loaders produces two distinct, incompatible `Class<?>` objects.
- HotSpot's tiered compilation has five levels: interpreter (L0), C1 with no profiling (L1), C1 with light profiling (L2), C1 with full profiling (L3), and C2 with aggressive optimization (L4); a method reaches L4 after approximately 10,000 invocations.
- C2 can devirtualize and inline virtual calls based on runtime profile data --- something static C++ AOT compilation cannot do in the general case.
- The heap is divided into young generation (Eden + two survivor spaces) and old generation; allocation in Eden is a cheap pointer bump; objects surviving enough minor GCs are promoted to old gen; Metaspace (Java 8+) holds class metadata in native memory outside the Java heap.
- Set `-Xms` equal to `-Xmx` in production to avoid heap resize overhead; cap Metaspace with `-XX:MaxMetaspaceSize` to guard against class-loader leaks.
- The five GC choices: Serial (single-threaded STW, small heaps), Parallel (multi-threaded STW, max throughput), G1 (default since Java 9, balanced, configurable pause target), ZGC and Shenandoah (sub-millisecond concurrent compaction, latency-sensitive apps).
- Key GC log fields: uptime, event sequence number, collection type (Young/Mixed/Full), Eden/survivor/heap before→after, and pause duration in ms; Full GC entries are a warning sign.
- `jps` lists JVM processes; `jstack` prints thread dumps; `jmap` takes heap dumps; `jstat -gcutil` streams GC stats; `jcmd` covers all of the above plus JFR control.
- JFR + JMC is the production-safe profiling stack (~1--2% overhead); `async-profiler` adds native-frame visibility useful when profiling JVM internals or JNI code.

   What security and stability guarantees does this provide?
   What legitimate reason might an application server have for *breaking* parent delegation (loading a child-loader class before asking the parent), and what problems can that cause?

2. **What does this do?**

    ```java
    public class LoaderQuiz {
        public static void main(String[] args) {
            ClassLoader cl = LoaderQuiz.class.getClassLoader();
            while (cl != null) {
                System.out.println(cl.getClass().getSimpleName());
                cl = cl.getParent();
            }
            System.out.println("(bootstrap)");
        }
    }
    ```

    How many lines does this print, and what are they?
    What does `getParent()` return when it reaches the Bootstrap loader, and why?

3. **Calculation:** A JVM is configured with `-Xmx4g -XX:+UseG1GC`.
   G1 selects a region size of 4 MB.
   The heap is therefore divided into 1,024 regions total.
   If the young generation currently occupies 20% of the heap and the old generation occupies 55%, how many regions are in each category?
   How many are unallocated (available for G1 to assign as needed)?
