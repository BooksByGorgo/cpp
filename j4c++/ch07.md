# Inheritance

C++ gives you multiple inheritance, virtual functions you opt into with the `virtual` keyword, and `override` as an optional safety net.
Java takes a different road: single class inheritance only, every method virtual by default, and `@Override` as a compile-time guard you should always use.
The philosophy is "safe by default" --- you have to work to turn off the dynamic dispatch, not to turn it on.
This chapter covers how Java inheritance works, what surprises await C++ programmers, and how `abstract` classes fill the role of C++ pure-virtual base classes.

## `extends` and Single Inheritance

\index{extends@\texttt{extends}}
\index{inheritance!single}

In Java a class inherits from exactly one other class using the `extends` keyword.
There is no `public`, `protected`, or `private` inheritance --- Java inheritance is always public.

```java
public class Artist {
    private String name;

    public Artist(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

public class BandMember extends Artist {
    private String instrument;

    public BandMember(String name, String instrument) {
        super(name);            // must call parent constructor
        this.instrument = instrument;
    }

    public String getInstrument() {
        return instrument;
    }
}
```

`BandMember` inherits `getName()` from `Artist`.
No multiple class inheritance --- `class Foo extends Bar, Baz` is a compile error.
This is a deliberate design choice to avoid the diamond problem entirely.
Multiple *interface* inheritance is allowed (covered in Chapter 8).

## All Methods Are Virtual by Default

\index{virtual method}
\index{final@\texttt{final}!method}

This is the single biggest surprise for C++ programmers:

**In Java, every non-`final`, non-`private`, non-`static` method is virtual.**

You do not write `virtual`.
You do not have to think about it.
If a subclass overrides a method, the overriding version is called --- always, for every call through any reference type.

```java
public class Artist {
    public String describe() {
        return "An artist";
    }
}

public class RockBand extends Artist {
    @Override
    public String describe() {               // overrides -- no "virtual" needed
        return "A rock band";
    }
}

public class Demo {
    public static void main(String[] args) {
        Artist a = new RockBand();           // reference type is Artist
        System.out.println(a.describe());    // prints: A rock band
    }
}
```

The call `a.describe()` dispatches to `RockBand.describe()` even though `a` is declared as `Artist`.
In C++ you would need `virtual` in `Artist` to get this behavior.
In Java it happens without any annotation.

::: {.tip}
**Wut:** If you want C++-style non-virtual behavior --- where the declared type determines which method runs --- use `final`:

```java
public final void describe() { ... }   // cannot be overridden
```

Or make the method `private` (private methods are never overridden --- a subclass that defines the same signature gets a *new* method, not an override).
:::

::: {.tip}
**Tip:** The JIT compiler is not naive about this.
When it can prove at runtime that only one implementation exists for a call site (a technique called *devirtualization*), it inlines the call and eliminates the dispatch overhead entirely.
"All methods are virtual" does not mean "all calls are slow."
:::

## `@Override`

\index{Override@\texttt{@Override}}
\index{annotation}

`@Override` is an annotation --- metadata attached to the method that tells the compiler "this method is intended to override a parent class method."
If no such method exists in any ancestor, the compiler reports an error.

```java
public class RockBand extends Artist {
    @Override
    public String descrebe() {   // compile error: typo -- no such method in Artist
        return "A rock band";
    }
}
```

Without `@Override`, the typo would silently compile as a brand-new method.
Calls through an `Artist` reference would still dispatch to `Artist.describe()`, and the bug would be invisible until runtime (if ever).

::: {.tip}
**Tip:** Always use `@Override`.
It is the Java equivalent of C++11's `override` specifier, except that in Java it is an annotation rather than a keyword.
The cost is two characters.
The benefit is catching an entire class of subtle bugs at compile time.
:::

## `super`

\index{super@\texttt{super}}

`super` gives you access to the parent class's members.
It has two uses.

**Calling a parent constructor** --- must be the first statement in the subclass constructor:

```java
public BandMember(String name, String instrument) {
    super(name);    // calls Artist(String)
    this.instrument = instrument;
}
```

If you do not write a `super(...)` call, the compiler inserts `super()` automatically.
If the parent class has no no-argument constructor, this causes a compile error.

**Calling a parent method** --- useful when you want to extend, not replace, the parent's behavior:

```java
@Override
public String describe() {
    return super.describe() + " (rock band)";
}
```

::: {.tip}
**Trap:** Unlike `this(...)` and `super(...)` in constructors, `super.method()` can be called anywhere in a method body, not just as the first statement.
Do not confuse the constructor-delegation rules with method-call rules.
:::

## `final` Classes and Methods

\index{final@\texttt{final}!class}
\index{final@\texttt{final}!method}

`final` on a class prevents extension:

```java
public final class Anthem {
    // no subclass can extend this
}
```

`String` is a `final` class.
So is `Integer`, `Double`, and every other wrapper type.
Making them final lets the JVM and JIT make strong assumptions about their behavior.

`final` on a method prevents overriding in subclasses while still allowing inheritance of the method itself:

```java
public class Artist {
    public final String getName() {
        return name;
    }
}
```

Subclasses inherit `getName()` but cannot override it.

::: {.tip}
**Tip:** If a method is part of your class's internal invariant --- something that must never be changed by a subclass --- mark it `final`.
This communicates intent clearly and lets the compiler (and JIT) optimize aggressively.
:::

## `instanceof` and Casting

\index{instanceof@\texttt{instanceof}}
\index{casting}
\index{ClassCastException@\texttt{ClassCastException}}

`instanceof` checks the runtime type of an object:

```java
Artist a = new BandMember("Dolores O'Riordan", "vocals");
System.out.println(a instanceof Artist);     // true
System.out.println(a instanceof BandMember); // true
```

### Classic Cast (Pre-Java 16)

Before Java 16, you test with `instanceof` and then cast separately:

```java
if (a instanceof BandMember) {
    BandMember bm = (BandMember) a;
    System.out.println(bm.getInstrument());
}
```

If you cast without checking, or the check lies (it cannot, but the logic might), you get a `ClassCastException` at runtime --- Java's equivalent of a failed `dynamic_cast`.

### Pattern Matching `instanceof` (Java 16+)

\index{pattern matching}
\index{instanceof!pattern matching}

Java 16 introduced pattern matching for `instanceof`.
The test and the cast happen in one step:

```java
if (a instanceof BandMember bm) {
    System.out.println(bm.getInstrument());  // bm is in scope here
}
```

If the test fails, `bm` is never bound.
If it succeeds, `bm` is already cast and ready to use.
This eliminates the redundant cast and makes the code harder to get wrong.

::: {.tip}
**Tip:** Prefer pattern matching `instanceof` (Java 16+) over the classic test-then-cast idiom.
It is shorter, clearer, and removes the window where the cast can fail unexpectedly.
:::

## Abstract Classes

\index{abstract class}
\index{abstract method}

An `abstract` class cannot be instantiated --- it exists to be extended.
An `abstract` method has no body --- subclasses must provide one.
This is Java's equivalent of C++ pure virtual functions.

```java
public abstract class Musician {
    private String name;

    public Musician(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    // subclass must implement this -- no body here
    public abstract String perform();
}

public class Vocalist extends Musician {
    public Vocalist(String name) {
        super(name);
    }

    @Override
    public String perform() {
        return getName() + " sings: 'Zombie, zombie, zombie-ie-ie...'";
    }
}
```

Trying to instantiate `Musician` directly is a compile error:

```java
Musician m = new Musician("nobody");  // compile error: Musician is abstract
```

A subclass that does not implement all abstract methods must itself be declared `abstract`.

The comparison with C++ is direct:

| C++ | Java |
|:---|:---|
| `virtual void foo() = 0;` | `public abstract void foo();` |
| class with any pure virtual | `abstract class` |
| cannot instantiate abstract class | same |
| subclass must override all pure virtuals | same |

Unlike a C++ abstract base class, a Java `abstract` class can have constructors --- they are called via `super(...)` from subclass constructors.

::: {.tip}
**Tip:** Use `abstract` classes when you want to share implementation (fields, concrete methods) across a family of subclasses while forcing them to provide specific behavior.
When you only need to define a contract with no shared state, prefer an interface (Chapter 8).
:::

## Key Points

- `extends` gives single class inheritance; Java has no multiple class inheritance by design.
- Every non-`final`, non-`private`, non-`static` method is virtual --- no `virtual` keyword needed.
- Use `final` on a method or class to prevent overriding or extension.
- Always annotate overriding methods with `@Override` to catch typos and signature mismatches at compile time.
- `super(...)` in a constructor calls the parent constructor and must be the first statement; the compiler inserts `super()` if you omit it.
- `super.method()` calls the parent's implementation from inside an overriding method.
- `instanceof` checks runtime type; Java 16+ pattern matching binds the cast in one step.
- `abstract` classes cannot be instantiated and may contain `abstract` methods that subclasses must implement.

1. **Think about it:** Java makes all methods virtual by default while C++ requires the `virtual` keyword.
   What are the design tradeoffs of each approach?
   Under what circumstances might a Java program suffer a performance penalty from virtual dispatch, and how does the JIT mitigate it?

2. **What does this print?**

    ```java
    public class Base {
        public String name() { return "Base"; }
    }

    public class Derived extends Base {
        @Override
        public String name() { return "Derived"; }

        public String superName() { return super.name(); }
    }

    public class Main {
        public static void main(String[] args) {
            Base b = new Derived();
            System.out.println(b.name());
            Derived d = new Derived();
            System.out.println(d.superName());
        }
    }
    ```

3. **Calculation:** Given the following hierarchy, how many abstract methods must `C` implement to be concrete (instantiable)?

    ```java
    abstract class A {
        public abstract void foo();
        public abstract void bar();
        public void baz() {}
    }

    abstract class B extends A {
        @Override
        public void foo() {}
    }

    class C extends B {
        // what goes here?
    }
    ```

4. **Where is the bug?**

    ```java
    public class Album {
        private String title;

        public Album(String title) { this.title = title; }

        public String getTitle() { return title; }
    }

    public class LiveAlbum extends Album {
        private String venue;

        public LiveAlbum(String title, String venue) {
            this.venue = venue;         // bug is here
            super(title);
        }

        public String getVenue() { return venue; }
    }
    ```

5. **Write a program:** Write an abstract class `Shape` with a `String name` field, a constructor, a concrete `getName()` method, and two abstract methods: `double area()` and `double perimeter()`.
   Implement two concrete subclasses: `Circle` (with radius) and `Rectangle` (with width and height).
   In `main`, create a `Shape[]` array containing one `Circle` and one `Rectangle`, iterate over it, and print each shape's name, area, and perimeter.
   Use `@Override` on all overriding methods.
