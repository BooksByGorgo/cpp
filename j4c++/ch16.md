# Records and Value Classes

C++ programmers know the pain: you want a simple data carrier --- a point, a named result, a configuration tuple --- and you end up writing a constructor, a fistful of getters, `operator==`, and a stream overload.
Java used to be just as bad.
Java 16 introduced `record`, a concise class form for immutable, transparent data holders that generates all that boilerplate for you automatically.
Java 25 goes further with **value classes**, giving the JVM permission to optimize identity-free objects by eliminating heap allocation entirely.

This chapter covers records: what they generate, how to validate or normalize their inputs with compact constructors, what you can and cannot do with them, and when to reach for a record versus a regular class.
It closes with a brief look at value classes in Java 25 preview.

## Records as Immutable Data Carriers

\index{record}
\index{record!as immutable data carrier}

A `record` declaration is the complete definition of the type.
No body is required for the common case:

```java
record Point(int x, int y) {}
```

Compare that to what you would write in C++ if you wanted the same semantics --- immutable fields, structural equality, and a readable `toString()`:

```cpp
struct Point {
    const int x;
    const int y;

    Point(int x, int y) : x(x), y(y) {}

    bool operator==(const Point& o) const { return x == o.x && y == o.y; }

    friend std::ostream& operator<<(std::ostream& os, const Point& p) {
        return os << "Point[x=" << p.x << ", y=" << p.y << "]";
    }
};
```

Seven lines of boilerplate vs one.
The Java `record` wins by a lot.

### What the Compiler Generates

\index{record!generated members}

For `record Point(int x, int y)`, the compiler automatically generates:

| Member | Signature | Description |
|:---|:---|:---|
| Canonical constructor | `Point(int x, int y)` | Assigns fields |
| `x` accessor | `int x()` | Returns the `x` component |
| `y` accessor | `int y()` | Returns the `y` component |
| `equals` | `boolean equals(Object o)` | Structural equality |
| `hashCode` | `int hashCode()` | Consistent with `equals` |
| `toString` | `String toString()` | `"Point[x=1, y=2]"` format |

::: {.tip}
**Wut:** Record accessor methods are named after the component --- `x()` and `y()`, not `getX()` and `getY()`.
This is intentional: records are meant to feel like transparent value types, not JavaBean property bags.
If you call `getX()` on a record you will get a `NoSuchMethodException` at runtime and a compile error at call sites.
:::

Here is the full record in action:

```java
// "MMMBop" - Hanson (1997)
record Song(String title, String artist, int year) {}

public class RecordDemo {
    public static void main(String[] args) {
        var s1 = new Song("MMMBop", "Hanson", 1997);
        var s2 = new Song("MMMBop", "Hanson", 1997);

        System.out.println(s1.title());           // MMMBop
        System.out.println(s1.artist());          // Hanson
        System.out.println(s1.year());            // 1997
        System.out.println(s1);                   // Song[title=MMMBop, artist=Hanson, year=1997]
        System.out.println(s1.equals(s2));        // true
        System.out.println(s1 == s2);             // false  (different objects)
    }
}
```

Notice that `s1.equals(s2)` is `true` even though `s1 == s2` is `false`.
Records use structural (value) equality, just like a C++ `struct` with `operator==` comparing each field.
`==` still compares object identity --- the reference addresses --- not content.

## Compact Constructors

\index{record!compact constructor}

Sometimes you need to validate or normalize a record's inputs without giving up the auto-generated field assignments.
A **compact constructor** lets you write validation logic; the compiler inserts the field assignments for you at the end:

```java
record BoundedInt(int value, int min, int max) {
    BoundedInt {   // no parameter list --- that is what makes it compact
        if (min > max) {
            throw new IllegalArgumentException(
                "min %d > max %d".formatted(min, max));
        }
        value = Math.clamp(value, min, max);   // normalize before assignment
    }
}
```

Inside a compact constructor the parameters are mutable local variables.
You can reassign them --- and any reassignment you make is what gets stored in the field.
The actual `this.value = value;` lines are generated *after* the compact body runs.

::: {.tip}
**Tip:** Use compact constructors for input validation (`throw` if bad) or normalization (clamp, trim, sort).
Do not do heavy computation in them --- keep them fast and side-effect-free.
:::

::: {.tip}
**Trap:** If you write a full canonical constructor (one with a parameter list), the compiler does **not** generate the field assignments --- you must write them yourself.
The compact constructor form (no parameter list) is the one that gets auto-generated assignments.
:::

Here is a concrete example with a range type used to represent chart positions:

```java
record ChartRange(int first, int last) {
    ChartRange {
        if (first < 1)    throw new IllegalArgumentException("first must be >= 1");
        if (last < first) throw new IllegalArgumentException("last must be >= first");
    }

    int span() { return last - first + 1; }
}

public class CompactDemo {
    public static void main(String[] args) {
        var top10 = new ChartRange(1, 10);
        System.out.println(top10.span());  // 10

        var bad = new ChartRange(5, 3);    // throws IllegalArgumentException
    }
}
```

## What Records Can and Cannot Do

\index{record!restrictions}
\index{record!capabilities}

Records are deliberately restricted.
Understanding the boundaries helps you decide when a record is the right tool.

### Records Are Implicitly Final

\index{record!final}

A `record` is always `final` --- you cannot extend it.
Attempting to `extend` a record causes a compile error.
This mirrors the C++ intuition that a `const`-member struct should not be a base class: immutability and inheritance are awkward together.

Records *can* implement interfaces, which gives you polymorphism without inheritance:

```java
interface Printable {
    void print();
}

record Point(int x, int y) implements Printable {
    @Override
    public void print() {
        System.out.printf("(%d, %d)%n", x, y);
    }
}
```

### Additional Methods and Static Members

Records can have instance methods, static fields, and static methods.
They cannot have instance fields beyond the record components.

```java
record Song(String title, String artist, int year) {
    // Static field is allowed
    static final int DECADE_START = 1990;

    // Instance method is allowed
    boolean isNineties() {
        return year >= 1990 && year < 2000;
    }

    // Static factory is allowed
    static Song unknown() {
        return new Song("Unknown", "Unknown", 0);
    }
}
```

::: {.tip}
**Trap:** You cannot add extra instance fields to a record.
The record's state is entirely defined by its component list.
If you need a derived field, use a method that computes it on the fly (as `isNineties()` does above), or make it a `static` field.
:::

### Nested and Local Records

Records can be declared as nested types (including inside methods), which is useful for local data grouping:

```java
public class ChartProcessor {
    public List<String> topArtists(List<Song> songs) {
        record ArtistCount(String artist, long count) {}

        return songs.stream()
            .collect(java.util.stream.Collectors.groupingBy(
                Song::artist, java.util.stream.Collectors.counting()))
            .entrySet().stream()
            .map(e -> new ArtistCount(e.getKey(), e.getValue()))
            .sorted(java.util.Comparator.comparingLong(ArtistCount::count).reversed())
            .map(ArtistCount::artist)
            .toList();
    }
}
```

## Records vs Regular Classes

\index{record!vs class}

The rule of thumb: reach for a `record` when you want an **immutable data carrier** with transparent state.

| Need | Use |
|:---|:---|
| Immutable, transparent data (DTO, result type, coordinate) | `record` |
| Mutable state | regular `class` |
| Inheritance hierarchy | regular `class` |
| Complex encapsulation (hide implementation) | regular `class` |
| Structural equality by default | `record` |
| Identity semantics (same object = same entity) | regular `class` |

Common record use cases include Data Transfer Objects (DTOs) that cross API or layer boundaries, coordinate and geometry types, typed result types (instead of `Pair<A,B>`), and configuration bundles:

```java
// DTO for an HTTP response body
record ApiResponse(int statusCode, String body, String contentType) {}

// Typed result instead of Pair<Boolean, String>
record ValidationResult(boolean valid, String message) {}

// Configuration bundle
record DbConfig(String host, int port, String database, int poolSize) {}
```

::: {.tip}
**Tip:** Records make great `Map.Entry` replacements for typed pairs.
`record Pair<A, B>(A first, B second) {}` gives you structural equality, a clean `toString()`, and named accessors --- all things raw `Map.Entry` does not provide.
:::

## Value Classes (Java 25 Preview)

\index{value class}
\index{Project Valhalla}

Java 25 introduces **value classes** as a preview feature under Project Valhalla.
A value class is an immutable, **identity-free** class.
"Identity-free" means the JVM is not required to give each instance a unique object address --- it can store them on the stack, pass them by value in registers, or inline them into containing objects, just as C++ does with plain structs.

The syntax uses `value class`:

```java
// Java 25 preview --- requires --enable-preview
value class Point(int x, int y) {}
```

The distinction from records:

- A `record` is a Java-language feature for concise, transparent data holders; it is still a heap-allocated reference type by default.
- A `value class` is a JVM-level hint that this type has no identity and can be flattened; the JVM can choose to optimize storage and calling conventions.
- In future Java versions, records and value classes are expected to converge: a `record` that is also a `value` class gets both the language convenience and the JVM optimization.

::: {.tip}
**Wut:** Even today, the JVM applies some value-type optimizations to primitives and to small records through escape analysis and scalar replacement --- but only informally and not guaranteed.
Value classes make the optimization contract explicit and reliable.
:::

Value classes carry all the restrictions of records (immutable, final) plus one more: they cannot be `null` by default (nullable value types are spelled `Point?` in Valhalla terminology and are still being finalized as of Java 25).
For most code today, records are the practical tool; value classes are the direction Java is heading.

## Key Points

- A `record` declaration generates a canonical constructor, component accessor methods (named `x()` not `getX()`), `equals`, `hashCode`, and `toString` automatically.
- Record fields are implicitly `private final`; their state is fixed at construction time.
- Compact constructors (no parameter list) let you validate or normalize inputs; field assignment is injected by the compiler after the body runs.
- Records are implicitly `final` --- they cannot be extended, but they can implement interfaces.
- Records can have static fields and methods, and additional instance methods, but no extra instance fields.
- Use records for immutable data carriers: DTOs, coordinates, result types, typed pairs.
- Use regular classes when you need mutability, inheritance, or encapsulation of hidden state.
- Value classes (Java 25 preview, Project Valhalla) are identity-free types the JVM can store on the stack and pass by value, similar to C++ plain structs.

## Exercises

1. **Think about it:** Records enforce structural equality: two `Song("MMMBop", "Hanson", 1997)` instances are `equals()`.
   A regular class with the same fields and no overridden `equals` would not be.
   In what kinds of applications is structural equality the right default?
   Can you think of a domain where structural equality would be the *wrong* default for an object that has the same fields as a record?

2. **What does this print?**

    ```java
    record Track(String title, int bpm) {
        Track {
            bpm = Math.max(bpm, 60);
        }
        boolean isDance() { return bpm >= 120; }
    }

    public class Q2 {
        public static void main(String[] args) {
            var t1 = new Track("MMMBop", 170);
            var t2 = new Track("MMMBop", 40);
            var t3 = new Track("MMMBop", 170);
            System.out.println(t1.bpm());
            System.out.println(t2.bpm());
            System.out.println(t1.equals(t3));
            System.out.println(t1.isDance());
            System.out.println(t2.isDance());
            System.out.println(t1);
        }
    }
    ```

3. **Calculation:** A `record Song(String title, String artist, int year)` is compiled.
   How many methods does the compiler generate automatically (not counting any methods you add yourself)?
   List them by name.

4. **Where is the bug?**

    ```java
    record Interval(int start, int end) {
        Interval(int start, int end) {
            if (start > end) throw new IllegalArgumentException("bad range");
        }

        int length() { return end - start; }
    }

    public class Q4 {
        public static void main(String[] args) {
            var i = new Interval(3, 7);
            System.out.println(i.length()); // expected: 4
        }
    }
    ```

5. **Write a program:** Define a record `Rectangle(double width, double height)` with a compact constructor that throws `IllegalArgumentException` if either dimension is not positive.
   Add instance methods `area()` and `perimeter()`.
   Write a `main` method that creates several rectangles, prints their area and perimeter, and demonstrates that two rectangles with the same dimensions are `equals()`.
