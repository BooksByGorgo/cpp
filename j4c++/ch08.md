# Interfaces and Abstract Classes

In C++ you build polymorphic contracts with abstract base classes --- virtual functions, pure virtuals, vtables.
Java has abstract classes too (covered in Chapter 7), but it also has a separate mechanism that C++ lacks: the interface.
An interface is a pure contract: no instance state, just method signatures and (since Java 8) optional default implementations.
Because interfaces carry no data, a class can implement as many of them as it likes, giving Java its answer to multiple inheritance without the diamond problem.
This chapter covers interfaces in depth, explains when to reach for an abstract class instead, and introduces `Comparable` and `Comparator` --- two interfaces every Java programmer uses constantly.

## Interface Semantics

\index{interface}
\index{implements@\texttt{implements}}

An interface is declared with the `interface` keyword.
Before Java 8 it could hold only abstract method signatures (and `public static final` constants).
A class opts in with `implements`:

```java
public interface Playable {
    void play();    // implicitly public and abstract
    void stop();
}

public class Track implements Playable {
    private String title;

    public Track(String title) {
        this.title = title;
    }

    @Override
    public void play() {
        System.out.println("Playing: " + title);
    }

    @Override
    public void stop() {
        System.out.println("Stopped: " + title);
    }
}
```

A class can implement multiple interfaces:

```java
public class Track implements Playable, Serializable, Comparable<Track> {
    // must implement all abstract methods from all interfaces
}
```

Compared to a C++ abstract base class:

| C++ ABC | Java interface (pre-Java 8) |
|:---|:---|
| Can have data members | No instance fields (only `public static final` constants) |
| Can have `protected` methods | All methods implicitly `public` (pre-Java 9) |
| Single inheritance of state | Implement as many interfaces as you like |
| `virtual void foo() = 0;` | `void foo();` (implicitly abstract) |

::: {.tip}
**Wut:** Fields declared inside an interface are implicitly `public static final`.
You cannot declare instance variables in an interface.
If you need shared state, use an abstract class.
:::

## Default and Static Interface Methods (Java 8+)

\index{interface!default method}
\index{interface!static method}

Java 8 added two kinds of methods with bodies to interfaces.

### Default Methods

A `default` method provides an implementation inside the interface.
Any class that implements the interface gets this implementation for free but can override it:

```java
public interface Playable {
    void play();
    void stop();

    default void restart() {    // free implementation
        stop();
        play();
    }
}
```

Default methods exist primarily so library authors can add methods to existing interfaces without breaking every class that already implements them.
Before Java 8, adding a method to an interface was a binary-breaking change.

::: {.tip}
**Tip:** When a class implements two interfaces that both declare a default method with the same signature, the class *must* override the method to resolve the ambiguity.
The compiler enforces this.
:::

### Static Methods

\index{interface!static method}

A `static` method in an interface is a utility method tied to the interface type.
It is not inherited --- you call it as `InterfaceName.method()`:

```java
public interface Playable {
    void play();

    static Playable silence() {     // factory utility
        return new Track("[silence]");
    }
}

// call it:
Playable p = Playable.silence();
```

Static interface methods replace the old Java idiom of pairing every interface with a companion utility class (`Collections` for `Collection`, for example).

## Private Interface Methods (Java 9+)

\index{interface!private method}

Java 9 added `private` methods to interfaces.
They exist for one reason: letting multiple `default` methods share helper code without exposing that helper as part of the public API.

```java
public interface Playable {
    void play();
    void stop();

    default void restart() {
        log("restarting");
        stop();
        play();
    }

    default void skipTo(int seconds) {
        log("skipping to " + seconds + "s");
        stop();
        // ... seek ...
        play();
    }

    private void log(String msg) {      // shared helper, not visible to callers
        System.out.println("[Playable] " + msg);
    }
}
```

Without `private` methods, you would have to make `log` a `default` method, polluting the interface's public surface.

## Functional Interfaces and `@FunctionalInterface`

\index{functional interface}
\index{FunctionalInterface@\texttt{@FunctionalInterface}}
\index{lambda}

An interface with exactly one abstract method is a **functional interface**.
It can be used anywhere a lambda expression or method reference is expected (full coverage in Chapter 13).

`@FunctionalInterface` is an optional annotation that documents the intent and causes a compile error if the interface ever gains a second abstract method:

```java
@FunctionalInterface
public interface Transformer {
    String transform(String input);     // the one abstract method
}
```

You can use it immediately with a lambda:

```java
Transformer shout = s -> s.toUpperCase();
System.out.println(shout.transform("Wonderwall")); // WONDERWALL
```

Java's standard library ships many functional interfaces in `java.util.function`.
The most common:

| Interface | Signature | Description |
|:---|:---|:---|
| `Runnable` | `void run()` | action with no input or output |
| `Callable<V>` | `V call() throws Exception` | like `Runnable` but returns a value and can throw |
| `Supplier<T>` | `T get()` | produces a value |
| `Consumer<T>` | `void accept(T t)` | consumes a value |
| `Function<T,R>` | `R apply(T t)` | transforms T to R |
| `Predicate<T>` | `boolean test(T t)` | tests a value |

`Runnable` has been in Java since version 1.0; it predates the concept of functional interfaces but qualifies as one.
`Callable<V>` (in `java.util.concurrent`) is like `Runnable` but can return a result and throw checked exceptions --- useful for tasks submitted to a thread pool.

::: {.tip}
**Tip:** Always annotate your custom functional interfaces with `@FunctionalInterface`.
It costs nothing and protects you from accidentally adding a second abstract method later and silently breaking every lambda that uses the interface.
:::

## Interface vs Abstract Class --- When to Use Which

\index{interface!vs abstract class}
\index{abstract class!vs interface}

The rule of thumb:

- **Use an interface** when you are defining a capability or contract that unrelated classes can share, or when you need multiple inheritance of behavior.
- **Use an abstract class** when subclasses share implementation code, or when you need to maintain instance state common to all subclasses.

A concrete example.
Suppose you are modeling media players.
`Playable` is clearly an interface --- a `Track`, a `Playlist`, and a `PodcastEpisode` can all be playable without sharing any implementation.

But if all concrete players share a `currentPositionMs` field and a `seek(int ms)` method that operates on it, pull those into an abstract class:

```java
public abstract class AbstractPlayer implements Playable {
    protected int currentPositionMs = 0;

    protected void seek(int ms) {
        currentPositionMs = ms;
    }

    @Override
    public void stop() {
        currentPositionMs = 0;
    }
}

public class Track extends AbstractPlayer {
    private String title;

    public Track(String title) {
        this.title = title;
    }

    @Override
    public void play() {
        System.out.println("Playing \"" + title + "\" from " + currentPositionMs + "ms");
    }
}
```

`AbstractPlayer` holds state and implements `stop()`.
`Track` provides only what varies: `play()`.
The interface `Playable` defines the contract that callers depend on.

::: {.tip}
**Tip:** A common Java pattern is: interface for the contract, abstract class for the skeletal implementation, concrete classes for the specifics.
The JDK uses this everywhere --- `List` / `AbstractList` / `ArrayList` is the canonical example.
:::

## `Comparable<T>` and `Comparator<T>`

\index{Comparable@\texttt{Comparable}}
\index{Comparator@\texttt{Comparator}}
\index{natural ordering}

These two interfaces are the canonical Java way to define ordering.

### `Comparable<T>`

\index{compareTo@\texttt{compareTo()}}

Signature: `int compareTo(T other)`

Implement `Comparable<T>` to give your class a **natural ordering** --- the default sort order.
`Collections.sort`, `Arrays.sort`, and `TreeSet`/`TreeMap` all use it.

The contract: return a negative number if `this` is less than `other`, zero if equal, positive if greater.
The simplest way to implement this for a numeric key is `Integer.compare(this.key, other.key)` rather than subtraction (subtraction overflows for large values).

```java
public class Album implements Comparable<Album> {
    private String title;
    private int    year;

    public Album(String title, int year) {
        this.title = title;
        this.year  = year;
    }

    @Override
    public int compareTo(Album other) {
        int cmp = Integer.compare(this.year, other.year);
        if (cmp != 0) return cmp;
        return this.title.compareTo(other.title);   // secondary: alphabetical
    }

    @Override
    public String toString() {
        return "\"" + title + "\" (" + year + ")";
    }

    public static void main(String[] args) {
        java.util.List<Album> albums = new java.util.ArrayList<>();
        albums.add(new Album("Wonderwall (single)", 1995));
        albums.add(new Album("(What's the Story) Morning Glory?", 1995));
        albums.add(new Album("Definitely Maybe", 1994));

        java.util.Collections.sort(albums);

        for (Album a : albums) {
            System.out.println(a);
        }
        // "Definitely Maybe" (1994)
        // "(What's the Story) Morning Glory?" (1995)
        // "Wonderwall (single)" (1995)
    }
}
```

### `Comparator<T>`

\index{compare@\texttt{compare()}}
\index{Comparator!comparing@\texttt{comparing()}}

Signature: `int compare(T o1, T o2)`

`Comparator<T>` provides an **external** ordering without modifying the class.
Use it when you need multiple sort orders, or when you cannot modify the class (e.g., a third-party type).

```java
import java.util.Comparator;
import java.util.List;
import java.util.ArrayList;
import java.util.Collections;

public class AlbumSortDemo {
    public static void main(String[] args) {
        List<Album> albums = new ArrayList<>();
        albums.add(new Album("Wonderwall (single)", 1995));
        albums.add(new Album("(What's the Story) Morning Glory?", 1995));
        albums.add(new Album("Definitely Maybe", 1994));

        // sort by title only, ignoring year
        Comparator<Album> byTitle = Comparator.comparing(a -> a.toString());

        Collections.sort(albums, byTitle);

        for (Album a : albums) {
            System.out.println(a);
        }
    }
}
```

`Comparator.comparing(keyExtractor)` is a static factory method (Java 8+) that builds a comparator from a key extraction function.
Chain `.thenComparing(...)` for secondary sorts.
In most cases you can avoid writing the `compare` method body by hand.

::: {.tip}
**Trap:** Do not implement `compareTo` as `return this.value - other.value`.
Integer overflow turns large positive values into negative numbers, reversing the sort order silently.
Use `Integer.compare(this.value, other.value)` instead.
:::

## Key Points

- An interface defines a contract with no instance state; a class can implement any number of interfaces.
- Before Java 8, all interface methods were implicitly `public abstract`; Java 8 added `default` and `static` methods.
- Java 9 added `private` interface methods to share code among `default` methods without polluting the public API.
- A functional interface has exactly one abstract method; annotate it with `@FunctionalInterface` for compiler protection.
- Use an interface when defining a shared capability across unrelated classes; use an abstract class when sharing state or skeletal implementation.
- `Comparable<T>` gives a class a natural ordering via `compareTo`; `Comparator<T>` provides external, swappable orderings via `compare`.
- Never implement `compareTo` or `compare` using subtraction --- use `Integer.compare` to avoid overflow.
- `Comparator.comparing(keyExtractor)` and `.thenComparing(...)` let you build comparators without writing `compare` by hand.

## Exercises

1. **Think about it:** Java 8 added `default` methods to interfaces.
   Before that, adding a new method to a widely-used interface (like `java.util.Collection`) would break every existing implementation.
   How do `default` methods solve this problem?
   What happens when a class implements two interfaces that both define the same `default` method?

2. **What does this print?**

    ```java
    @FunctionalInterface
    interface Greeter {
        String greet(String name);
    }

    public class Main {
        public static void main(String[] args) {
            Greeter formal = name -> "Good day, " + name + ".";
            Greeter casual = name -> "Hey, " + name + "!";

            System.out.println(formal.greet("Noel"));
            System.out.println(casual.greet("Liam"));

            Greeter[] arr = { formal, casual };
            for (Greeter g : arr) {
                System.out.println(g.greet("Gallagher"));
            }
        }
    }
    ```

3. **Calculation:** You have an interface with 2 `default` methods, 1 `static` method, 1 `private` method, and 3 abstract methods.
   How many methods must a concrete class implement to satisfy this interface?
   How many methods does an instance of that class expose through the interface reference type?

4. **Where is the bug?**

    ```java
    public class Score implements Comparable<Score> {
        private int points;

        public Score(int points) { this.points = points; }

        @Override
        public int compareTo(Score other) {
            return this.points - other.points;  // sorts ascending
        }

        public static void main(String[] args) {
            Score a = new Score(Integer.MAX_VALUE);
            Score b = new Score(-1);
            System.out.println(a.compareTo(b));  // should be positive
        }
    }
    ```

5. **Write a program:** Create an interface `Describable` with a single `default` method `String describe()` that returns `"I am a " + getClass().getSimpleName()`.
   Create two unrelated classes `Song` and `Podcast` that both implement `Describable` (neither class needs to override `describe()`).
   Then add a `Comparator<Song>` that sorts `Song` objects by their `title` field (add a `title` field and constructor).
   In `main`, demonstrate that both `Song` and `Podcast` produce correct output from `describe()`, and sort a list of three `Song` objects using your comparator.
