# Primitives, References, and Variables

Java's type system has a clean split that C++ does not: every type is either a **primitive** or a **reference type**, and the rules for each are different.
Primitives behave a lot like C++ fundamental types, except their sizes are guaranteed by the Java specification --- no more `sizeof(int)` surprises.
Reference types behave like pointers in a straightjacket: safer, more limited, and managed by the garbage collector.
Understanding the boundary between primitives and references --- and the autoboxing machinery that blurs it --- is essential for writing correct, efficient Java.

## Primitive Types

\index{primitive type}

Java has exactly eight primitive types.
Their sizes are **guaranteed by the Java Language Specification**, regardless of the underlying hardware.
This is a deliberate break from C and C++, where `int` can be 16, 32, or 64 bits depending on the platform.

| Type      | Width    | Range / Notes                              |
|:----------|:---------|:-------------------------------------------|
| `byte`    | 8-bit    | -128 to 127, signed                        |
| `short`   | 16-bit   | -32,768 to 32,767, signed                  |
| `int`     | 32-bit   | -2^31^ to 2^31^ - 1, signed               |
| `long`    | 64-bit   | -2^63^ to 2^63^ - 1, signed               |
| `float`   | 32-bit   | IEEE 754 single precision                  |
| `double`  | 64-bit   | IEEE 754 double precision                  |
| `char`    | 16-bit   | UTF-16 code unit, 0 to 65,535 (unsigned)   |
| `boolean` | JVM-defined | `true` or `false` only                 |

\index{int}

Notice a few things that will catch C++ programmers off guard.
There are **no unsigned integer types** --- no `unsigned int`, no `unsigned long`, no `uint32_t`.
Every integer type except `char` is signed.
The `char` type is unsigned but exists solely to hold a UTF-16 code unit; it is not used for general arithmetic.

There is also no `signed char` vs `unsigned char` ambiguity --- `byte` is always signed 8-bit, full stop.

Literal suffixes work similarly to C++: `L` or `l` for `long`, `f` or `F` for `float`, `d` or `D` for `double` (though `double` is the default for floating-point literals).

```java
int    year   = 1994;           // TLC drops "CrazySexyCool"
long   ms     = 1_000_000_000L; // underscore separators (Java 7+)
float  bpm    = 98.6f;
double pi     = 3.14159265358979;
char   grade  = 'A';
boolean cool  = true;
```

::: {.tip}
**Wut:** `boolean` size is intentionally left to the JVM implementation.
A `boolean` field in an object may be stored as a byte; a `boolean[]` array typically uses one byte per element.
You cannot rely on a specific bit width and you cannot cast `boolean` to `int` --- `if (1)` is a compile error in Java (unlike C++).
:::

::: {.tip}
**Tip:** Java 7+ allows underscores in numeric literals as separators (`1_000_000L`, `0xFF_EC_D1_8C`).
Use them freely to improve readability of large constants.
:::

## Reference Types

\index{reference type}
\index{null}

Everything that is not a primitive is a **reference type**.
Strings, arrays, every class you write, every library class you use --- all reference types.

A reference in Java is conceptually a pointer: it holds the memory address of an object on the heap.
But it comes with meaningful restrictions compared to a C++ pointer:

- **No pointer arithmetic.** You cannot add an integer to a reference or subtract two references.
- **No raw memory access.** You cannot cast a reference to an integer and poke at bytes.
- **Null dereference throws.** Dereferencing a `null` reference throws `NullPointerException` instead of producing undefined behavior.
- **No stack-allocated objects.** There is no Java equivalent of `MyClass obj;` on the stack. Objects always live on the heap; the stack holds only primitives and references (the pointer itself).

```java
String song   = "Waterfalls";   // song holds a reference to a String object on the heap
String artist = null;           // valid: artist holds a null reference
int    length = song.length();  // fine
int    boom   = artist.length();// NullPointerException at runtime
```

The stack/heap split in Java is straightforward: **primitive values live on the stack** (or in registers, as an optimization), **objects live on the heap**, and **references (the addresses) live wherever their variable is declared** (on the stack for locals, in the object for fields).

Compare this to C++, where you choose:

```cpp
// C++: you decide where the object lives
MyClass onStack;              // object on the stack, destroyed at scope exit
MyClass* onHeap = new MyClass(); // object on the heap, must delete manually
MyClass& ref    = onStack;    // reference to stack object
```

In Java you have no such choice --- the object always goes on the heap and the GC cleans it up.
This simplifies memory management at the cost of flexibility.

::: {.tip}
**Tip:** Just because objects always live on the heap does not mean Java is automatically slow.
The JIT compiler aggressively optimizes short-lived objects through **escape analysis** --- if the JIT can prove an object never escapes the current method, it may allocate it on the stack anyway.
You get the simple mental model without always paying the heap-allocation price.
:::

## `var` --- Local Variable Type Inference

\index{var}
\index{type inference}

Java 10 introduced `var` for local variable type inference.
It is spelled the same as C++11's `auto` but has a narrower scope.

```java
var song    = "Macarena";           // inferred as String
var year    = 1996;                  // inferred as int
var factors = new ArrayList<Long>(); // inferred as ArrayList<Long>
```

The compiler substitutes the inferred type at compile time.
The bytecode is identical to what you would get with an explicit type.

**Key differences from C++ `auto`:**

- `var` is **local variables only** --- you cannot use it for method parameters, return types, or fields.
- `var` requires an **initializer** --- `var x;` is a compile error.
- `var` does not change the type system; the variable is still statically typed. There is no duck typing.

```java
var x = "Waterfalls"; // String
x = 42;               // compile error: int is not String
```

::: {.tip}
**Trap:** `var` is a **context-sensitive keyword**, not a reserved word.
You can (but should not) have a class or method named `var` --- old code that uses `var` as an identifier is still valid Java.
:::

::: {.tip}
**Tip:** Use `var` when the type is obvious from the right-hand side (constructor calls, casts, factory methods).
Avoid it when the inferred type would surprise a reader, for example when the right-hand side is a method call whose return type is not immediately obvious.
:::

## Wrapper Classes and Autoboxing

\index{wrapper class}
\index{autoboxing}
\index{unboxing}

Java's collections and generics work only with reference types --- you cannot put an `int` in an `ArrayList<int>`.
To bridge this gap, every primitive type has a corresponding **wrapper class**: `Integer`, `Long`, `Double`, `Float`, `Short`, `Byte`, `Character`, and `Boolean`.

| Primitive | Wrapper     |
|:----------|:------------|
| `byte`    | `Byte`      |
| `short`   | `Short`     |
| `int`     | `Integer`   |
| `long`    | `Long`      |
| `float`   | `Float`     |
| `double`  | `Double`    |
| `char`    | `Character` |
| `boolean` | `Boolean`   |

**Autoboxing** is the automatic conversion of a primitive to its wrapper class.
**Unboxing** is the reverse.
The compiler inserts the conversions for you.

```java
List<Integer> chart = new ArrayList<>();
chart.add(1);       // autoboxing: int 1 -> Integer.valueOf(1)
int top = chart.get(0); // unboxing: Integer -> int
```

This is convenient, but it has a trap.

::: {.tip}
**Trap:** Do not use `==` to compare boxed types.
`==` on reference types compares **object identity** (addresses), not values.

```java
Integer a = 127;
Integer b = 127;
System.out.println(a == b);    // true  -- cached range
System.out.println(a.equals(b)); // true

Integer c = 128;
Integer d = 128;
System.out.println(c == d);    // false -- new objects, outside cache
System.out.println(c.equals(d)); // true
```

The JVM caches `Integer` objects in the range -128 to 127, so `==` happens to work there.
Outside that range, each autobox creates a new object and `==` returns `false`.
Always use `.equals()` to compare boxed values.
:::

\index{Integer!cache}

The wrapper classes also provide useful static methods:

```java
int  parsed = Integer.parseInt("1994");  // String -> int
String hex  = Integer.toHexString(1994); // "7ca"
int  max    = Integer.MAX_VALUE;         // 2147483647
```

Some commonly used signatures:

```java
static int     Integer.parseInt(String s)
static int     Integer.parseInt(String s, int radix)
static String  Integer.toBinaryString(int i)
static String  Integer.toHexString(int i)
static String  Integer.toOctalString(int i)
```

`Double.parseDouble(String s)`, `Long.parseLong(String s)`, and the other wrappers follow the same pattern.

## Operators

\index{operators}

Most operators work exactly as they do in C++: `+`, `-`, `*`, `/`, `%`, `++`, `--`, `&&`, `||`, `!`, `&`, `|`, `^`, `~`, `<<`.
A few things differ.

### No Unsigned Right Shift in C++ --- Java Has `>>>`

\index{>>>}
\index{right shift}

Java has **three** shift operators:

- `<<` --- left shift (same as C++)
- `>>` --- **arithmetic** right shift: sign-extends (fills with the sign bit)
- `>>>` --- **logical** right shift: always fills with zero bits (treats the value as unsigned)

In C++, right-shifting a negative signed integer is implementation-defined behavior.
Java nails it down: `>>` is always arithmetic, `>>>` is always logical.

```java
int n = -1;                 // all bits set: 0xFFFFFFFF
System.out.println(n >> 1); // -1: arithmetic shift, fills with 1s
System.out.println(n >>> 1);// 2147483647: logical shift, fills with 0s (0x7FFFFFFF)
```

### No Pointer Arithmetic

\index{pointer arithmetic}

Java has no pointer types, so there is nothing to do arithmetic on.
You cannot increment a reference or compute the byte offset between two objects.

### No Operator Overloading --- Except `+` for String

\index{operator overloading}
\index{String concatenation}

Java does not support user-defined operator overloading.
The `+` operator is overloaded for `String` concatenation by the language itself --- this is the one and only special case.

```java
String s = "La " + "Macarena"; // "La Macarena"
String t = "Year: " + 1996;    // "Year: 1996" -- int is converted to String automatically
```

The compiler rewrites string concatenation using `StringBuilder` (or a JVM intrinsic in modern Java), so chaining many `+` operations in a loop is inefficient --- use `StringBuilder` directly in that case (covered in Ch 9).

::: {.tip}
**Wut:** Concatenating `null` with a `String` does not throw --- it produces the string `"null"`.

```java
String x = null;
System.out.println("Value: " + x); // "Value: null"
```

This is sometimes handy, sometimes a debugging nightmare.
:::

## Key Points

- Java's eight primitive types have **guaranteed sizes** set by the specification; C++ fundamental type sizes are platform-defined.
- There are **no unsigned integer types** (except `char`, which is unsigned but meant for UTF-16 code units).
- Every non-primitive type is a **reference type**: a managed pointer to a heap-allocated object.
- Java references share qualities of C++ pointers (hold an address) but forbid pointer arithmetic and replace undefined behavior with `NullPointerException`.
- **Objects always live on the heap** in Java; the stack holds only primitives and references.
- `var` provides local variable type inference (Java 10+), similar to C++ `auto` but restricted to local variables with initializers.
- **Autoboxing** converts primitives to wrapper classes automatically; use `.equals()` (not `==`) to compare boxed values.
- Java adds the `>>>` logical right-shift operator; C++ right-shifting a signed negative is implementation-defined.
- Java has no user-defined operator overloading; `+` for `String` concatenation is the sole language-defined exception.
