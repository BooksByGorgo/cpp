# Optional

\index{Optional@\texttt{Optional}}

Null references are responsible for more runtime crashes in Java than almost any other single cause.
Tony Hoare, who introduced null references in ALGOL W in 1965, later called it his "billion-dollar mistake" --- a conservative estimate given the decades of `NullPointerException` stack traces that have followed.
Java 14+ improved matters by producing *helpful* NPEs that name the exact variable that was null, but naming the problem is not the same as preventing it.

The real fix is to make "this value might be absent" explicit in the type system.
`Optional<T>` is a container object that either holds exactly one non-null value or holds nothing.
When a method returns `Optional<T>` instead of `T`, the type signature itself tells callers they must handle the absent case.
If you know C++17's `std::optional<T>`, the concept is identical --- the Java API even uses parallel names (`of`, `empty`, `isPresent`, `orElse`, `map`, `flatMap`, `filter`).
The main difference is that Java's `Optional` is a heap-allocated object, not a stack-allocated value type, so you will see it used mainly as a return type rather than as a general "maybe" wrapper the way C++ programmers sometimes use `std::optional`.

## The Null Problem in Java

\index{NullPointerException}
\index{null!billion-dollar mistake}

Consider a simple repository method:

```java
// before Optional -- the null contract is invisible
public Song findByTitle(String title) {
    // returns null if not found -- but the caller has no idea
    ...
}
```

Nothing in the signature warns a caller that null is a possible return value.
The caller may forget to check, and the program crashes far from the source:

```java
Song s = repo.findByTitle("Semi-Charmed Life");
System.out.println(s.artist());   // NullPointerException if not found
```

Java 14+ makes the crash message slightly more helpful:

```
Cannot invoke "Song.artist()" because "s" is null
```

But a better design prevents the crash entirely:

```java
// after Optional -- the type says "you might get nothing"
public Optional<Song> findByTitle(String title) { ... }
```

Now the compiler will not let you call `s.artist()` directly --- you must unwrap the `Optional` first, forcing you to think about the absent case.

::: {.tip}
**Tip:** `Optional` is not about eliminating null from Java entirely.
Null still exists, and internal code still uses it.
`Optional` is a *return type* convention that signals to callers "this method may produce no result."
:::

## Creating Optionals

\index{Optional!of@\texttt{of()}}
\index{Optional!ofNullable@\texttt{ofNullable()}}
\index{Optional!empty@\texttt{empty()}}

Three factory methods cover all creation cases.

`static <T> Optional<T> Optional.of(T value)` wraps a known non-null value.
If you pass null, it throws `NullPointerException` immediately --- that is by design, to catch bugs at the source.

`static <T> Optional<T> Optional.ofNullable(T value)` wraps a value that might be null.
If the value is null, you get an empty `Optional`; otherwise you get a present `Optional`.

`static <T> Optional<T> Optional.empty()` returns an empty `Optional` directly.

```java
Optional<String> present = Optional.of("Semi-Charmed Life");   // present
Optional<String> empty   = Optional.empty();                    // empty

String maybeNull = null;
Optional<String> safe = Optional.ofNullable(maybeNull);         // empty, no NPE
Optional<String> also = Optional.ofNullable("Third Eye Blind"); // present
```

::: {.tip}
**Trap:** `Optional.of(null)` throws `NullPointerException`.
Use `Optional.ofNullable` when the value might legitimately be null (for example, when bridging legacy APIs that return null).
:::

## Checking and Extracting Values

\index{Optional!isPresent@\texttt{isPresent()}}
\index{Optional!isEmpty@\texttt{isEmpty()}}
\index{Optional!get@\texttt{get()}}
\index{Optional!orElse@\texttt{orElse()}}
\index{Optional!orElseGet@\texttt{orElseGet()}}
\index{Optional!orElseThrow@\texttt{orElseThrow()}}

Once you have an `Optional`, several methods let you inspect or extract its value.

### `isPresent` and `isEmpty`

`boolean isPresent()` returns `true` if the `Optional` contains a value.
`boolean isEmpty()` (Java 11+) returns `true` if the `Optional` is empty --- the logical negation of `isPresent()`.

```java
Optional<String> song = Optional.of("Semi-Charmed Life");

System.out.println(song.isPresent());   // true
System.out.println(song.isEmpty());     // false
```

### `get`

`T get()` returns the contained value, or throws `NoSuchElementException` if the `Optional` is empty.

```java
Optional<String> song = Optional.of("Semi-Charmed Life");
String title = song.get();   // "Semi-Charmed Life"
```

::: {.tip}
**Trap:** Calling `get()` without first checking `isPresent()` is as dangerous as dereferencing a pointer without checking for null.
Almost every use of `get()` can be replaced with a safer extraction method.
The Java 16+ linter tool considers `get()` without a guard a likely bug.
:::

### `orElse`

`T orElse(T other)` returns the value if present, or `other` if empty.

```java
Optional<String> empty = Optional.empty();
String title = empty.orElse("Unknown");   // "Unknown"
```

Note that `other` is *always evaluated*, even if the `Optional` is present.
For cheap defaults (a literal, a constant) this is fine.
For expensive defaults, use `orElseGet`.

### `orElseGet`

`T orElseGet(Supplier<? extends T> supplier)` returns the value if present, or calls the supplier to produce a default if empty.
The supplier is only called when the `Optional` is empty.

```java
Optional<String> empty = Optional.empty();
String title = empty.orElseGet(() -> computeExpensiveDefault());   // called only if empty
```

### `orElseThrow`

`T orElseThrow()` (Java 10+) returns the value, or throws `NoSuchElementException` if empty.
`<X extends Throwable> T orElseThrow(Supplier<? extends X> exceptionSupplier)` throws a custom exception of your choosing.

```java
Optional<String> empty = Optional.empty();

// throws NoSuchElementException
String t1 = empty.orElseThrow();

// throws a custom exception
String t2 = empty.orElseThrow(
    () -> new IllegalStateException("Song not found"));
```

Use `orElseThrow` when absence is genuinely an error at the call site --- it makes the intent explicit without the noise of `isPresent` + `get`.

::: {.tip}
**Tip:** `orElseThrow()` with no arguments is the clean replacement for the `get()`-after-`isPresent()` anti-pattern.
It makes the exceptional nature of absence visible in the code.
:::

## Conditional Operations

\index{Optional!ifPresent@\texttt{ifPresent()}}
\index{Optional!ifPresentOrElse@\texttt{ifPresentOrElse()}}

### `ifPresent`

`void ifPresent(Consumer<? super T> action)` runs the consumer only when the `Optional` is present; does nothing when empty.

```java
Optional<String> song = Optional.of("Semi-Charmed Life");
song.ifPresent(t -> System.out.println("Found: " + t));   // Found: Semi-Charmed Life

Optional<String> empty = Optional.empty();
empty.ifPresent(t -> System.out.println("Found: " + t));  // prints nothing
```

This replaces the common pattern `if (value != null) { use(value); }`.

### `ifPresentOrElse`

`void ifPresentOrElse(Consumer<? super T> action, Runnable emptyAction)` (Java 9+) runs the consumer when present, or the `Runnable` when empty.

```java
Optional<String> song = findByTitle("Semi-Charmed Life");
song.ifPresentOrElse(
    t -> System.out.println("Playing: " + t),
    ()  -> System.out.println("Not in library")
);
```

This cleanly handles both branches without a variable, an `if`, or a null check.

## Transforming Optionals

\index{Optional!map@\texttt{map()}}
\index{Optional!flatMap@\texttt{flatMap()}}
\index{Optional!filter@\texttt{filter()}}
\index{Optional!stream@\texttt{stream()}}

The real power of `Optional` comes from treating it like a one-element stream.
You can chain transformations without ever unwrapping the value, and the empty case propagates automatically.

### `map`

`<U> Optional<U> map(Function<? super T, ? extends U> mapper)` applies the function to the value if present and wraps the result in an `Optional`.
If the `Optional` is empty, or if the mapper returns `null`, the result is an empty `Optional`.

```java
Optional<String> song  = Optional.of("Semi-Charmed Life");
Optional<Integer> len  = song.map(String::length);    // Optional[16]
Optional<String>  upper = song.map(String::toUpperCase); // Optional[SEMI-CHARMED LIFE]

Optional<String> empty   = Optional.empty();
Optional<Integer> noLen  = empty.map(String::length); // Optional.empty
```

Compare to C++: `std::optional<T>` has `transform` (C++23) for the same operation --- `map` is the Java name for it.

### `flatMap`

`<U> Optional<U> flatMap(Function<? super T, ? extends Optional<? extends U>> mapper)` is like `map`, but the mapper itself returns an `Optional`.
Without `flatMap` you would get `Optional<Optional<U>>`; `flatMap` flattens the nesting.

```java
// imagine a Song record with an Optional<String> remix field
record Song(String title, Optional<String> remix) {}

Optional<Song> song = Optional.of(new Song("Semi-Charmed Life", Optional.of("Radio Edit")));

// map would give Optional<Optional<String>> -- not what you want
Optional<Optional<String>> nested = song.map(Song::remix);

// flatMap gives Optional<String> -- correct
Optional<String> remix = song.flatMap(Song::remix);
remix.ifPresent(r -> System.out.println("Remix: " + r));   // Remix: Radio Edit
```

::: {.tip}
**Tip:** The relationship between `map` and `flatMap` here is the same as in the Stream API (Chapter 14).
If the mapping function already returns an `Optional`, use `flatMap`; otherwise use `map`.
:::

### `filter`

`Optional<T> filter(Predicate<? super T> predicate)` returns the `Optional` unchanged if the value is present and the predicate returns `true`; otherwise returns an empty `Optional`.

```java
Optional<String> song = Optional.of("Semi-Charmed Life");

Optional<String> long1  = song.filter(t -> t.length() > 10);   // Optional[Semi-Charmed Life]
Optional<String> short1 = song.filter(t -> t.length() < 5);    // Optional.empty
```

This lets you chain conditions without unwrapping:

```java
Optional<String> result = findByTitle("Semi-Charmed Life")
    .filter(t -> !t.isBlank())
    .map(String::toUpperCase);
```

### `stream`

`Stream<T> stream()` (Java 9+) converts the `Optional` into a zero-or-one-element stream.
Its main value is when you have a collection of `Optional`s and want to flat-map them into a stream of present values.

```java
List<Optional<String>> maybes = List.of(
    Optional.of("Semi-Charmed Life"),
    Optional.empty(),
    Optional.of("Jumper")
);

List<String> present = maybes.stream()
    .flatMap(Optional::stream)   // each Optional becomes a 0-or-1-element stream
    .toList();

System.out.println(present);   // [Semi-Charmed Life, Jumper]
```

Without `Optional::stream` you would need `filter(Optional::isPresent).map(Optional::get)` --- correct but noisier.

## When to Use Optional

\index{Optional!when to use}

`Optional` is a deliberately narrow tool.
Used in the right places it eliminates a class of bugs; used everywhere it adds noise without benefit.

### Use Optional as a Return Type

\index{Optional!return type}

`Optional` shines when a method genuinely may have no result to return.

```java
// repository lookup -- might not find a row
public Optional<Song> findByTitle(String title) { ... }

// stream terminal ops -- stream might be empty
Optional<Song> first = songs.stream().filter(...).findFirst();
Optional<Song> max   = songs.stream().max(Comparator.comparingInt(Song::year));

// parsing that might fail
public Optional<Integer> parseYear(String s) {
    try {
        return Optional.of(Integer.parseInt(s));
    } catch (NumberFormatException e) {
        return Optional.empty();
    }
}
```

### Do Not Use Optional as a Method Parameter

\index{Optional!method parameters}

Passing an `Optional` as a parameter forces every caller to wrap a value in `Optional.of(...)`, which is ugly and provides no benefit over a regular nullable parameter or method overloading.

```java
// bad: forces callers to write Optional.of("Semi-Charmed Life")
public void play(Optional<String> title) { ... }

// good: two overloads with clear intent
public void play(String title) { ... }
public void playDefault() { ... }
```

::: {.tip}
**Trap:** `Optional` as a method parameter is widely considered a code smell.
The official Java API design FAQ recommends against it.
Use overloading, a `@Nullable` annotation, or a clearly documented nullable parameter instead.
:::

### Do Not Use Optional as a Class Field

\index{Optional!class fields}

`Optional` does not implement `Serializable`, so an `Optional` field breaks Java serialization.
It also adds heap allocation overhead and signals a design that should probably use a simpler null-with-documentation approach, or be redesigned to avoid optional state altogether.

```java
// bad: serialization breaks, overhead, awkward API
public class Song {
    private Optional<String> remix;   // do not do this
}

// good: document the nullable contract
public class Song {
    /** May be null if no remix exists. */
    private String remix;
}
```

### Do Not Put Optional in Collections

\index{Optional!in collections}

`List<Optional<T>>` is almost always a mistake.
If absence means "not in the list," use `List<T>` and simply omit absent elements.
`Map<K, Optional<V>>` is similarly suspicious --- use a map with no entry for absent keys.

```java
// bad: what does an empty Optional in a list even mean?
List<Optional<String>> titles;

// good: absent means not present in the collection
List<String> titles;
```

### Do Not Use Optional Instead of Proper Error Handling

When the absent case carries information --- a reason, an error code, a message --- an empty `Optional` discards that information.
Consider throwing a checked exception (see Chapter 12), or using a purpose-built Result type if your project supports one.

```java
// bad: caller cannot tell *why* the lookup failed
Optional<Song> result = repo.findByTitle("Semi-Charmed Life");

// better when failure details matter: throw or use a Result type
Song result = repo.findByTitle("Semi-Charmed Life");   // throws SongNotFoundException
```

## Common Anti-Patterns

\index{Optional!anti-patterns}

### Anti-pattern 1: `isPresent` + `get`

The most common misuse of `Optional` is replicating the null-check pattern:

```java
// bad: this is just null-checking with extra steps
if (song.isPresent()) {
    return song.get();
} else {
    return defaultSong();
}

// good: say what you mean
return song.orElseGet(this::defaultSong);
```

Every `isPresent()` / `get()` pair in your code is a sign that you should reach for `orElse`, `orElseGet`, `orElseThrow`, `map`, or `ifPresent` instead.

### Anti-pattern 2: `get` without checking

```java
// bad: NoSuchElementException at runtime if empty
String title = repo.findByTitle("Semi-Charmed Life").get();
```

If you are certain the value is present, explain why in a comment and use `orElseThrow()` to make the exceptional case explicit.

### Anti-pattern 3: Optional method parameter

```java
// bad: ugly at every call site
public void addToPlaylist(Optional<String> title) {
    title.ifPresent(playlist::add);
}

// caller is forced to write:
addToPlaylist(Optional.of("Semi-Charmed Life"));
addToPlaylist(Optional.empty());

// good: two clear methods
public void addToPlaylist(String title) { playlist.add(title); }
public void skipAdd() { /* no-op */ }
```

### Anti-pattern 4: Optional field in a class

```java
// bad: not Serializable, heap overhead, awkward to work with
public class Playlist {
    private Optional<Song> currentSong = Optional.empty();   // do not do this

    public void setCurrent(Optional<Song> s) { currentSong = s; }
}

// good: null with clear ownership
public class Playlist {
    /** Null when nothing is playing. */
    private Song currentSong;

    public void setCurrent(Song s) { currentSong = s; }      // null to clear
    public Optional<Song> getCurrent() {                      // Optional on the getter is fine
        return Optional.ofNullable(currentSong);
    }
}
```

Note the last example: a getter that wraps a nullable field in `Optional.ofNullable` before returning it is a perfectly reasonable pattern.
The field stays null internally, but the public API is explicit.

## A Complete Example

```java
import java.util.*;
import java.util.stream.*;

public class OptionalDemo {
    record Song(String title, String artist, int year, String remix) {
        /** Returns the remix title, or empty if there is no remix. */
        Optional<String> remixTitle() {
            return Optional.ofNullable(remix);
        }
    }

    static Optional<Song> findByTitle(List<Song> lib, String title) {
        return lib.stream()
            .filter(s -> s.title().equalsIgnoreCase(title))
            .findFirst();
    }

    public static void main(String[] args) {
        List<Song> library = List.of(
            new Song("Semi-Charmed Life", "Third Eye Blind", 1997, "Radio Edit"),
            new Song("Jumper",            "Third Eye Blind", 1998, null),
            new Song("Narcolepsy",        "Third Eye Blind", 1997, null)
        );

        // orElse: provide a default title
        String title = findByTitle(library, "Jumper")
            .map(Song::title)
            .orElse("Not found");
        System.out.println(title);                    // Jumper

        // flatMap: unwrap Optional inside Optional
        String remix = findByTitle(library, "Semi-Charmed Life")
            .flatMap(Song::remixTitle)
            .orElse("(no remix)");
        System.out.println(remix);                    // Radio Edit

        // filter + map chained
        findByTitle(library, "Narcolepsy")
            .filter(s -> s.year() == 1997)
            .map(Song::artist)
            .ifPresent(a -> System.out.println("1997 artist: " + a));
        // 1997 artist: Third Eye Blind

        // flatMap over a list of Optionals using stream()
        List<String> remixes = library.stream()
            .map(Song::remixTitle)   // Stream<Optional<String>>
            .flatMap(Optional::stream)
            .toList();
        System.out.println(remixes);                  // [Radio Edit]

        // orElseThrow: treat absence as a bug
        Song s = findByTitle(library, "Semi-Charmed Life")
            .orElseThrow(() -> new NoSuchElementException("Semi-Charmed Life not found"));
        System.out.println(s.year());                 // 1997
    }
}
```

## Key Points

- `Optional<T>` is a container that is either present (holds a non-null value) or empty; it makes "might be absent" explicit in the return type.
- Create `Optional`s with `Optional.of(value)` (non-null required), `Optional.ofNullable(value)` (null becomes empty), or `Optional.empty()`.
- `orElse(default)` always evaluates the default; use `orElseGet(supplier)` when the default is expensive to compute.
- `orElseThrow()` throws `NoSuchElementException`; `orElseThrow(supplier)` throws a custom exception --- prefer these over `isPresent()` + `get()`.
- `ifPresent(consumer)` and `ifPresentOrElse(consumer, runnable)` replace null-check `if` blocks.
- `map`, `flatMap`, and `filter` let you chain transformations without unwrapping; empty propagates automatically.
- Use `flatMap` when the mapping function itself returns an `Optional`, to avoid `Optional<Optional<T>>`.
- `Optional::stream` (Java 9+) converts a list of `Optional`s to a flat stream of present values via `flatMap(Optional::stream)`.
- **Use** `Optional` as a return type for methods that may genuinely have no result.
- **Do not use** `Optional` as a method parameter, class field, or inside a collection.

## Exercises

1. **Think about it:** `Optional` is a reference type in Java, so `Optional<Integer>` involves two heap allocations: one for the `Optional` wrapper and one for the boxed `Integer`.
   `std::optional<int>` in C++ is a stack-allocated value type with zero extra heap overhead.
   Given this difference, why does Java restrict `Optional` to return types, and what would be the practical cost of using `Optional<Integer>` as a field in a class with millions of instances?

2. **What does this print?**

    ```java
    import java.util.*;

    public class Q2 {
        public static void main(String[] args) {
            Optional<String> a = Optional.of("Semi-Charmed Life");
            Optional<String> b = Optional.empty();

            System.out.println(a.map(String::length).orElse(-1));
            System.out.println(b.map(String::length).orElse(-1));
            System.out.println(a.filter(s -> s.startsWith("Z")).orElse("nope"));
            System.out.println(b.orElseGet(() -> "default"));
        }
    }
    ```

3. **Calculation:** Given:

    ```java
    List<Optional<String>> opts = List.of(
        Optional.of("A"),
        Optional.empty(),
        Optional.of("B"),
        Optional.empty(),
        Optional.of("C")
    );

    long count = opts.stream()
        .flatMap(Optional::stream)
        .count();
    ```

    How many elements are in `opts`?
    How many empty `Optional`s are in the list?
    What does `count` print, and why?

4. **Where is the bug?**

    ```java
    import java.util.*;

    public class Q4 {
        static Optional<String> lookup(String key) {
            Map<String, String> map = Map.of("song", "Semi-Charmed Life");
            return Optional.ofNullable(map.get(key));
        }

        public static void main(String[] args) {
            String result = lookup("song").get();
            System.out.println(result);

            String missing = lookup("artist").get();   // line A
            System.out.println(missing);
        }
    }
    ```

    What happens at line A, and how would you fix it?

5. **Write a program:** Write a class `SongLibrary` that stores a `List<Song>`, where `Song` is a record with `String title`, `String artist`, and `Optional<Integer> trackNumber` (some songs have no track number).
   Implement the following methods using `Optional` and the Stream API (no null checks, no `isPresent`/`get` pairs):
   - `Optional<Song> findByArtist(String artist)` --- return the first matching song, or empty.
   - `String titleOrDefault(String artist, String defaultTitle)` --- return the title of the first song by the artist, or `defaultTitle` if none found.
   - `List<Integer> allTrackNumbers()` --- return a list of all track numbers that are present, in encounter order.
   Test your implementation with at least five songs from at least two artists, including some with and some without track numbers.
