# Concurrency Fundamentals

You already know the pain of shared mutable state.
`std::thread`, `std::mutex`, `std::atomic`, `std::condition_variable` --- you have wrestled with all of them.
Java's concurrency model grew from the same POSIX-threads roots, so a lot of the concepts map directly.
The vocabulary is different, the syntax is different, and --- critically --- Java has a formal memory model that C++ only got in C++11.
Once you see where the concepts align and where they diverge, Java concurrency will feel familiar.

This chapter covers `Thread`, `Runnable`, the `synchronized` keyword, `volatile`, the Java Memory Model, deadlock, race conditions, and the low-level `wait`/`notify` mechanism.
Chapter 19 covers `java.util.concurrent`, which is where you will spend most of your time in practice.

## `Thread` and `Runnable`

\index{Thread}
\index{Runnable}

The most direct equivalent of `std::thread` is `java.lang.Thread`.
You give it something to run and call `start()`.

The runnable unit of work is expressed as a `Runnable`:

```java
@FunctionalInterface
public interface Runnable {
    void run();
}
```

Pass a `Runnable` to the `Thread` constructor, then call `start()`:

```java
Thread t = new Thread(() -> {
    System.out.println("It's been one week");  // Barenaked Ladies, 1998
});
t.start();          // spawn the OS thread and return immediately
t.join();           // wait for t to finish, like std::thread::join()
```

`Thread.start()`\index{Thread!start} hands control to the JVM, which creates an OS thread and calls `run()` on your `Runnable`.
Calling `run()` directly --- instead of `start()` --- just executes the code on the calling thread.
That is the Java equivalent of accidentally calling a function pointer instead of passing it to a thread.

`Thread.join()`\index{Thread!join} blocks the calling thread until the target thread exits, exactly like `std::thread::join()`.
The overload `void join(long millis)` adds a timeout in milliseconds.

### Sleeping

\index{Thread!sleep}

```java
static void sleep(long millis) throws InterruptedException
```

`Thread.sleep(millis)` suspends the calling thread for at least the given number of milliseconds.
It throws `InterruptedException` if another thread calls `interrupt()` on the sleeping thread --- handle or declare it.

```java
try {
    Thread.sleep(500);   // sleep 500 ms
} catch (InterruptedException e) {
    Thread.currentThread().interrupt(); // restore interrupt status
}
```

::: {.tip}
**Tip:** When you catch `InterruptedException`, call `Thread.currentThread().interrupt()` to restore the interrupt flag before returning.
Swallowing the exception silently breaks cancellation for callers higher up the call stack.
:::

### Extending `Thread`

\index{Thread!subclassing}

You can also subclass `Thread` directly and override `run()`:

```java
class Worker extends Thread {
    @Override
    public void run() {
        System.out.println("I got it from Alanis");
    }
}

new Worker().start();
```

This style is less preferred because it tightly couples the work to the thread mechanism.
Passing a `Runnable` --- or a `Callable` (Chapter 19) --- keeps the task decoupled from the threading infrastructure.

### Thread Naming and Daemon Threads

\index{Thread!name}
\index{Thread!daemon}

Every thread has a name (`Thread-0`, `Thread-1`, ...) and a daemon flag.
Daemon threads do not prevent the JVM from shutting down --- when all non-daemon threads finish, the JVM exits even if daemon threads are still running.

```java
Thread t = new Thread(() -> System.out.println("background"), "my-worker");
t.setDaemon(true);
t.start();
```

::: {.tip}
**Wut:** In C++, detached threads continue running after `main` exits only until the process dies --- which is immediate.
Java's daemon flag is the idiomatic way to express the same intent, and the JVM handles it cleanly.
:::

## `synchronized`

\index{synchronized}

Every Java object has an intrinsic **monitor lock** (also called an intrinsic lock or mutex).
The `synchronized` keyword acquires that lock.
This is Java's built-in alternative to `std::mutex` + `std::lock_guard`.

### Synchronized Methods

\index{synchronized!method}

```java
public class Counter {
    private int value = 0;

    public synchronized void increment() {   // locks `this`
        value++;
    }

    public synchronized int get() {          // locks `this`
        return value;
    }
}
```

When a method is marked `synchronized`, the JVM acquires `this`'s monitor on entry and releases it on exit --- whether the method returns normally or throws an exception.
There is no RAII object like `std::lock_guard`, but the exception-safety guarantee is equivalent.

For a `static synchronized` method, the lock is on the `Class` object, not `this`.

### Synchronized Blocks

\index{synchronized!block}

You can lock any object reference, not just `this`:

```java
public class PlaylistManager {
    private final List<String> tracks = new ArrayList<>();
    private final Object lock = new Object();

    public void add(String track) {
        synchronized (lock) {        // acquire lock on `lock` object
            tracks.add(track);
        }                            // released here, even on exception
    }
}
```

The C++ equivalent is:

```cpp
std::mutex mtx;
std::lock_guard<std::mutex> guard(mtx);  // RAII unlock on scope exit
tracks.push_back(track);
```

The key semantic difference: Java's `synchronized` block is always released on block exit; C++'s `lock_guard` is released on destructor call.
In practice they behave identically for linear control flow.

### Reentrancy

\index{synchronized!reentrant}
\index{reentrant lock}

Java's intrinsic lock is **reentrant**: if a thread already holds a lock, it can re-acquire it without deadlocking.
This mirrors `std::recursive_mutex` in C++, except that Java's intrinsic lock is always reentrant --- there is no non-reentrant variant.

```java
public synchronized void outer() {
    inner();       // same thread re-acquires the same lock --- ok
}

public synchronized void inner() {
    System.out.println("Ironic");  // Alanis Morissette, 1995
}
```

::: {.tip}
**Wut:** C++'s `std::mutex` is NOT reentrant.
Calling a `std::mutex`-locked function from another locked function on the same thread is undefined behavior (usually a deadlock).
Java's intrinsic locks are always reentrant, which makes it safe to call `synchronized` methods from other `synchronized` methods on the same object.
:::

## `volatile`

\index{volatile}

Java's `volatile` keyword looks like C++'s `volatile`, but it means something stronger.

In C++, `volatile` prevents the compiler from optimizing away reads and writes (useful for memory-mapped hardware registers), but it provides **no memory ordering guarantees** between threads.
You need `std::atomic` for thread-safe visibility.

In Java, a `volatile` field provides two guarantees:

1. **Visibility:** a write to a `volatile` variable is immediately visible to all other threads.
2. **Ordering:** reads and writes to `volatile` variables are not reordered with respect to each other.

This makes `volatile` suitable for simple single-variable flags:

```java
public class Stopper {
    private volatile boolean stop = false;

    public void requestStop() {
        stop = true;         // visible to all threads immediately
    }

    public void run() {
        while (!stop) {      // always reads the current value
            // ... do work
        }
    }
}
```

Without `volatile`, the JVM (or the CPU) could cache `stop` in a register and the reading thread might never see the updated value.

::: {.tip}
**Trap:** `volatile` is not sufficient for compound check-then-act operations.
`count++` is three operations (read, increment, write) even on a `volatile int`.
Two threads can both read `0`, both increment to `1`, and both write `1` --- your counter now shows `1` instead of `2`.
Use `AtomicInteger` or `synchronized` for that case (see Chapter 19).
:::

::: {.tip}
**Wut:** C++ `volatile` and Java `volatile` share a keyword but barely share a meaning.
C++ `volatile` does not prevent data races.
Java `volatile` does prevent data races on that specific variable --- it is closer to `std::atomic<T>` with `memory_order_seq_cst` load/store than to C++ `volatile`.
:::

## The Java Memory Model

\index{Java Memory Model}
\index{happens-before}

C++ got a formal memory model in C++11.
Java has had one since Java 5 (JSR-133).
The core concept in both is **happens-before (HB)**: if action A happens-before action B, then B is guaranteed to see all effects of A.

The key happens-before relationships in Java:

| Action A | Action B | Guarantee |
|:---|:---|:---|
| Unlock monitor M | Lock monitor M | B sees all writes before A's unlock |
| Write to `volatile` field | Read of same `volatile` field | Read sees the write |
| `thread.start()` | First action in the thread | Thread sees all writes before `start()` |
| Last action in a thread | `thread.join()` returns | Caller sees all writes by the thread |
| Static initializer | Any use of the class | Static init is visible everywhere |

Without a happens-before relationship, you have a **data race**\index{data race}, and the JVM is free to do whatever it wants --- just like C++ undefined behavior.

```java
// BAD: no happens-before between the write and the read
int sharedValue = 0;

Thread writer = new Thread(() -> sharedValue = 42);
Thread reader = new Thread(() -> System.out.println(sharedValue)); // may print 0 or 42

writer.start();
reader.start();
writer.join();
reader.join();
```

Adding `volatile` or `synchronized` around `sharedValue` establishes the required happens-before.

## Race Conditions and Visibility

\index{race condition}
\index{visibility}

A **race condition** occurs when the program outcome depends on the relative timing of operations in different threads.
The canonical example is two threads incrementing a shared counter:

```java
public class RaceDemo {
    static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable inc = () -> {
            for (int i = 0; i < 100_000; i++) {
                count++;     // read-modify-write: NOT atomic
            }
        };

        Thread t1 = new Thread(inc);
        Thread t2 = new Thread(inc);
        t1.start();
        t2.start();
        t1.join();
        t2.join();

        System.out.println(count); // probably NOT 200000
    }
}
```

`count++` compiles to three bytecodes: load, add, store.
Two threads can interleave those three steps and both write back the same result, losing increments.
This is identical to the C++ race on a non-atomic `int`.

Fix it with `synchronized`:

```java
static synchronized void increment() { count++; }
```

Or with `AtomicInteger` (covered in Chapter 19), which is faster for this specific pattern.

### Visibility Without Synchronization

\index{visibility!stale read}

Even if you avoid torn writes, you can still have **visibility** bugs.
A thread may read a stale cached value from its local CPU cache if there is no synchronization establishing a happens-before relationship.

The `volatile` fix for the flag example in the previous section is the classic solution.

## Deadlock

\index{deadlock}

Deadlock in Java looks exactly like deadlock in C++: two threads each hold a lock the other needs.

```java
public class DeadlockDemo {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lockA) {
                System.out.println("t1 holds A, wants B");
                synchronized (lockB) {               // waits for t2
                    System.out.println("t1 holds both");
                }
            }
        });

        Thread t2 = new Thread(() -> {
            synchronized (lockB) {
                System.out.println("t2 holds B, wants A");
                synchronized (lockA) {               // waits for t1
                    System.out.println("t2 holds both");
                }
            }
        });

        t1.start();
        t2.start();
    }
}
```

Both threads are now waiting forever.
The JVM does not detect and recover from deadlocks --- you can observe them with `jstack` (Chapter 24), but the program will not exit on its own.

### Prevention Strategies

\index{deadlock!prevention}

The standard prevention strategies are the same as in C++:

- **Consistent lock ordering:** always acquire `lockA` before `lockB`, everywhere.
Never acquire them in the other order.
This is the simplest and most effective strategy.
- **`tryLock` with timeout:** `ReentrantLock.tryLock(long timeout, TimeUnit unit)` (covered in Chapter 19) lets you attempt a lock and back off if it is unavailable, breaking potential deadlocks.
- **Lock fewer things:** the less code runs under a lock, the fewer opportunities for circular waits.

::: {.tip}
**Tip:** Detect deadlocks in production with `jstack <pid>` or `jcmd <pid> Thread.print`.
Both tools dump all thread stacks and clearly label threads that are "waiting to lock" an object already held by another thread.
:::

## `wait()`, `notify()`, and `notifyAll()`

\index{wait}
\index{notify}
\index{notifyAll}

These three methods are the low-level producer-consumer mechanism built into every Java object.
They are the equivalent of `std::condition_variable` in C++.

The signatures, inherited from `java.lang.Object`:

```java
void wait() throws InterruptedException
void wait(long timeoutMillis) throws InterruptedException
void notify()
void notifyAll()
```

All three must be called from within a `synchronized` block on the same object.
Calling them without holding the monitor throws `IllegalMonitorStateException`.

```java
public class SimpleQueue<T> {
    private T item = null;
    private final Object monitor = new Object();

    public void produce(T value) throws InterruptedException {
        synchronized (monitor) {
            while (item != null) {          // wait until slot is empty
                monitor.wait();             // releases lock; re-acquires on wake
            }
            item = value;
            monitor.notifyAll();            // wake waiting consumers
        }
    }

    public T consume() throws InterruptedException {
        synchronized (monitor) {
            while (item == null) {          // wait until item available
                monitor.wait();
            }
            T result = item;
            item = null;
            monitor.notifyAll();            // wake waiting producers
            return result;
        }
    }
}
```

The C++ equivalent uses `std::unique_lock` + `std::condition_variable::wait(lock, predicate)`.

::: {.tip}
**Trap:** Always re-check the condition in a `while` loop after `wait()` returns, never in an `if`.
`wait()` can return spuriously (without a corresponding `notify()`) --- just like `std::condition_variable::wait()` in C++.
The `while` loop re-checks the condition and goes back to sleep if it is still false.
:::

::: {.tip}
**Tip:** Prefer `notifyAll()` over `notify()` unless you have a specific, well-understood reason to use the single-wake version.
`notify()` wakes exactly one waiting thread (chosen arbitrarily by the JVM).
If the wrong thread wakes up and cannot make progress, the others stay asleep.
`notifyAll()` wakes all waiters and lets them compete, which is safer.
:::

::: {.tip}
**Tip:** In practice, prefer `java.util.concurrent` constructs (Chapter 19) over raw `wait`/`notify`.
`BlockingQueue`, `CountDownLatch`, `Semaphore`, and `CompletableFuture` cover virtually every producer-consumer and synchronization pattern without the boilerplate and the sharp edges.
:::

## Key Points

- `Thread` takes a `Runnable`; call `start()` to spawn the OS thread and `join()` to wait for it.
- `synchronized` on a method locks `this`; on a block it locks the specified object.
Every Java object has an intrinsic monitor lock; it is always reentrant.
- The `synchronized` block releases the lock on exit even if an exception is thrown --- equivalent to C++ RAII.
- Java `volatile` provides both visibility and ordering guarantees for that single variable.
This is stronger than C++ `volatile`, which provides neither.
- The Java Memory Model defines **happens-before**: without it, reads may observe stale values.
Key HB edges: unlock/lock a monitor; write/read a volatile; `start()`/thread body; thread body/`join()`.
- `count++` on a non-`volatile` `int` is not atomic --- it is three operations and can be interleaved.
Use `synchronized` or `AtomicInteger`.
- Deadlock requires circular lock acquisition; prevent it with consistent lock ordering.
- `wait()`, `notify()`, and `notifyAll()` are the low-level condition-variable mechanism; always call them inside a `synchronized` block and re-check the condition in a `while` loop.
- Prefer `java.util.concurrent` over raw `wait`/`notify` for new code.

## Exercises

1. **Think about it:** Java's intrinsic lock is always reentrant, while C++'s `std::mutex` is not.
What design advantage does reentrancy give you when writing class hierarchies where subclasses call `super` methods?
What risk does it introduce?

2. **What does this print?**

    ```java
    public class Q2 {
        private static volatile int x = 0;
        private static volatile int y = 0;

        public static void main(String[] args) throws InterruptedException {
            Thread w = new Thread(() -> { x = 1; y = 2; });
            w.start();
            w.join();
            System.out.println(x + " " + y);
        }
    }
    ```

3. **Calculation:** A `synchronized` method acquires the intrinsic lock on entry and releases it on exit.
If thread A is executing a `synchronized` method on object `obj` and thread B calls a *different* `synchronized` method on the same `obj`, how many threads can be executing `synchronized` methods on `obj` at the same time?
What if one of those methods is `static synchronized`?

4. **Where is the bug?**

    ```java
    public class BuggyFlag {
        private boolean done = false;

        public void setDone() { done = true; }

        public void run() {
            while (!done) {
                // ... do work
            }
            System.out.println("Finished");
        }
    }
    ```

    Two threads are used: one calls `setDone()`, the other calls `run()`.
    What can go wrong, and how do you fix it?

5. **Write a program:** Implement a thread-safe bounded buffer of capacity 1 using `wait()` and `notifyAll()`.
The buffer should have a `put(String item)` method and a `String take()` method.
