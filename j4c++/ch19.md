# `java.util.concurrent`

Raw `Thread`, `synchronized`, and `wait`/`notify` are the assembly language of Java concurrency.
They work, but you would not want to build a production service out of them any more than you would build one out of raw pthreads.
`java.util.concurrent` (JUC) --- introduced in Java 5 and continuously extended since --- is the standard library of concurrency primitives: thread pools, composable futures, atomic variables, flexible locks, coordination barriers, and thread-safe collections.
If you use C++ `std::async`, `std::atomic`, or reach for a third-party thread pool, JUC covers all of that and more.

This chapter also covers virtual threads, introduced as a preview in Java 19 and stabilized in Java 21.
Virtual threads fundamentally change the cost model of concurrent Java, and they are the closest thing Java has to Go goroutines or C++ coroutines.

## `ExecutorService` and Thread Pools

\index{ExecutorService}
\index{thread pool}

In C++, the standard library has no built-in thread pool.
You use `std::async` (which may or may not reuse threads depending on the implementation) or a third-party library.
Java provides `ExecutorService`\index{ExecutorService} as the standard interface, with factory methods in `Executors` for common pool configurations.

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
```

The common factory methods:

```java
static ExecutorService Executors.newFixedThreadPool(int nThreads)
static ExecutorService Executors.newCachedThreadPool()
static ExecutorService Executors.newSingleThreadExecutor()
```

- `newFixedThreadPool(n)` --- exactly `n` threads; tasks queue when all are busy.
Good for CPU-bound work where you want to limit parallelism to the number of cores.
- `newCachedThreadPool()` --- creates threads on demand; idle threads are recycled after 60 seconds.
Good for short-lived, bursty I/O-bound tasks.
- `newSingleThreadExecutor()` --- one thread, tasks execute in submission order.
Good for background serialized work.

### Submitting Work

\index{ExecutorService!execute}
\index{ExecutorService!submit}

```java
void ExecutorService.execute(Runnable command)
<T> Future<T> ExecutorService.submit(Callable<T> task)
Future<?> ExecutorService.submit(Runnable task)
```

`execute()` is fire-and-forget: submit a `Runnable`, get nothing back.
`submit()` returns a `Future` that lets you retrieve the result or check for exceptions.

```java
ExecutorService pool = Executors.newFixedThreadPool(2);

// fire-and-forget
pool.execute(() -> System.out.println("Livin' la Vida Loca"));  // Ricky Martin, 1999

// get the result back
Future<Integer> future = pool.submit(() -> {
    return 1 + 1;
});
System.out.println(future.get()); // 2
```

### Shutting Down

\index{ExecutorService!shutdown}
\index{ExecutorService!shutdownNow}

```java
void ExecutorService.shutdown()
List<Runnable> ExecutorService.shutdownNow()
boolean ExecutorService.awaitTermination(long timeout, TimeUnit unit) throws InterruptedException
```

`shutdown()` stops accepting new tasks but lets submitted tasks finish --- graceful shutdown.
`shutdownNow()` interrupts running tasks and returns a list of tasks that never started.

```java
pool.shutdown();
if (!pool.awaitTermination(10, TimeUnit.SECONDS)) {
    pool.shutdownNow();
}
```

::: {.tip}
**Trap:** Forgetting to shut down an `ExecutorService` leaks threads.
The JVM will not exit while non-daemon pool threads are still alive.
Always shut down your pools --- ideally with try-with-resources using `ExecutorService.close()` (Java 19+), which calls `shutdown()` and waits.
:::

## `Future<V>` and `Callable<V>`

\index{Future}
\index{Callable}

`Callable<V>` is `Runnable` with a return value and the ability to throw checked exceptions:

```java
@FunctionalInterface
public interface Callable<V> {
    V call() throws Exception;
}
```

`Future<V>` is a handle to the eventual result of an asynchronous computation --- the equivalent of C++ `std::future<T>`:

```java
V Future.get() throws InterruptedException, ExecutionException
V Future.get(long timeout, TimeUnit unit) throws InterruptedException, ExecutionException, TimeoutException
boolean Future.isDone()
boolean Future.cancel(boolean mayInterruptIfRunning)
boolean Future.isCancelled()
```

`get()` blocks until the result is available.
If the `Callable` threw an exception, `get()` wraps it in an `ExecutionException`; call `getCause()` to unwrap it.

```java
ExecutorService pool = Executors.newFixedThreadPool(2);

Future<String> result = pool.submit(() -> {
    Thread.sleep(100);
    return "I'll Be There for You";   // The Rembrandts, 1995
});

// do other work while the task runs...

String song = result.get();           // blocks here until done
System.out.println(song);
pool.shutdown();
```

::: {.tip}
**Wut:** `ExecutionException` wraps checked exceptions from your `Callable`.
If your callable throws `IOException`, `result.get()` throws `ExecutionException`, not `IOException`.
You must call `e.getCause()` and cast it.
This differs from C++ `std::future`, which rethrows the original exception type.
:::

## `CompletableFuture<T>`

\index{CompletableFuture}

`Future<V>` has a serious limitation: it can only block.
You cannot attach a callback that runs when the result is ready --- you must poll `isDone()` or block on `get()`.
`CompletableFuture<T>` (Java 8+) is Java's answer: a non-blocking, composable future.

The closest C++ analogs are `std::experimental::future` chaining (not yet standardized) or callback-based async frameworks like Boost.Asio.

### Starting an Async Computation

\index{CompletableFuture!supplyAsync}
\index{CompletableFuture!runAsync}

```java
static <T> CompletableFuture<T> CompletableFuture.supplyAsync(Supplier<T> supplier)
static <T> CompletableFuture<T> CompletableFuture.supplyAsync(Supplier<T> supplier, Executor executor)
static CompletableFuture<Void> CompletableFuture.runAsync(Runnable runnable)
```

`supplyAsync` runs the `Supplier` on the common ForkJoinPool (or a provided `Executor`) and returns a `CompletableFuture<T>`:

```java
CompletableFuture<String> cf =
    CompletableFuture.supplyAsync(() -> "Barbie Girl");  // Aqua, 1997
```

### Transforming Results

\index{CompletableFuture!thenApply}
\index{CompletableFuture!thenAccept}
\index{CompletableFuture!thenRun}

```java
<U> CompletableFuture<U> thenApply(Function<? super T, ? extends U> fn)
CompletableFuture<Void> thenAccept(Consumer<? super T> action)
CompletableFuture<Void> thenRun(Runnable action)
```

These run on the same thread that completed the upstream stage (usually a pool thread).

```java
CompletableFuture<Integer> length =
    CompletableFuture.supplyAsync(() -> "Barbie Girl")
                     .thenApply(String::length);          // 10

length.thenAccept(n -> System.out.println("Length: " + n));
```

Use `thenApplyAsync`, `thenAcceptAsync`, or `thenRunAsync` if you want the continuation to run on a pool thread rather than the completing thread.

### Chaining Async Operations

\index{CompletableFuture!thenCompose}

```java
<U> CompletableFuture<U> thenCompose(Function<? super T, ? extends CompletionStage<U>> fn)
```

`thenCompose` is flatMap for futures --- it chains one async operation after another without nesting `CompletableFuture<CompletableFuture<T>>`:

```java
CompletableFuture<String> result =
    CompletableFuture.supplyAsync(() -> "Livin'")
                     .thenCompose(s -> CompletableFuture.supplyAsync(() -> s + " la Vida Loca"));

System.out.println(result.get()); // Livin' la Vida Loca
```

### Combining Two Futures

\index{CompletableFuture!thenCombine}

```java
<U, V> CompletableFuture<V> thenCombine(CompletionStage<? extends U> other,
                                         BiFunction<? super T, ? super U, ? extends V> fn)
```

`thenCombine` waits for both futures and combines their results:

```java
CompletableFuture<String> artist = CompletableFuture.supplyAsync(() -> "Aqua");
CompletableFuture<String> song   = CompletableFuture.supplyAsync(() -> "Barbie Girl");

CompletableFuture<String> both =
    artist.thenCombine(song, (a, s) -> a + " - " + s);

System.out.println(both.get()); // Aqua - Barbie Girl
```

### Error Handling

\index{CompletableFuture!exceptionally}
\index{CompletableFuture!handle}

```java
CompletableFuture<T> exceptionally(Function<Throwable, ? extends T> fn)
<U> CompletableFuture<U> handle(BiFunction<? super T, Throwable, ? extends U> fn)
```

`exceptionally` is like a catch block --- it runs only if the upstream stage completed with an exception, and returns a fallback value.
`handle` always runs and receives both the result (possibly null) and the exception (possibly null):

```java
CompletableFuture<String> safe =
    CompletableFuture.supplyAsync(() -> { throw new RuntimeException("oops"); })
                     .exceptionally(ex -> "Waterfalls");  // TLC, 1994
```

### Waiting for All or Any

\index{CompletableFuture!allOf}
\index{CompletableFuture!anyOf}

```java
static CompletableFuture<Void> CompletableFuture.allOf(CompletableFuture<?>... cfs)
static CompletableFuture<Object> CompletableFuture.anyOf(CompletableFuture<?>... cfs)
```

`allOf` completes when all futures complete; `anyOf` completes when the first one does.

```java
CompletableFuture<String> f1 = CompletableFuture.supplyAsync(() -> "one");
CompletableFuture<String> f2 = CompletableFuture.supplyAsync(() -> "two");
CompletableFuture<String> f3 = CompletableFuture.supplyAsync(() -> "three");

CompletableFuture.allOf(f1, f2, f3).join(); // wait for all (join() = get() without checked exception)
System.out.println(f1.get() + ", " + f2.get() + ", " + f3.get());
```

## Atomic Variables

\index{atomic variables}
\index{AtomicInteger}
\index{AtomicLong}
\index{AtomicBoolean}
\index{AtomicReference}

`java.util.concurrent.atomic` provides lock-free atomic operations on single variables, backed by CPU compare-and-swap (CAS) instructions --- the same hardware primitive behind C++'s `std::atomic<T>`.

The main classes are `AtomicInteger`, `AtomicLong`, `AtomicBoolean`, and `AtomicReference<V>`.

Key operations on `AtomicInteger`:

```java
int get()
void set(int newValue)
int getAndIncrement()
int incrementAndGet()
int getAndDecrement()
int decrementAndGet()
int getAndAdd(int delta)
int addAndGet(int delta)
boolean compareAndSet(int expectedValue, int newValue)
```

`compareAndSet(expected, update)` is the CAS operation: atomically sets the value to `update` only if the current value equals `expected`.
Returns `true` on success.
This is identical to C++'s `std::atomic<int>::compare_exchange_strong`.

```java
AtomicInteger counter = new AtomicInteger(0);

Runnable inc = () -> {
    for (int i = 0; i < 100_000; i++) {
        counter.incrementAndGet();   // atomic: no race condition
    }
};

Thread t1 = new Thread(inc);
Thread t2 = new Thread(inc);
t1.start(); t2.start();
t1.join();  t2.join();

System.out.println(counter.get()); // exactly 200000, every time
```

`AtomicReference<V>` applies the same CAS principle to object references:

```java
AtomicReference<String> ref = new AtomicReference<>("Ready to Run");  // Taylor Swift ref --- wait, 1989 = 2014
```

::: {.tip}
**Tip:** Prefer `AtomicInteger`/`AtomicLong` over `synchronized` for simple counters and accumulators.
The lock-free CAS path has lower overhead under contention and avoids the risk of deadlock.
For high-throughput counters, consider `LongAdder` (Java 8+), which reduces contention by striping across multiple cells.
:::

## `Lock` and `ReadWriteLock`

\index{Lock}
\index{ReentrantLock}
\index{ReadWriteLock}
\index{ReentrantReadWriteLock}

`ReentrantLock` is an explicit lock that provides everything `synchronized` does plus more flexibility.
The C++ equivalent is `std::unique_lock<std::mutex>`.

```java
import java.util.concurrent.locks.*;

ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    // critical section
} finally {
    lock.unlock();   // MUST be in finally; no RAII in Java
}
```

::: {.tip}
**Trap:** Always unlock a `ReentrantLock` in a `finally` block.
Unlike `synchronized`, a `ReentrantLock` is not automatically released when an exception is thrown.
If you forget the `finally`, an exception leaves the lock permanently held and every future caller deadlocks.
:::

### `tryLock`

\index{ReentrantLock!tryLock}

```java
boolean ReentrantLock.tryLock()
boolean ReentrantLock.tryLock(long timeout, TimeUnit unit) throws InterruptedException
```

`tryLock()` attempts to acquire the lock without blocking --- it returns immediately with `false` if the lock is held.
`tryLock(timeout, unit)` waits up to the given time.
This is useful for breaking potential deadlocks:

```java
if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
    try {
        // critical section
    } finally {
        lock.unlock();
    }
} else {
    System.out.println("Could not acquire lock, retrying...");
}
```

### `ReentrantReadWriteLock`

\index{ReentrantReadWriteLock}

When reads outnumber writes, a read-write lock increases throughput.
Multiple threads can hold the read lock simultaneously; the write lock is exclusive.
This is equivalent to C++17's `std::shared_mutex`:

```java
ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
Lock readLock  = rwLock.readLock();
Lock writeLock = rwLock.writeLock();

// multiple threads can read concurrently
readLock.lock();
try {
    // read shared state
} finally {
    readLock.unlock();
}

// only one thread writes at a time, and no readers run concurrently
writeLock.lock();
try {
    // write shared state
} finally {
    writeLock.unlock();
}
```

::: {.tip}
**Wut:** `ReentrantReadWriteLock` does NOT allow upgrading from a read lock to a write lock.
If you hold the read lock and call `writeLock.lock()`, you will deadlock --- the write lock waits for all readers (including yourself) to release.
Release the read lock first, then acquire the write lock.
:::

## `CountDownLatch`, `CyclicBarrier`, and `Semaphore`

\index{CountDownLatch}
\index{CyclicBarrier}
\index{Semaphore}

These are the coordination primitives for common threading patterns.

### `CountDownLatch`

\index{CountDownLatch!countDown}
\index{CountDownLatch!await}

A `CountDownLatch(n)` starts at count `n`.
Threads call `countDown()` to decrement; callers of `await()` block until the count reaches zero.
Unlike a `CyclicBarrier`, a latch cannot be reset.

```java
void CountDownLatch.countDown()
void CountDownLatch.await() throws InterruptedException
boolean CountDownLatch.await(long timeout, TimeUnit unit) throws InterruptedException
```

Classic use: wait for N initialization tasks to complete before proceeding.

```java
int workers = 3;
CountDownLatch ready = new CountDownLatch(workers);

for (int i = 0; i < workers; i++) {
    int id = i;
    new Thread(() -> {
        System.out.println("Worker " + id + " ready");
        ready.countDown();
    }).start();
}

ready.await();   // main thread blocks until all 3 workers count down
System.out.println("All workers ready --- starting");
```

### `CyclicBarrier`

\index{CyclicBarrier!await}

A `CyclicBarrier(n)` makes N threads rendezvous --- each calls `await()` and blocks until all N have arrived, then all are released simultaneously.
It can be reused (hence "cyclic").

```java
int await() throws InterruptedException, BrokenBarrierException
```

```java
CyclicBarrier barrier = new CyclicBarrier(3, () -> System.out.println("Round complete"));

for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        System.out.println(Thread.currentThread().getName() + " at barrier");
        barrier.await();   // all three block here until the third arrives
        // then all three continue
    }).start();
}
```

### `Semaphore`

\index{Semaphore!acquire}
\index{Semaphore!release}

A `Semaphore(n)` limits concurrent access to a resource to `n` threads at a time.
Threads call `acquire()` to decrement the permit count (blocking if zero) and `release()` to increment it.

```java
void Semaphore.acquire() throws InterruptedException
boolean Semaphore.tryAcquire()
void Semaphore.release()
```

```java
Semaphore sem = new Semaphore(2);   // at most 2 threads at a time

Runnable task = () -> {
    sem.acquire();
    try {
        // access limited resource
    } finally {
        sem.release();
    }
};
```

## Concurrent Collections

\index{concurrent collections}
\index{ConcurrentHashMap}
\index{CopyOnWriteArrayList}
\index{BlockingQueue}

Thread-safe collections in `java.util.concurrent` are preferred over wrapping standard collections with `Collections.synchronizedXxx()`.

### `ConcurrentHashMap<K,V>`

\index{ConcurrentHashMap}

`ConcurrentHashMap` is a thread-safe hash map with fine-grained internal locking (Java 8+: lock-free reads, CAS-based writes).
It is dramatically faster than `Collections.synchronizedMap(new HashMap<>())` under contention because reads never block.

```java
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
map.put("Barbie Girl", 1997);
map.put("Livin' la Vida Loca", 1999);

// atomic check-then-act
map.putIfAbsent("Barbie Girl", 2000);        // not updated (key exists)
map.computeIfAbsent("Wannabe", k -> 1996);   // Spice Girls, 1996
```

::: {.tip}
**Trap:** `ConcurrentHashMap` makes individual operations atomic, but compound operations are not.
A `get` followed by a `put` is still a race condition.
Use `putIfAbsent`, `computeIfAbsent`, `merge`, or `compute` for atomic compound updates.
:::

### `CopyOnWriteArrayList<E>`

\index{CopyOnWriteArrayList}

Every write (add, remove, set) copies the entire backing array.
Reads never lock.
Suitable for lists that are read far more often than they are written, such as event listener lists.

```java
CopyOnWriteArrayList<String> listeners = new CopyOnWriteArrayList<>();
listeners.add("Waterfalls");   // copies the array once per write
// reads iterate a stable snapshot --- no ConcurrentModificationException
```

### `BlockingQueue<E>`

\index{BlockingQueue}
\index{ArrayBlockingQueue}
\index{LinkedBlockingQueue}

`BlockingQueue` is the standard producer-consumer abstraction.
`put()` blocks if the queue is full; `take()` blocks if the queue is empty.
Common implementations: `ArrayBlockingQueue` (bounded), `LinkedBlockingQueue` (optionally bounded), `SynchronousQueue` (zero capacity, direct handoff).

```java
E BlockingQueue.take() throws InterruptedException
void BlockingQueue.put(E e) throws InterruptedException
boolean BlockingQueue.offer(E e, long timeout, TimeUnit unit) throws InterruptedException
```

```java
BlockingQueue<String> queue = new ArrayBlockingQueue<>(10);

Thread producer = new Thread(() -> {
    queue.put("One Week");    // blocks if queue is full
});

Thread consumer = new Thread(() -> {
    String item = queue.take();            // blocks if queue is empty
    System.out.println("Got: " + item);
});

producer.start();
consumer.start();
producer.join();
consumer.join();
```

## Virtual Threads (Java 21+)

\index{virtual threads}
\index{Thread!virtual}

Platform threads (the threads covered in Chapter 18) are one-to-one with OS threads.
Creating one costs around 1 MB of stack space by default.
On a typical server you can run thousands, not millions, of them.

Virtual threads are JVM-managed threads.
They are cheap --- you can create millions of them.
When a virtual thread blocks (on I/O, `sleep`, `lock`, etc.), the JVM **unmounts** it from its carrier platform thread and parks its stack on the heap.
When the block clears, the JVM **remounts** it onto any available carrier thread.
This is essentially Go goroutines or, more closely, cooperative coroutines --- except from user code they look like ordinary blocking threads.

### Creating Virtual Threads

\index{Thread!ofVirtual}
\index{Executors!newVirtualThreadPerTaskExecutor}

```java
static Thread.Builder Thread.ofVirtual()
static ExecutorService Executors.newVirtualThreadPerTaskExecutor()
```

Using the builder:

```java
Thread vt = Thread.ofVirtual().name("virt-1").start(() -> {
    System.out.println("I'm a virtual thread");
    Thread.sleep(1000);                          // cheap: unmounts, does not block a platform thread
});
vt.join();
```

Using an executor (the preferred pattern for server code):

```java
try (ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        exec.submit(() -> {
            Thread.sleep(100);
            return "done";
        });
    }
}  // close() calls shutdown() and waits
```

Submitting a million tasks here is practical.
With `newFixedThreadPool(4)`, those million tasks would queue up and run four at a time.

### Pinning

\index{virtual threads!pinning}

A virtual thread is **pinned** when it cannot unmount from its carrier thread.
The two main causes:

1. The virtual thread is inside a `synchronized` block or method and performs a blocking operation.
2. The virtual thread calls native code that then blocks.

While pinned, the virtual thread holds the carrier thread hostage --- it behaves like a platform thread and blocks the carrier.
If all carrier threads are pinned, throughput collapses.

The fix: replace `synchronized` with `ReentrantLock` in code that might block while holding the lock.

```java
// BEFORE: synchronized + blocking I/O can pin
synchronized (lock) {
    data = inputStream.read();  // blocks; may pin the carrier thread
}

// AFTER: ReentrantLock + blocking I/O --- virtual thread can unmount
lock.lock();
try {
    data = inputStream.read();  // virtual thread unmounts cleanly
} finally {
    lock.unlock();
}
```

::: {.tip}
**Tip:** Virtual threads are designed for high-concurrency, I/O-bound workloads where you want simple blocking code without the complexity of reactive programming.
They are not faster than platform threads for CPU-bound work --- they are still limited by the number of carrier threads (which defaults to the number of CPU cores).
Use `ForkJoinPool` or a fixed-size pool for CPU-bound parallelism.
:::

::: {.tip}
**Trap:** Do not pool virtual threads.
Thread pools exist to amortize the cost of thread creation --- but virtual threads are so cheap to create that pooling them adds overhead and defeats the purpose.
Use `Executors.newVirtualThreadPerTaskExecutor()` and let the JVM manage them.
:::

::: {.tip}
**Wut:** Virtual threads are still `Thread` objects.
`Thread.currentThread().isVirtual()` returns `true` if you are on a virtual thread.
All the usual `Thread` API --- `sleep`, `join`, `interrupt`, `getName` --- works identically.
Code written against `Thread` does not need to change to benefit from virtual threads --- you just swap the executor.
:::

## Key Points

- `ExecutorService` manages a pool of threads; submit work with `execute()` (fire-and-forget) or `submit()` (returns a `Future`).
Always shut down the pool.
- `Callable<V>` is like `Runnable` but returns a value and can throw checked exceptions.
- `Future<V>.get()` blocks until the result is ready; exceptions from the callable are wrapped in `ExecutionException`.
- `CompletableFuture<T>` enables non-blocking, composable async pipelines: `supplyAsync`, `thenApply`, `thenCompose`, `thenCombine`, `exceptionally`, `allOf`.
- `AtomicInteger` and friends provide lock-free CAS operations on single variables --- equivalent to C++'s `std::atomic<T>`.
- `ReentrantLock` is more flexible than `synchronized` but requires explicit unlock in a `finally` block.
`ReentrantReadWriteLock` is the equivalent of C++17's `std::shared_mutex`.
- `CountDownLatch`, `CyclicBarrier`, and `Semaphore` cover the common coordination patterns.
- `ConcurrentHashMap` is the thread-safe map of choice; `CopyOnWriteArrayList` for read-heavy lists; `BlockingQueue` for producer-consumer.
- Virtual threads (Java 21+) are JVM-managed, cheap, and unmount during blocking --- enabling millions of concurrent tasks without reactive programming.
- Avoid `synchronized` for blocking operations on virtual threads --- it can pin the carrier thread.
Use `ReentrantLock` instead.
