# Testing

C++ has a rich testing ecosystem --- Google Test, Catch2, doctest --- but none of it is standardized.
Every project makes its own choices about frameworks, mocking libraries, and CMake integration.
Java landed on a much more uniform stack: JUnit 5 for test execution, Mockito for mocking, JaCoCo for coverage, and Maven or Gradle to wire it all together.
If you have used Google Test and GMock, the mental model transfers almost directly; the API just looks different.

This chapter walks you through JUnit 5, assertions, parameterized tests, Mockito, test organization, running tests from the command line, and measuring coverage with JaCoCo.

## JUnit 5 Overview

\index{JUnit 5}
\index{JUnit 5!Jupiter}

**JUnit 5** (also called **Jupiter**) is the current standard test framework for Java.
Like Google Test or Catch2, it discovers test methods automatically and reports results.
Unlike Google Test, there is no base class to inherit from.
A test class is a plain Java class, and test methods are identified by the `@Test` annotation.

To add JUnit 5 to a Maven project, add this dependency to `pom.xml`:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.11.0</version>
    <scope>test</scope>
</dependency>
```

The `<scope>test</scope>` element means the dependency is available only during compilation and execution of tests --- it is not included in your production artifact.
This is roughly analogous to a CMake target that only links test executables.

The Maven Surefire plugin (version 3.x) picks up JUnit 5 tests automatically when `junit-jupiter` is on the test classpath.

::: {.tip}
**Tip:** In Google Test you subclass `::testing::Test` or `::testing::TestWithParam<T>`.
In JUnit 5 you annotate a plain class.
No inheritance, no registration macros --- just annotations.
:::

## Lifecycle Annotations

\index{JUnit 5!lifecycle annotations}

JUnit 5 controls test setup and teardown through annotations placed on methods in the test class.

### `@Test`

\index{@Test}

```java
@Test
void shouldReturnUpperCase() { ... }
```

Marks a method as a test case.
The method must return `void` and, by default, takes no parameters.
JUnit 5 discovers and runs every `@Test`-annotated method in the class.

### `@BeforeEach` and `@AfterEach`

\index{@BeforeEach}
\index{@AfterEach}

```java
@BeforeEach
void setUp() { ... }

@AfterEach
void tearDown() { ... }
```

`@BeforeEach` runs before every test method in the class --- the JUnit equivalent of Google Test's `SetUp()`.
`@AfterEach` runs after every test method --- the equivalent of `TearDown()`.
Each test method gets a fresh object instance by default, so instance state set in one test does not leak into another.

### `@BeforeAll` and `@AfterAll`

\index{@BeforeAll}
\index{@AfterAll}

```java
@BeforeAll
static void setUpClass() { ... }

@AfterAll
static void tearDownClass() { ... }
```

`@BeforeAll` runs exactly once before any test in the class.
`@AfterAll` runs exactly once after all tests in the class finish.
Both methods must be `static` (unless you annotate the class with `@TestInstance(Lifecycle.PER_CLASS)`, which tells JUnit to create one instance for all tests instead of one per test).
Use these for expensive shared setup like starting a database or reading a large file.

### `@Disabled`

\index{@Disabled}

```java
@Disabled("Virtual Insanity fix pending --- Jamiroquai's key keeps changing")
@Test
void skippedTest() { ... }
```

Skips a test method or an entire class.
Always provide a reason --- future you will thank present you.
In Google Test the equivalent is `DISABLED_` prefixed to the test name; `@Disabled` is cleaner because the reason is attached.

### `@DisplayName`

\index{@DisplayName}

```java
@DisplayName("Song title must not be blank")
@Test
void titleMustNotBeBlank() { ... }
```

Provides a human-readable name that appears in test reports and IDE output instead of the method name.
Useful for long, descriptive test names that would be ugly as Java identifiers.

### Complete Lifecycle Skeleton

Here is a test class that uses all lifecycle annotations:

```java
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

@DisplayName("SongService tests")
class SongServiceTest {

    private SongService service;

    @BeforeAll
    static void initSharedResources() {
        System.out.println("once before all tests");
    }

    @AfterAll
    static void cleanupSharedResources() {
        System.out.println("once after all tests");
    }

    @BeforeEach
    void setUp() {
        service = new SongService();    // fresh instance each test
    }

    @AfterEach
    void tearDown() {
        service = null;
    }

    @Test
    @DisplayName("find() returns matching song")
    void findReturnsSong() {
        assertNotNull(service.find("Virtual Insanity"));
    }

    @Test
    @Disabled("not implemented yet")
    void skippedTest() {
        fail("should not run");
    }
}
```

## Assertions

\index{JUnit 5!assertions}
\index{Assertions}

All JUnit 5 assertion methods live in `org.junit.jupiter.api.Assertions`.
Static-import the class to avoid typing the full name on every line:

```java
import static org.junit.jupiter.api.Assertions.*;
```

### `assertEquals` and `assertNotEquals`

\index{assertEquals}
\index{assertNotEquals}

```java
static void assertEquals(Object expected, Object actual)
static void assertNotEquals(Object unexpected, Object actual)
```

`assertEquals` calls `.equals()`, not `==`.
Put the expected value first and the actual value second --- this is the convention for meaningful failure messages.
Both methods have overloads for all primitive types (`int`, `long`, `double`, etc.) and for `double` with a delta: `assertEquals(double expected, double actual, double delta)`.

```java
@Test
void songTitleEquals() {
    String title = service.find("Virtual Insanity").title();
    assertEquals("Virtual Insanity", title);    // uses .equals()
    assertNotEquals("Cosmic Girl", title);
}
```

::: {.tip}
**Trap:** `assertEquals` on floating-point values can fail due to rounding.
Use `assertEquals(double expected, double actual, double delta)` or `assertEquals(float expected, float actual, float delta)` and supply a tolerance.
:::

### `assertTrue` and `assertFalse`

\index{assertTrue}
\index{assertFalse}

```java
static void assertTrue(boolean condition)
static void assertFalse(boolean condition)
```

Simple boolean checks.
Prefer `assertEquals` or a more specific assertion when possible --- the failure message from `assertEquals` is more informative than "expected true but was false."

### `assertNull` and `assertNotNull`

\index{assertNull}
\index{assertNotNull}

```java
static void assertNull(Object actual)
static void assertNotNull(Object actual)
```

Verify that a reference is or is not `null`.
Useful after factory methods or lookups that may return `null`.

### `assertThrows`

\index{assertThrows}

```java
static <T extends Throwable> T assertThrows(Class<T> expectedType, Executable executable)
```

Verifies that executing `executable` throws an exception of the given type.
Returns the thrown exception so you can inspect its message or state --- this is more powerful than Google Test's `EXPECT_THROW`, which only checks the type.

```java
@Test
void lookupMissingSongThrows() {
    IllegalArgumentException ex = assertThrows(
        IllegalArgumentException.class,
        () -> service.find(null)
    );
    assertTrue(ex.getMessage().contains("null"));
}
```

### `assertDoesNotThrow`

\index{assertDoesNotThrow}

```java
static void assertDoesNotThrow(Executable executable)
```

Verifies that `executable` completes without throwing.
Use this when the absence of an exception is the explicit assertion --- it documents intent better than a bare call with no assertion.

### `assertAll`

\index{assertAll}

```java
static void assertAll(Executable... executables)
```

Runs every assertion in its argument list and reports all failures, not just the first one.
Google Test does something similar with `EXPECT_*` (non-fatal) vs `ASSERT_*` (fatal); `assertAll` is the JUnit equivalent of grouping `EXPECT_*` checks.

```java
@Test
void songHasAllFields() {
    Song song = service.find("Virtual Insanity");
    assertAll(
        () -> assertNotNull(song.title()),
        () -> assertNotNull(song.artist()),
        () -> assertTrue(song.year() > 1990)
    );
}
```

### `assertIterableEquals`

\index{assertIterableEquals}

```java
static void assertIterableEquals(Iterable<?> expected, Iterable<?> actual)
```

Performs a deep, element-by-element comparison of two iterables.
The iterables must have the same size and the same elements in the same order, as determined by `.equals()`.

### Optional Message Parameter

Every assertion accepts an optional last `String` argument (or `Supplier<String>`) that appears in the failure message.
Use the `Supplier<String>` form for expensive messages that you only want to construct on failure:

```java
assertEquals("Virtual Insanity", title, "song title mismatch");
assertEquals("Virtual Insanity", title, () -> "got: " + title);
```

## Parameterized Tests

\index{JUnit 5!parameterized tests}
\index{@ParameterizedTest}

Parameterized tests run the same test logic against multiple inputs.
In Google Test this is `INSTANTIATE_TEST_SUITE_P` with a typed test suite; in JUnit 5 it is the `@ParameterizedTest` annotation with a source annotation that supplies the inputs.

The `junit-jupiter-params` artifact provides parameterized test support.
It is included automatically when you depend on `org.junit.jupiter:junit-jupiter`.

### `@ValueSource`

\index{@ValueSource}

```java
@ParameterizedTest
@ValueSource(strings = {"Virtual Insanity", "Cosmic Girl", "Alright"})
void titleIsNonEmpty(String title) {
    assertFalse(title.isEmpty());
}
```

`@ValueSource` supplies a single value per invocation.
It supports `strings`, `ints`, `longs`, `doubles`, `chars`, `booleans`, `bytes`, `shorts`, `floats`, and `classes`.

### `@CsvSource`

\index{@CsvSource}

```java
@ParameterizedTest
@CsvSource({
    "Virtual Insanity, Jamiroquai, 1996",
    "Cosmic Girl,      Jamiroquai, 1996",
    "Alright,          Jamiroquai, 1996"
})
void songBelongsToArtist(String title, String artist, int year) {
    Song song = service.find(title);
    assertEquals(artist, song.artist());
    assertEquals(year,   song.year());
}
```

Each string is a CSV row.
JUnit converts each column to the corresponding parameter type.

### `@NullSource`, `@EmptySource`, `@NullAndEmptySource`

\index{@NullSource}
\index{@EmptySource}
\index{@NullAndEmptySource}

These convenience source annotations inject `null`, an empty value, or both, as extra test cases.
They are often combined with `@ValueSource`:

```java
@ParameterizedTest
@NullAndEmptySource
@ValueSource(strings = {"   "})
void blankOrNullTitleIsInvalid(String title) {
    assertThrows(IllegalArgumentException.class,
        () -> new Song(title, "Jamiroquai", 1996));
}
```

### `@MethodSource`

\index{@MethodSource}

`@MethodSource` points to a static factory method that returns a `Stream<Arguments>` (or a `Stream` of single values).
This is the most flexible source: you can build complex objects, add documentation strings, and reuse providers across test classes.

```java
import org.junit.jupiter.params.provider.Arguments;
import org.junit.jupiter.params.provider.MethodSource;
import java.util.stream.Stream;

class SongValidationTest {

    static Stream<Arguments> validSongs() {
        return Stream.of(
            Arguments.of("Virtual Insanity", "Jamiroquai", 1996),
            Arguments.of("Cosmic Girl",      "Jamiroquai", 1996),
            Arguments.of("Alright",          "Jamiroquai", 1996)
        );
    }

    @ParameterizedTest(name = "{0} by {1} ({2})")
    @MethodSource("validSongs")
    void validSongCanBeCreated(String title, String artist, int year) {
        Song song = new Song(title, artist, year);
        assertEquals(title,  song.title());
        assertEquals(artist, song.artist());
        assertEquals(year,   song.year());
    }
}
```

The `name` attribute on `@ParameterizedTest` lets you customize the display name for each invocation; `{0}`, `{1}`, `{2}` are the argument indices.

::: {.tip}
**Tip:** Name the provider method after what it provides (`validSongs`, `invalidTitles`) rather than after the test (`songDataProvider`).
That way the `@MethodSource` value reads like documentation.
:::

## Mockito

\index{Mockito}

**Mockito** is the de-facto mocking library for Java.
It plays the same role as GMock in C++: replace a dependency with a controlled fake so you can test a unit in isolation.
The key difference from GMock is that Mockito works on any interface or concrete class at runtime via bytecode generation; you do not need to write mock classes by hand or use template magic.

Add Mockito to `pom.xml`:

```xml
<dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-core</artifactId>
    <version>5.12.0</version>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-junit-jupiter</artifactId>
    <version>5.12.0</version>
    <scope>test</scope>
</dependency>
```

### Creating Mocks

\index{Mockito!mock}

```java
SongRepository repo = Mockito.mock(SongRepository.class);
```

`Mockito.mock(Class<T> classToMock)` returns an object that implements the given type.
By default every method returns its zero value: `null` for objects, `0` for numbers, `false` for booleans, and an empty collection for collection return types.
Calling an unstubbed method does not throw --- it silently returns the default.
This is different from GMock, where calling an unconfigured expectation fails by default in strict mode.

### `@Mock` and `@ExtendWith`

\index{@Mock}
\index{@ExtendWith}
\index{MockitoExtension}

Using `Mockito.mock()` inline works but gets verbose.
The `@Mock` annotation with `@ExtendWith(MockitoExtension.class)` does the same thing with less code:

```java
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class SongServiceTest {

    @Mock
    SongRepository repo;    // injected by Mockito before each test

    // ...
}
```

`MockitoExtension` is a JUnit 5 extension that initializes `@Mock` fields before each test and validates that all configured interactions were used.

### Stubbing

\index{Mockito!stubbing}
\index{when}
\index{thenReturn}
\index{thenThrow}

Stubbing tells Mockito what to return (or throw) when a specific method is called:

```java
when(repo.findByTitle("Virtual Insanity")).thenReturn(
    new Song("Virtual Insanity", "Jamiroquai", 1996)
);

when(repo.findByTitle(null)).thenThrow(
    new IllegalArgumentException("title must not be null")
);
```

`when(mock.method(args))` is the stubbing trigger; `.thenReturn(value)` sets the return value; `.thenThrow(exception)` makes the method throw.
You can chain multiple outcomes: `thenReturn(first).thenReturn(second)` returns `first` on the first call and `second` on subsequent calls.

### Verification

\index{Mockito!verify}
\index{verify}

After exercising the code under test, you verify that the mock was called as expected:

```java
verify(repo).findByTitle("Virtual Insanity");           // called exactly once
verify(repo, times(2)).findByTitle("Cosmic Girl");       // called exactly twice
verify(repo, never()).save(any());                       // never called
```

`verify(mock)` is a shorthand for `verify(mock, times(1))`.
GMock sets expectations before the call; Mockito verifies after the call.
Both styles work; Mockito's post-call style tends to read more naturally for state-based tests.

### Argument Matchers

\index{Mockito!argument matchers}
\index{any()}
\index{eq()}

When you do not care about the exact argument, use a matcher:

```java
when(repo.findByTitle(anyString())).thenReturn(null);
verify(repo).save(any(Song.class));
verify(repo, never()).delete(anyInt());
```

The primary matchers:

| Matcher | Matches |
|:--------|:--------|
| `any()` | Any object including `null` |
| `any(Foo.class)` | Any non-null `Foo` instance |
| `anyString()` | Any non-null `String` |
| `anyInt()` | Any `int` value |
| `anyLong()` | Any `long` value |
| `eq(value)` | Exact equality via `.equals()` |
| `isNull()` | `null` specifically |
| `isNotNull()` | Any non-null value |

::: {.tip}
**Trap:** You cannot mix matchers and raw values in the same method call.
`verify(repo).findByTitleAndYear("Virtual Insanity", anyInt())` will throw a Mockito error.
Wrap the literal with `eq()`: `verify(repo).findByTitleAndYear(eq("Virtual Insanity"), anyInt())`.
:::

### `ArgumentCaptor`

\index{Mockito!ArgumentCaptor}
\index{@Captor}

When you need to inspect the exact argument passed to a mock, use `ArgumentCaptor`:

```java
@Captor
ArgumentCaptor<Song> songCaptor;

@Test
void savesCorrectSong() {
    service.add("Virtual Insanity", "Jamiroquai", 1996);
    verify(repo).save(songCaptor.capture());
    Song saved = songCaptor.getValue();
    assertEquals("Virtual Insanity", saved.title());
    assertEquals(1996, saved.year());
}
```

`@Captor` is the annotation equivalent of `ArgumentCaptor.forClass(Song.class)`.
After `verify`, call `getValue()` to retrieve the captured argument, or `getAllValues()` if the method was called multiple times.

### `@Spy`

\index{Mockito!@Spy}
\index{@Spy}

A **spy** wraps a real object.
Real methods are called by default; you selectively stub the ones you want to override.
Use `doReturn` rather than `when` for spies to avoid executing the real method during setup:

```java
@Spy
SongService realService = new SongService(new InMemorySongRepository());

@Test
void findDelegatesCorrectly() {
    doReturn(new Song("Cosmic Girl", "Jamiroquai", 1996))
        .when(realService).find("Cosmic Girl");
    Song s = realService.find("Cosmic Girl");
    assertEquals("Cosmic Girl", s.title());
}
```

Spies are useful when you want to test most of a class's real behavior but need to control one or two methods, such as a network call or a clock.

### Complete Mockito Example

Here is a self-contained example that defines an interface and a service class, then tests the service with a mocked repository:

```java
// --- domain ---
record Song(String title, String artist, int year) {}

// --- repository interface (the dependency) ---
interface SongRepository {
    Song findByTitle(String title);
    void save(Song song);
}

// --- service (the class under test) ---
class SongService {
    private final SongRepository repo;

    SongService(SongRepository repo) {
        this.repo = repo;
    }

    Song find(String title) {
        if (title == null) throw new IllegalArgumentException("title must not be null");
        return repo.findByTitle(title);
    }

    void add(String title, String artist, int year) {
        repo.save(new Song(title, artist, year));
    }
}

// --- test ---
import org.junit.jupiter.api.*;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.*;
import org.mockito.junit.jupiter.MockitoExtension;
import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class)
class SongServiceMockTest {

    @Mock
    SongRepository repo;

    SongService service;

    @BeforeEach
    void setUp() {
        service = new SongService(repo);
    }

    @Test
    void findDelegatesToRepository() {
        Song expected = new Song("Virtual Insanity", "Jamiroquai", 1996);
        when(repo.findByTitle("Virtual Insanity")).thenReturn(expected);

        Song result = service.find("Virtual Insanity");

        assertEquals(expected, result);
        verify(repo).findByTitle("Virtual Insanity");
    }

    @Test
    void findThrowsOnNullTitle() {
        assertThrows(IllegalArgumentException.class,
            () -> service.find(null));
        verify(repo, never()).findByTitle(any());
    }

    @Test
    void addSavesCorrectSong() {
        service.add("Virtual Insanity", "Jamiroquai", 1996);

        ArgumentCaptor<Song> captor = ArgumentCaptor.forClass(Song.class);
        verify(repo).save(captor.capture());
        assertEquals("Virtual Insanity", captor.getValue().title());
        assertEquals(1996,               captor.getValue().year());
    }
}
```

## Test Organization

\index{test organization}
\index{unit test}
\index{integration test}

### Test Pyramid

The industry-standard layering:

- **Unit tests**: one class under test, all dependencies mocked.
Fast (milliseconds), isolated, run on every build.
- **Integration tests**: multiple real components together --- a real database, a real HTTP client, a file system.
Slower (seconds), catch wiring bugs that unit tests miss.
- **End-to-end tests**: the full system, driven through its external interface.
Slowest, highest confidence, most brittle.

Run all three in CI; run only unit tests locally during development.

### Maven Directory Layout

\index{Maven!directory layout}

Maven enforces a standard layout that JUnit and your IDE understand automatically:

```
src/
  main/
    java/
      com/example/SongService.java       ← production code
  test/
    java/
      com/example/SongServiceTest.java   ← unit tests
      com/example/SongServiceIT.java     ← integration tests
```

Put test classes in the same package as the class under test.
This gives the test class access to package-private members --- the Java equivalent of a `friend` declaration, but without the coupling it implies in C++.

### Naming Conventions

\index{test!naming conventions}

- `FooTest` --- unit test for `Foo`.
- `FooIT` --- integration test for `Foo` (the `IT` suffix is the Maven Failsafe plugin convention).

The suffix distinction matters: the Maven Surefire plugin (which runs `mvn test`) includes `*Test` and `Test*` patterns by default; the Failsafe plugin (which runs `mvn verify`) targets `*IT`, `IT*`, and `*ITCase`.
Keep the naming consistent and you get the right tests at the right phase automatically.

## Running Tests

\index{running tests}
\index{Maven!mvn test}

### Maven

```
mvn test
```

Runs all unit tests (Surefire, `*Test` pattern).
Results appear in `target/surefire-reports/`.

```
mvn verify
```

Runs unit tests and then integration tests (Failsafe, `*IT` pattern).

Run a specific test class:

```
mvn test -Dtest=SongServiceTest
```

Run a specific test method:

```
mvn test -Dtest=SongServiceTest#findDelegatesToRepository
```

### Gradle

```
./gradlew test
```

Runs all tests.
Results appear in `build/reports/tests/test/`.

Run a specific test class or method:

```
./gradlew test --tests "com.example.SongServiceTest"
./gradlew test --tests "com.example.SongServiceTest.findDelegatesToRepository"
```

::: {.tip}
**Tip:** In a large project, `mvn test -pl module-name` (Maven) or `./gradlew :module-name:test` (Gradle) runs tests for a single submodule.
You do not need to run the entire build to iterate on one module.
:::

## Code Coverage with JaCoCo

\index{JaCoCo}
\index{code coverage}

**JaCoCo** (Java Code Coverage) is the standard coverage tool in the Java ecosystem.
It instruments your bytecode and tracks which lines and branches are executed by your tests.
The equivalent in C++ is `gcov`/`lcov` or LLVM's `llvm-cov`.

Add the JaCoCo Maven plugin to `pom.xml` under the `<build><plugins>` section:

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.12</version>
    <executions>
        <execution>
            <goals>
                <goal>prepare-agent</goal>
            </goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>verify</phase>
            <goals>
                <goal>report</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

Run `mvn verify` and JaCoCo generates an HTML report under `target/site/jacoco/index.html`.
Open it in a browser to see line-by-line and branch-by-branch coverage.

The two metrics to watch:

- **Line coverage**: the percentage of lines executed at least once by your tests.
- **Branch coverage**: the percentage of conditional branches (both sides of every `if`, `?:`, `switch` arm) exercised by your tests.

Branch coverage is the more demanding metric.
A test suite can achieve 100% line coverage while missing half the branches, leaving untested paths through every conditional.

::: {.tip}
**Wut:** 100% coverage does not mean your tests are good.
Coverage tells you which code was *executed*, not whether the assertions were meaningful.
A test that calls every method but asserts nothing will hit 100% and catch nothing.
Coverage is a lower bound on quality, not an upper bound.
:::

::: {.tip}
**Tip:** Add a JaCoCo coverage enforcement rule to fail the build when coverage drops below a threshold.
Add an `<execution>` with `<goal>check</goal>` and a `<rule>` element specifying minimum line or branch coverage.
This prevents coverage regressions from slipping through code review.
:::

## Key Points

- JUnit 5 test classes are plain Java classes; annotate methods with `@Test` --- no base class required.
- `@BeforeEach` / `@AfterEach` run before/after each test; `@BeforeAll` / `@AfterAll` run once for the class and must be `static` by default.
- `@Disabled("reason")` skips a test; `@DisplayName("text")` gives it a human-readable label in reports.
- `assertThrows` returns the thrown exception so you can inspect its message; `assertAll` runs all assertions and reports all failures instead of stopping at the first.
- Parameterized tests use `@ParameterizedTest` with a source annotation: `@ValueSource` for simple single values, `@CsvSource` for tabular data, `@MethodSource` for full `Stream<Arguments>` control.
- Mockito creates mocks at runtime with no hand-written mock classes; stub with `when(...).thenReturn(...)` and verify with `verify(mock).method(args)`.
- Always mix matchers consistently in a single call --- use `eq(value)` to wrap literal arguments when other arguments use matchers.
- `ArgumentCaptor` captures arguments passed to a mock for precise post-call assertions.
- Place test classes in the same package as the class under test to access package-private members; use `FooTest` for unit tests and `FooIT` for integration tests.
- `mvn test` runs unit tests via Surefire; `mvn verify` also runs integration tests via Failsafe; Gradle uses `./gradlew test`.
- JaCoCo measures line and branch coverage; branch coverage is the harder and more useful metric; high coverage is necessary but not sufficient for a good test suite.

    import org.junit.jupiter.api.*;
