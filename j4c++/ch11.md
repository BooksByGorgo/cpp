# Generics

C++ templates are one of the most powerful features of the language --- compile-time code generation, full type information at every instantiation, zero-overhead abstractions.
Java generics look similar on the surface: angle brackets, type parameters, bounded constraints.
But the underlying mechanism is fundamentally different, and that difference has real, unavoidable consequences.
Understanding *why* Java generics work the way they do --- and what the tradeoffs cost you --- is essential for writing correct generic Java code.

This chapter covers the syntax, type erasure, wildcards, bounded type parameters, and the most common pitfalls.
If you have ever asked "why can't I do `new T()`?" or "why won't the compiler accept `List<Dog>` where `List<Animal>` is expected?", you are about to find out.

## Syntax vs C++ Templates

\index{generics}
\index{generics!syntax}
\index{type parameter}

In C++, you declare a generic class with:

```cpp
template<typename T>
class Box {
    T value;
};
```

In Java, the syntax swaps `template<typename T>` for a type parameter list directly after the class name:

```java
public class Box<T> {
    private T value;

    public Box(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}
```

Using the class:

```java
Box<String> lyrics = new Box<>("What's up?");    // 4 Non Blondes, 1992
Box<Integer> year  = new Box<>(1992);
String s = lyrics.get();                          // String, no cast needed
```

The `<>` on the right side is the **diamond operator** (Java 7+) --- the compiler infers the type argument from context, just like C++ template argument deduction.

Multiple type parameters work the same way as in C++:

```java
public class Pair<K, V> {
    private final K key;
    private final V value;

    public Pair(K key, V value) {
        this.key   = key;
        this.value = value;
    }

    public K getKey()   { return key; }
    public V getValue() { return value; }
}
```

### Generic Methods

\index{generics!generic method}

Generic methods carry their own type parameter list, placed before the return type:

```java
public static <T> List<T> repeat(T item, int count) {
    List<T> result = new ArrayList<>();
    for (int i = 0; i < count; i++) {
        result.add(item);
    }
    return result;
}
```

Usage:

```java
List<String> chorus = repeat("What's up?", 4);
List<Integer> zeros = repeat(0, 10);
```

The compiler infers the type argument from the argument you pass.
You can also specify it explicitly: `Generics.<String>repeat("hey", 3)`, but you rarely need to.

In C++ this is just a function template:

```cpp
template<typename T>
std::vector<T> repeat(T item, int count) { ... }
```

The syntax is different but the intent is identical.

### The Critical Difference: Code Generation vs Type Erasure

\index{type erasure}
\index{generics!type erasure}

Here is where Java and C++ diverge completely.

In C++, `vector<int>` and `vector<string>` are **completely separate types** generated at compile time.
The compiler stamps out a new copy of `vector`'s code for each distinct type argument.
At runtime, `vector<int>` and `vector<string>` have nothing in common; they are as different as two unrelated classes.

Java takes the opposite approach.
At compile time, the compiler uses type information to check correctness and insert casts.
Then it **erases** the type parameters.
At runtime, `Box<String>` and `Box<Integer>` are both just `Box`.
There is one class, one set of bytecode, shared by all instantiations.

This approach is called **type erasure**, and it was chosen for backward compatibility with Java code written before generics existed (pre-Java 5).

::: {.tip}
**Wut:** At runtime, `Box<String>` and `Box<Integer>` are the same type --- `Box`.
`new Box<String>().getClass() == new Box<Integer>().getClass()` evaluates to `true`.
In C++, `std::vector<int>` and `std::vector<std::string>` are completely different types with no runtime relationship.
:::

## Type Erasure --- What It Costs You

\index{type erasure!consequences}

Type erasure is not just an implementation detail; it has direct, unavoidable consequences for what you can write.

### No `new T()`

You cannot instantiate a type parameter:

```java
public class Maker<T> {
    public T make() {
        return new T();   // compile error: cannot instantiate T
    }
}
```

The reason is simple: at runtime `T` is gone.
The JVM has no idea what type `T` was, so it cannot call any constructor.

The standard workaround is to pass a `Class<T>` object (or, in modern Java, a `Supplier<T>`):

```java
public class Maker<T> {
    private final Supplier<T> factory;

    public Maker(Supplier<T> factory) {
        this.factory = factory;
    }

    public T make() {
        return factory.get();
    }
}

// Usage:
Maker<StringBuilder> m = new Maker<>(StringBuilder::new);
```

### No Generic Arrays

You cannot create an array of a generic type:

```java
T[] arr = new T[10];           // compile error
Box<String>[] boxes = new Box<String>[5]; // compile error (generic array creation)
```

The JVM's array system retains element type information at runtime (for `ArrayStoreException` checking), but erased generics cannot supply that information.
Use `ArrayList<T>` instead, or create an `Object[]` and cast it (with a suppressed warning and careful code).

### No `instanceof Box<String>`

You cannot test the generic type of an instance:

```java
Object obj = new Box<String>("hey");
if (obj instanceof Box<String>) { ... }   // compile error
if (obj instanceof Box<?>)      { ... }   // OK
if (obj instanceof Box)         { ... }   // OK (raw type)
```

At runtime, both `Box<String>` and `Box<Integer>` are just `Box`, so there is nothing to test.

### No Overloading on Generic Type Arguments

Because `List<String>` and `List<Integer>` erase to the same type `List`, these two method signatures are identical after erasure:

```java
void process(List<String> strings) { ... }
void process(List<Integer> ints)   { ... }  // compile error: same erasure
```

The compiler rejects this.
In C++ this is fine because the template instantiations are distinct types.

### Heap Pollution

\index{heap pollution}

Mixing raw types and parameterized types can put the wrong type of object into a generic container --- a condition called **heap pollution**.
The compiler warns you with an `unchecked` warning:

```java
List raw = new ArrayList<String>();    // raw type: no warning yet
raw.add(1992);                         // unchecked warning: adding int to raw List
List<String> typed = raw;             // unchecked warning: unsafe assignment
String s = typed.get(0);             // ClassCastException at runtime
```

::: {.tip}
**Trap:** Never use raw types in new code.
Raw types exist only for backward compatibility with pre-Java-5 code.
Always use parameterized types: `List<String>`, not `List`.
:::

## Bounded Type Parameters

\index{bounded type parameter}
\index{generics!bounds}

You can constrain a type parameter to a subtype of some class or interface using `extends`:

```java
public <T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}
```

The bound `T extends Comparable<T>` means "T must implement `Comparable<T>`."
The compiler then allows you to call `compareTo` on values of type `T`, because it knows the bound guarantees that method exists.

Compare this to C++ concepts:

```cpp
// C++20 concept
template<typename T>
requires std::totally_ordered<T>
T max(T a, T b) {
    return a >= b ? a : b;
}
```

Both constrain what types are accepted.
The key difference is mechanism: Java's bound is a **subtype constraint** (T must be a subtype of the bound), while C++ concepts can express arbitrary structural requirements.
Java cannot say "T must have a method named `foo` that takes a `String`" without that method being declared in some interface that T extends.

### Multiple Bounds

\index{bounded type parameter!multiple bounds}

A type parameter can have multiple bounds using `&`:

```java
public <T extends Serializable & Comparable<T>> void store(T item) {
    // item can be serialized and compared
}
```

The `&` separates bounds.
At most one bound may be a class; the rest must be interfaces.
The class bound must come first.

```java
<T extends AbstractBase & InterfaceA & InterfaceB>   // OK: one class, two interfaces
<T extends InterfaceA & InterfaceB>                   // OK: two interfaces
<T extends ClassA & ClassB>                           // compile error: two class bounds
```

## Wildcards

\index{wildcard}
\index{generics!wildcard}

Wildcards are one of the trickiest parts of Java generics.
They solve a problem that C++ does not have, because C++ templates are covariant by instantiation whereas Java generics are invariant.

Consider this: you have a method that should print any list of numbers:

```java
void printAll(List<Number> list) {
    for (Number n : list) System.out.println(n);
}
```

You try to call it with a `List<Integer>`:

```java
List<Integer> ints = List.of(1, 9, 9, 2);
printAll(ints);   // compile error: List<Integer> is not List<Number>
```

The compiler rejects this.
`List<Integer>` is **not** a subtype of `List<Number>` even though `Integer` is a subtype of `Number`.
This is generic **invariance**, and Java generics are invariant by default.

Arrays, on the other hand, are **covariant**: `Integer[]` is a subtype of `Number[]`.
But covariant arrays cause `ArrayStoreException`:

```java
Number[] arr = new Integer[4];  // compiles
arr[0] = 3.14;                  // ArrayStoreException at runtime
```

Java made generics invariant precisely to avoid this class of runtime error.

Wildcards let you express flexibility without breaking type safety.

### Unbounded Wildcard: `<?>`

\index{wildcard!unbounded}

`List<?>` means "a list of some unknown type."

```java
void printAll(List<?> list) {
    for (Object item : list) {
        System.out.println(item);
    }
}
```

Now `printAll(ints)` compiles.
You can read elements as `Object`, but you **cannot add** anything (except `null`) because the compiler does not know what type the list holds.

### Upper-Bounded Wildcard: `<? extends T>`

\index{wildcard!upper bounded}

`List<? extends Number>` means "a list of some type that is Number or a subtype of Number."

```java
void sumAll(List<? extends Number> list) {
    double sum = 0;
    for (Number n : list) {
        sum += n.doubleValue();
    }
    System.out.println(sum);
}
```

You can read elements as `Number` (the upper bound), but you still cannot add elements, because the compiler does not know the exact element type.
Is it `List<Integer>`? `List<Double>`? Adding a `Double` to a `List<Integer>` would be wrong.
Upper-bounded wildcards make the list a **producer** of values.

### Lower-Bounded Wildcard: `<? super T>`

\index{wildcard!lower bounded}

`List<? super Integer>` means "a list of some type that is Integer or a supertype of Integer."

```java
void addIntegers(List<? super Integer> list, int count) {
    for (int i = 0; i < count; i++) {
        list.add(i);
    }
}
```

You can add `Integer` values because any supertype of `Integer` --- `Number`, `Object` --- can hold an `Integer`.
But when you read, you can only get `Object` because that is the only type guaranteed to be a supertype of every possible bound.
Lower-bounded wildcards make the list a **consumer** of values.

### PECS: Producer Extends, Consumer Super

\index{PECS}
\index{generics!PECS}

The mnemonic **PECS** summarizes when to use each wildcard:

- **Producer Extends**: use `<? extends T>` when you only read from the collection (it produces values for you).
- **Consumer Super**: use `<? super T>` when you only write to the collection (it consumes values you give it).

A concrete example: copying elements from one list to another.

```java
public static <T> void copy(List<? extends T> src, List<? super T> dst) {
    for (T item : src) {
        dst.add(item);
    }
}
```

`src` produces `T` values, so `extends`.
`dst` consumes `T` values, so `super`.
This single method can copy `List<Integer>` into `List<Number>`, or `List<String>` into `List<Object>`.

::: {.tip}
**Tip:** If you only read from a generic collection parameter, use `<? extends T>`.
If you only write to it, use `<? super T>`.
If you do both, use the exact type `<T>`.
:::

## Raw Types

\index{raw type}

A **raw type** is a generic class used without any type argument:

```java
List list = new ArrayList();    // raw type: the T in List<T> is gone
list.add("hey");
list.add(1992);                 // no compile error -- you just lost type safety
String s = (String) list.get(1); // ClassCastException at runtime
```

Raw types exist solely for backward compatibility with Java code written before Java 5 (2004).
The compiler warns you when you use them.
New code should never use raw types.

::: {.tip}
**Trap:** Raw types silence the generics type checker.
The compiler will not catch type mismatches until you get a `ClassCastException` at runtime.
Use parameterized types everywhere.
:::

## Generics and Inheritance: Invariance

\index{generics!invariance}

To hammer the invariance point home with a clear example:

```java
List<String> songs   = new ArrayList<>();
List<Object> objects = songs;     // compile error: incompatible types
```

Even though `String` is a subtype of `Object`, `List<String>` is **not** a subtype of `List<Object>`.
If this were allowed, you could do:

```java
objects.add(1992);                 // would add an Integer to a List<String>
String s = songs.get(0);          // ClassCastException
```

This is the same reason C++ templates are invariant too: `vector<Dog>*` does not convert to `vector<Animal>*`.
Java makes this a compile error rather than undefined behavior; C++ gives you a type mismatch that the compiler also rejects.

The difference is that Java arrays *are* covariant (they have a runtime check), while Java generics are invariant (no runtime type info to check with).

::: {.tip}
**Wut:** `Dog[]` is a subtype of `Animal[]` in Java (covariant arrays), but `List<Dog>` is **not** a subtype of `List<Animal>` (invariant generics).
C++ templates are also invariant --- `vector<Dog>` does not convert to `vector<Animal>` --- but C++ arrays decay to pointers and have no such covariance guarantee.
:::

## Key Points

- Java generics use **type erasure**: type parameters are erased at compile time and replaced with `Object` (or the upper bound).
  At runtime, `Box<String>` and `Box<Integer>` are the same class.
- C++ templates generate **distinct types** for each instantiation; Java generics produce one shared class.
- Type erasure means you cannot: instantiate `T` with `new T()`, create `T[]` arrays, use `instanceof Box<String>`, or overload methods that differ only in generic type arguments.
- **Bounded type parameters** (`<T extends Comparable<T>>`) constrain what types are accepted, like C++ concepts but restricted to subtype relationships.
- **Multiple bounds** use `&`: `<T extends Serializable & Comparable<T>>` (at most one class, rest interfaces; class comes first).
- `List<Dog>` is **not** a subtype of `List<Animal>` --- generics are invariant.
  Arrays are covariant (`Dog[]` is a `Animal[]`), but generics are not.
- Use `<? extends T>` when a parameter only **produces** values (you read from it).
- Use `<? super T>` when a parameter only **consumes** values (you write to it).
- **PECS**: Producer Extends, Consumer Super.
- **Raw types** (`List` without `<>`) bypass the type system.
  Never use them in new code.
