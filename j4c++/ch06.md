# Classes and Objects

In C++ you split a class across two files --- a header declaring the interface and a `.cpp` file defining the methods.
In Java, the declaration and the definition live together in one `.java` file, and the file name must match the `public` class name.
There are no header files, no forward declarations, and no link-time surprises.
This chapter covers how Java classes are structured, how construction works, what access modifiers mean (with one critical difference from C++), and why you will never write a destructor again.

## Class Structure

\index{class}
\index{field}
\index{method}

A Java class file holds the fields, constructors, and methods all in one place.

```java
public class Song {
    // fields (instance variables)
    private String title;
    private String artist;
    private int    year;

    // constructor
    public Song(String title, String artist, int year) {
        this.title  = title;
        this.artist = artist;
        this.year   = year;
    }

    // method
    public String getTitle() {
        return title;
    }
}
```

Fields are declared directly inside the class body, not in a separate header.
Methods are defined there too --- no `Song::getTitle()` syntax outside the class.
The whole thing compiles from a single file named `Song.java`.

## Constructors

\index{constructor}
\index{constructor!overloading}
\index{constructor!delegation}

A constructor has the same name as the class and no return type --- not even `void`.
Java finds the right constructor by overload resolution, just like C++.

```java
public class Song {
    private String title;
    private String artist;
    private int    year;

    public Song(String title, String artist, int year) {
        this.title  = title;    // disambiguate field from parameter
        this.artist = artist;
        this.year   = year;
    }

    // overloaded: artist defaults to "Unknown"
    public Song(String title, int year) {
        this(title, "Unknown", year);   // delegate to the three-arg constructor
    }
}
```

The `this(...)` call on the last line is **constructor delegation**.
\index{constructor!this@\texttt{this(...)}}
It must be the very first statement in the constructor body --- you cannot run any other code before delegating.
This is Java's substitute for C++ delegating constructors (which use the initializer-list syntax `Foo() : Foo(args) {}`).

::: {.tip}
**Wut:** Java provides a no-argument constructor automatically *only* if you write no constructors at all.
The moment you define even one constructor, the free no-arg constructor disappears.
This matches C++ behavior exactly, so at least this one won't surprise you.
:::

## The `this` Keyword

\index{this@\texttt{this}}

In C++ `this` is a pointer --- you write `this->field`.
In Java `this` is a reference --- you write `this.field`.
Its most common use is disambiguating a field from a parameter with the same name:

```java
public Song(String title, int year) {
    this.title = title; // left: field; right: parameter
    this.year  = year;
}
```

You can also pass the current object to another method using plain `this`:

```java
public void register(Registry r) {
    r.add(this);    // hand myself to the registry
}
```

And as shown above, `this(...)` delegates to another constructor.
Those are the three uses: field access, passing the current object, and constructor delegation.

## Access Modifiers

\index{access modifier}
\index{public@\texttt{public}}
\index{private@\texttt{private}}
\index{protected@\texttt{protected}}
\index{package-private}

Java has four access levels:

| Modifier | Accessible from |
|:---|:---|
| `public` | everywhere |
| `protected` | same class, subclasses, same package |
| *(none)* | same package only (called **package-private**) |
| `private` | same class only |

There is no `friend` keyword.
Package-private is the default when you write no modifier at all --- it is not the same as `private`.

::: {.tip}
**Wut:** In Java, access control is **per class**, not per object.
A method of class `Foo` can read and write `private` fields of *any* `Foo` instance, not just `this`.
This is identical to C++ behavior, but it surprises programmers coming from languages where private means "only my instance."

```java
public class Song {
    private String title;

    public boolean sameTitle(Song other) {
        return this.title.equals(other.title);  // accessing other's private field -- legal!
    }
}
```
:::

::: {.tip}
**Tip:** Declare fields `private` and expose them through methods.
This keeps your options open to change the internal representation later without breaking callers.
:::

## No Destructor --- The GC Model

\index{garbage collector}
\index{destructor}
\index{RAII}

In C++, a destructor runs deterministically when an object goes out of scope or is deleted.
You rely on this for RAII: file handles close, mutexes unlock, database connections release.

Java has a garbage collector.
It frees heap memory automatically when no references to an object remain, but the GC runs on its own schedule.
You have no idea *when* --- or even *whether* --- it will run before the program exits.

`Object.finalize()` used to be the GC-era substitute for a destructor, but it was deprecated in Java 9 and removed in Java 18.
Do not use it.
There is no RAII in Java.

::: {.tip}
**Trap:** Do not try to implement RAII with a finalizer or even a `close()` method that you call manually at the end of a block.
Manual calls are easy to forget, and exceptions make them unreliable.
The correct Java idiom is `AutoCloseable` combined with `try`-with-resources (covered in Chapter 12).
That is the closest Java gets to RAII: the compiler guarantees the `close()` call even if an exception is thrown.
:::

The tradeoff is real.
You gain freedom from memory leaks and use-after-free bugs.
You lose deterministic cleanup of non-memory resources.
For non-memory resources --- files, sockets, database connections --- always use try-with-resources.

## The Object Contract: `equals`, `hashCode`, and `toString`

\index{Object@\texttt{Object}}
\index{equals@\texttt{equals()}}
\index{hashCode@\texttt{hashCode()}}
\index{toString@\texttt{toString()}}

Every Java class implicitly extends `Object`.
`Object` defines several methods that your class inherits by default, and three of them form what the community calls the **Object contract**.

### `equals(Object other)`

Signature: `public boolean equals(Object other)`

The default implementation inherited from `Object` tests **reference equality** --- it returns `true` only if `other` is the exact same object in memory.
This is like C++ `==` on raw pointers.

If you want value equality (two `Song` objects with the same title and year should be equal), you must override `equals`.

### `hashCode()`

Signature: `public int hashCode()`

Returns an integer hash of the object.
The contract: **if `a.equals(b)` is true, then `a.hashCode()` must equal `b.hashCode()`.**
The converse is not required --- two unequal objects can share a hash code (a collision), but hash-based collections (`HashMap`, `HashSet`) depend on equal objects having equal hashes.

::: {.tip}
**Trap:** Override `equals` without overriding `hashCode` and your objects will behave incorrectly in `HashMap` and `HashSet`.
The JVM will look them up using a hash that does not match, and your objects will vanish into the void.
Always override both together.
:::

### `toString()`

Signature: `public String toString()`

Returns a human-readable string representation.
The default output looks like `Song@6d06d69c` --- the class name and the object's identity hash in hex.
Override it to get something useful.
Java calls `toString()` implicitly in string concatenation, so `"Now playing: " + song` will use your override.

### A Complete Example

Here is a `Song` class that overrides all three:

```java
import java.util.Objects;

public class Song {
    private final String title;
    private final String artist;
    private final int    year;

    public Song(String title, String artist, int year) {
        this.title  = title;
        this.artist = artist;
        this.year   = year;
    }

    @Override
    public boolean equals(Object other) {
        if (this == other)      return true;    // same reference
        if (!(other instanceof Song s)) return false;
        return year == s.year
            && title.equals(s.title)
            && artist.equals(s.artist);
    }

    @Override
    public int hashCode() {
        return Objects.hash(title, artist, year);
    }

    @Override
    public String toString() {
        return "\"" + title + "\" by " + artist + " (" + year + ")";
    }

    public static void main(String[] args) {
        Song a = new Song("Ironic", "Alanis Morissette", 1995);
        Song b = new Song("Ironic", "Alanis Morissette", 1995);
        Song c = new Song("María",  "Ricky Martin",      1995);

        System.out.println(a);              // "Ironic" by Alanis Morissette (1995)
        System.out.println(a.equals(b));    // true  -- same content
        System.out.println(a.equals(c));    // false -- different song
        System.out.println(a == b);         // false -- different objects
    }
}
```

`Objects.hash(...)` is a convenience method from `java.util.Objects` that combines multiple values into a consistent hash.
Use it --- rolling your own hash is error-prone.

::: {.tip}
**Tip:** The pattern in `equals` --- check reference equality first, then check type, then check fields --- is the standard Java idiom.
The `instanceof` pattern-matching form (`instanceof Song s`) shown above requires Java 16 or later.
Before Java 16, you would write `instanceof Song` and then cast: `Song s = (Song) other;`.
:::

## Key Points

- A Java class declaration and definition live in one `.java` file; no headers, no separate `.cpp`.
- Constructors have the same name as the class and no return type.
- `this(...)` delegates to another constructor and must be the first statement.
- Java provides a free no-arg constructor only if you write no constructors at all.
- `this` in Java is a reference, not a pointer; use `this.field` and `this(...)`.
- Access is `public`, `protected`, package-private (no keyword), or `private`; access is per-class, not per-object.
- There is no destructor and no RAII; use `AutoCloseable` + try-with-resources for non-memory resources.
- Override `equals`, `hashCode`, and `toString` together; never override `equals` without `hashCode`.

2. **What does this print?**

    ```java
    public class Box {
        private int value;

        public Box(int value) { this.value = value; }

        public boolean sameValue(Box other) {
            return this.value == other.value;
        }

        public static void main(String[] args) {
            Box x = new Box(42);
            Box y = new Box(42);
            Box z = x;

            System.out.println(x.equals(y));
            System.out.println(x == y);
            System.out.println(x == z);
            System.out.println(x.sameValue(y));
        }
    }
    ```

4. **Where is the bug?**

    ```java
    import java.util.HashSet;

    public class Track {
        private String name;

        public Track(String name) { this.name = name; }

        @Override
        public boolean equals(Object other) {
            if (!(other instanceof Track t)) return false;
            return name.equals(t.name);
        }

        public static void main(String[] args) {
            HashSet<Track> set = new HashSet<>();
            set.add(new Track("Zombie"));

    ```
