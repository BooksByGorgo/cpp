# Methods

Methods in Java play the same role as free functions and member functions in C++.
The syntax is close enough that you will feel at home immediately, but several C++ features have no Java equivalent --- default arguments, `const` parameters, reference parameters --- and their absence shapes idiomatic Java code in ways worth understanding up front.
This chapter covers signatures, overloading, varargs, the pass-by-value semantics that always apply (even for objects), and the role of `static` and `final`.

## Signatures and Overloading

\index{method signature}
\index{overloading}

A method's **signature** in Java is its **name plus its parameter types**.
The return type is **not** part of the signature.
Two methods with the same name and parameter types but different return types are a compile error --- not overloads.

```java
// legal overloads: same name, different parameter types
void   log(String msg) { System.out.println(msg); }
void   log(int code, String msg) { System.out.printf("[%d] %s%n", code, msg); }
String log(String msg, boolean toFile) { /* ... */ return msg; }

// illegal: same name AND same parameter types, only return type differs
// int log(String msg) { return 0; } // compile error
```

Overload resolution works the same way as in C++: the compiler picks the most specific matching overload.
If no overload matches exactly, the compiler tries widening conversions (e.g., `int` to `long`).
If multiple overloads match equally well, the call is ambiguous and the compiler reports an error.

Java does not have function templates.
For type-generic methods, you use **generics** (covered in Ch 11).

## Varargs

\index{varargs}

Java's varargs let a method accept a variable number of arguments of a given type.
The syntax is `Type... name` on the last parameter.

```java
void log(String fmt, Object... args) {
    System.out.printf(fmt, args);
}
```

Inside the method, `args` is a plain `Object[]` array.
The caller can pass zero or more arguments, or pass an array directly.

```java
log("Song: %s%n", "Creep");             // one extra arg
log("Artist: %s, Year: %d%n", "Radiohead", 1992); // two extra args
log("No extras%n");                      // zero extra args
```

Varargs must be the **last parameter**.
A method can have at most one varargs parameter.
This is safer than C-style variadic functions (`va_list`, `va_arg`) because the type is checked at compile time.

::: {.tip}
**Trap:** Calling a varargs method with an array argument is ambiguous when the array type matches the varargs component type.
The compiler will accept it, but you may get an "unchecked" warning if the element type is generic.
Annotate with `@SafeVarargs` on the method if you know it is safe.
:::

## Pass-by-Value --- Always

\index{pass-by-value}
\index{pass-by-reference}

This is the most important conceptual difference between Java and C++ method calls.

**Java always passes by value.** Always. There are no exceptions.

For **primitives**, "by value" means a copy of the number (or boolean, or char) is made.
Modifying the parameter inside the method does not affect the caller's variable.
This is the same as C++ pass-by-value.

```java
static void doubleIt(int n) {
    n *= 2;              // modifies the local copy only
}

public static void main(String[] args) {
    int x = 5;
    doubleIt(x);
    System.out.println(x); // 5 -- unchanged
}
```

For **objects**, "by value" means a copy of the **reference** (the address) is made.
This is where C++ programmers sometimes get confused.
The method receives its own copy of the pointer --- it can use that pointer to reach into the object and mutate its state, but it cannot make the caller's variable point to a different object.

```java
static void appendCreep(StringBuilder sb) {
    sb.append(" -- Creep");  // mutates the object the reference points to
    sb = new StringBuilder("replaced"); // rebinds the local copy of the reference only
}

public static void main(String[] args) {
    StringBuilder song = new StringBuilder("Radiohead");
    appendCreep(song);
    System.out.println(song); // "Radiohead -- Creep" -- mutation visible
                               // but song still points to the original object
}
```

The analogy in C++ terms: Java object arguments behave like passing a raw pointer **by value**.
The pointer is copied; the object it points to can be modified through the copy; but reassigning the pointer inside the function does not affect the caller's pointer.

```cpp
// C++ equivalent mental model
void appendCreep(std::string* sb) { // pointer passed by value
    sb->append(" -- Creep");        // mutates the object
    sb = new std::string("replaced"); // rebinds local pointer only
}
```

What Java does **not** have is C++'s pass-by-reference (`T&`).
There is no way to write a Java method that makes the caller's variable point to a different object.
The classic C++ `swap(T& a, T& b)` cannot be written in Java for primitive values or for the references themselves.

::: {.tip}
**Wut:** Many Java tutorials say "objects are passed by reference."
This is imprecise and leads to exactly the confusion illustrated above.
The correct statement is: **the reference is passed by value**.
The object itself is not copied; the address of the object is copied.
:::

## No Default Arguments

\index{default arguments}

Java does not support default parameter values.
There is no Java equivalent of:

```cpp
void connect(const std::string& host, int port = 8080, bool tls = true);
```

The idiomatic Java solution is **overloading**: provide multiple overloads where the shorter ones call the longer one with the defaults filled in.

```java
void connect(String host, int port, boolean tls) {
    // actual implementation
}

void connect(String host, int port) {
    connect(host, port, true);   // default tls = true
}

void connect(String host) {
    connect(host, 8080, true);   // default port and tls
}
```

This is more verbose than C++ default arguments but has one advantage: each overload is independently documented in the API, making the defaults explicit and visible.

For methods with many optional parameters, the **builder pattern** is the preferred alternative (covered in Ch 6).

::: {.tip}
**Tip:** The convention for overloads that supply defaults is to have the shorter overloads call the longer (most-specific) one --- not the other way around.
This ensures all paths go through a single implementation, making future maintenance straightforward.
:::

## No `const` Parameters --- `final` Instead

\index{final!parameter}
\index{const}

Java has no `const`.
There is no way to write a Java equivalent of a C++ `const T&` parameter that prevents both reassignment of the reference and mutation of the object.

The keyword `final` on a parameter means the **parameter variable cannot be reassigned** inside the method.
It says nothing about the object the reference points to.

```java
static void print(final String msg) {
    msg = "something else"; // compile error: msg is final
    System.out.println(msg.toUpperCase()); // fine: calling methods on the object is allowed
}
```

For a mutable object, `final` on the parameter does not prevent mutation:

```java
static void addEntry(final List<String> list) {
    list = new ArrayList<>();        // compile error: list is final
    list.add("Creep -- Radiohead");  // fine: mutating the object is allowed
}
```

This is weaker than C++'s `const T&`, which prevents both.
Java's approach to immutability is via **immutable classes** (e.g., `String`, `Integer`) and the **record** type (Ch 16) rather than `const` qualifiers.

::: {.tip}
**Tip:** Using `final` on parameters is idiomatic in some codebases as a self-discipline tool to avoid accidental reassignment, but it is not universal.
Immutability in Java is a property of the **type** (e.g., `String` is immutable), not of the reference to it.
:::

## `static` vs Instance Methods

\index{static method}
\index{instance method}

A **`static` method** belongs to the class, not to any particular instance.
It is analogous to a C++ static member function.

```java
public class MathHelper {
    static int square(int n) {    // no instance needed
        return n * n;
    }
}

int result = MathHelper.square(7); // called on the class name, not an object
```

A `static` method:

- Cannot access instance fields directly (there is no `this`).
- Cannot call instance methods directly.
- Can be called without creating an object.

An **instance method** has an implicit `this` reference and can access both instance and static members.

```java
public class Song {
    private String title;     // instance field

    public Song(String title) {
        this.title = title;
    }

    public String getTitle() {         // instance method: has 'this'
        return this.title;
    }

    public static Song fromYear(int year) { // static factory: no 'this'
        return new Song("Creep (" + year + ")");
    }
}
```

`main` is always `static` because the JVM calls it before any objects exist.

::: {.tip}
**Trap:** A common mistake is calling an instance method from a `static` context without a reference.

```java
public class Broken {
    String name = "Radiohead";
    public static void main(String[] args) {
        System.out.println(name); // compile error: cannot access instance field from static context
    }
}
```

You need an instance: `new Broken().name` or move `name` to a local variable in `main`.
:::

## `final` Methods and Local Variables

\index{final!method}
\index{final!local variable}

`final` has three distinct uses in Java, and two of them appear in this chapter.

**`final` on a local variable:** The variable can be assigned exactly once.
After that, any attempt to reassign it is a compile error.

```java
final int max = 100;
max = 200;             // compile error
```

This is useful for documenting intent and enables the compiler to catch accidental reassignment.
Effectively-final variables (assigned once but not declared `final`) are treated similarly by lambdas and anonymous classes (covered in Ch 13).

**`final` on a method:** The method cannot be overridden by a subclass.
This is analogous to marking a virtual function `final` in C++.

```java
public class Base {
    public final void doNotOverride() {
        System.out.println("Base implementation only");
    }
}

public class Derived extends Base {
    @Override
    public void doNotOverride() { } // compile error: cannot override final method
}
```

A `final` method can still be called polymorphically through a base class reference; it just cannot be replaced in a subclass.

The third use of `final` --- on a class, to prevent inheritance entirely --- is covered in Ch 7.

## Key Points

- A method's **signature** is its name plus parameter types; the return type is not part of the signature.
- Java supports method **overloading**; the compiler picks the most specific match, widening if necessary.
- **Varargs** (`Type... name`) must be the last parameter and become an array inside the method.
- Java **always passes by value**. Primitive values are copied; for objects, the reference (address) is copied. A method can mutate the object a reference points to, but cannot make the caller's variable point elsewhere.
- There are **no default arguments**; the idiom is to provide multiple overloads where shorter ones call the full-parameter version.
- `final` on a parameter means the parameter variable cannot be reassigned; it does not make the referenced object immutable.
- `static` methods belong to the class and have no `this`; they cannot access instance members directly.
- `final` on a method prevents subclasses from overriding it.
