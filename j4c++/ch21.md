# The Module System

As a C++ programmer, you are used to controlling API boundaries at the library level.
You hide implementation symbols with `-fvisibility=hidden`, expose only what you want via header files, and let the linker enforce that nothing outside the `.so` can reach internal symbols.
Before Java 9, Java had none of this at the JAR level --- every `public` class in every JAR on the classpath was reachable from any other JAR, whether you intended it or not.
The Java Platform Module System (JPMS), introduced in Java 9, brings that enforcement to Java: you declare what your module exports, what it requires, and what it opens for reflection, and the JVM enforces those boundaries at both compile time and runtime.

This chapter covers `module-info.java`, the full set of module directives, the unnamed module migration escape hatch, multi-module project layout, and the most common pain points you will hit when modularizing an existing codebase.

## The Problem Before Java 9

\index{classpath}
\index{JAR hell}

The classical Java build model is simple: you put JARs on the classpath, the JVM searches them in order, and any `public` class anywhere is visible everywhere.
That simplicity came with two chronic problems.

**JAR hell** is what happens when two JARs on the classpath contain different versions of the same class (say, `com.fasterxml.jackson.databind.ObjectMapper` from Jackson 2.13 and Jackson 2.15).
The JVM loads whichever version it finds first and ignores the other.
The result is random, load-order-dependent behavior that is painful to diagnose.
In C++ terms, this is the equivalent of linking two `.so` files that both export the same symbol --- except in Java the linker does not even warn you.

**Accidental internal API access** is the other problem.
The JDK itself is full of `public` classes in `sun.*` and `com.sun.*` packages that were never meant to be public APIs --- they are just implementation details that had to be `public` because another JDK package needed them.
Nothing stopped application code from depending on them, and a lot of application code did, which meant the JDK team could never safely change those internals without breaking someone.

::: {.tip}
**Wut:** In C++, if you mark a symbol `__attribute__((visibility("hidden")))` it cannot be called from outside the `.so`.
In pre-Java-9, there was no equivalent mechanism for JARs.
`public` meant public to the entire universe.
:::

## `module-info.java`

\index{module-info.java@\texttt{module-info.java}}
\index{JPMS}
\index{module!declaration}

A module is declared by a file named `module-info.java` placed at the root of the module's source tree --- the same level as your top-level package directory.
The file contains a single module declaration with directives.

Here is a realistic example for a library that parses song metadata:

```java
module com.gorgo.songlib {
    requires java.logging;
    requires transitive com.gorgo.common;
    requires static org.checkerframework.checker.qual;

    exports com.gorgo.songlib.api;
    exports com.gorgo.songlib.model;
    exports com.gorgo.songlib.spi to com.gorgo.songlib.jackson,
                                     com.gorgo.songlib.xml;

    opens com.gorgo.songlib.model to com.fasterxml.jackson.databind;

    uses com.gorgo.songlib.spi.SongParser;
    provides com.gorgo.songlib.spi.SongParser
        with com.gorgo.songlib.internal.DefaultSongParser;
}
```

Module names follow the same reverse-DNS convention as package names.
A module named `com.gorgo.songlib` typically contains packages that start with `com.gorgo.songlib`.
This is a convention, not a requirement, but following it keeps things sane.

::: {.tip}
**Tip:** Put `module-info.java` at the module root, not inside a package directory.
If your source root is `src/main/java`, the file goes at `src/main/java/module-info.java`, alongside (not inside) `src/main/java/com/`.
:::

## Key Directives

\index{module!requires@\texttt{requires}}
\index{module!exports@\texttt{exports}}
\index{module!opens@\texttt{opens}}

### `requires`

```
requires moduleName;
```

`requires` declares a compile-time and runtime dependency.
Your module cannot see types from any module it does not explicitly `requires`.
This is the module system's answer to the old "everything is visible to everything" problem --- the equivalent of making a `.so` dependency explicit in your `CMakeLists.txt` or `pkg-config` file.

```java
module com.gorgo.player {
    requires java.base;       // implicit, but you can write it explicitly
    requires java.logging;
    requires com.gorgo.songlib;
}
```

`java.base` is the only module that is required implicitly by every module --- it contains the core classes (`java.lang`, `java.util`, `java.io`, etc.).
Every other module must be required explicitly.

### `requires transitive`

\index{module!requires transitive@\texttt{requires transitive}}

```
requires transitive moduleName;
```

`requires transitive` re-exports a dependency.
Any module that `requires` yours automatically also gains access to the transitive dependency --- you do not have to require it separately.

Use this when your public API returns or accepts types from that dependency.
For example, if `com.gorgo.songlib` exports a method that returns a type from `com.gorgo.common`, then any caller of `com.gorgo.songlib` also needs to see `com.gorgo.common` types.
Making it `requires transitive` means callers get that visibility automatically.

```java
module com.gorgo.songlib {
    requires transitive com.gorgo.common;   // callers see com.gorgo.common too
    // ...
}
```

::: {.tip}
**Trap:** Only use `requires transitive` when the dependency appears in your exported API --- return types, parameter types, or thrown exceptions that clients must handle.
If the dependency is purely internal (used only in your implementation), a plain `requires` keeps it hidden from callers.
:::

### `requires static`

\index{module!requires static@\texttt{requires static}}

```
requires static moduleName;
```

`requires static` is a compile-time-only dependency --- the module is optional at runtime.
The canonical use case is annotation processors and compile-time checkers: the annotations need to be on the classpath when you compile, but at runtime the annotations may be absent or replaced with stubs.

```java
module com.gorgo.songlib {
    requires static org.checkerframework.checker.qual;   // Checker Framework annotations
    // ...
}
```

If the module is absent at runtime, `Class.forName` calls on its types will throw `ClassNotFoundException`, so your code must handle that case.

### `exports`

\index{module!exports@\texttt{exports}}

```
exports packageName;
```

`exports` makes a package's `public` types visible to all other modules.
Packages not listed in any `exports` directive are completely hidden --- even other modules that `requires` yours cannot see them.
This is exactly what `-fvisibility=hidden` with selective `__attribute__((visibility("default")))` gives you in C++: everything is hidden by default, and you opt in what you want public.

```java
module com.gorgo.songlib {
    exports com.gorgo.songlib.api;     // public API
    exports com.gorgo.songlib.model;   // shared data types
    // com.gorgo.songlib.internal is NOT exported --- callers cannot see it
}
```

### `exports ... to`

\index{module!exports to@\texttt{exports ... to}}

```
exports packageName to moduleName [, moduleName ...];
```

A qualified export makes a package visible only to specific named modules.
This is useful for internal APIs that are shared between sibling modules but should not be visible to the world.

```java
module com.gorgo.songlib {
    exports com.gorgo.songlib.spi to com.gorgo.songlib.jackson,
                                     com.gorgo.songlib.xml;
}
```

Only `com.gorgo.songlib.jackson` and `com.gorgo.songlib.xml` can see `com.gorgo.songlib.spi`.
Everyone else sees nothing.

### `opens`

\index{module!opens@\texttt{opens}}
\index{reflection!module access}

```
opens packageName;
```

`opens` allows *deep reflective access* to a package --- meaning code in other modules can use `Class.getDeclaredField`, `Method.setAccessible(true)`, and similar reflective operations on the package's types, including private members.

Without `opens`, the module system blocks reflective access to non-exported packages even if the caller has a reference to the class.
This breaks frameworks like Spring, Hibernate, and Jackson that rely heavily on reflection to wire up objects, populate fields, and deserialize data.

```java
module com.gorgo.app {
    opens com.gorgo.app.model;   // Spring can reflect on these classes
}
```

The difference between `exports` and `opens`:
- `exports` --- other modules can compile against and call the public API.
- `opens` --- other modules can reflect into the package (including private members) at runtime.

A package can be both exported and opened, or just one or the other.

::: {.tip}
**Wut:** `opens` is about *reflective* access.
An exported package that is not opened still blocks `setAccessible(true)` on private members.
Frameworks that only use your public API need `exports`; frameworks that reach into private fields (Jackson, Hibernate) need `opens`.
:::

### `opens ... to`

\index{module!opens to@\texttt{opens ... to}}

```
opens packageName to moduleName [, moduleName ...];
```

A qualified open restricts reflective access to specific modules.
This is the right default: instead of opening everything to everyone, you explicitly grant access to the frameworks that need it.

```java
module com.gorgo.app {
    opens com.gorgo.app.model to com.fasterxml.jackson.databind,
                                 org.hibernate.orm.core;
}
```

### `uses`

\index{module!uses@\texttt{uses}}
\index{ServiceLoader@\texttt{ServiceLoader}}

```
uses ServiceInterface;
```

`uses` declares that your module is a consumer of a service via `ServiceLoader`.
`ServiceLoader` is Java's built-in service-provider mechanism --- think of it as the Java equivalent of a plugin interface, similar to how `dlopen` + a well-known function name works in C.

```java
module com.gorgo.player {
    uses com.gorgo.songlib.spi.SongParser;
}
```

At runtime, `ServiceLoader.load(SongParser.class)` discovers all modules on the module path that provide an implementation.

The signature for `ServiceLoader.load` is:

```java
static <S> ServiceLoader<S> ServiceLoader.load(Class<S> service)
static <S> ServiceLoader<S> ServiceLoader.load(Class<S> service, ClassLoader loader)
```

### `provides ... with`

\index{module!provides@\texttt{provides ... with}}

```
provides ServiceInterface with ImplementationClass [, ImplementationClass ...];
```

`provides` declares that your module provides an implementation of a service.
The implementation class must implement or extend the service interface and have a public no-argument constructor.

```java
module com.gorgo.songlib {
    provides com.gorgo.songlib.spi.SongParser
        with com.gorgo.songlib.internal.DefaultSongParser;
}
```

`ServiceLoader` discovers this automatically --- no registration file needed beyond the `module-info.java` declaration.
(For comparison, old-style pre-module service providers registered themselves in `META-INF/services/` text files.)

::: {.tip}
**Tip:** The `uses`/`provides` mechanism is how the JDK itself is extensible --- JDBC drivers, charset providers, and log handlers all use it.
Modular applications should prefer `ServiceLoader` over reflection-based plugin discovery.
:::

## The Unnamed Module

\index{unnamed module}
\index{classpath!and modules}

Not every JAR needs a `module-info.java`.
Code on the classpath --- JARs without a `module-info.java` --- lands in the **unnamed module**.
The unnamed module:

- reads all exported packages from every named module on the module path.
- exports all its packages to all named modules.
- can access the public types of any named module's exported packages.

Named modules, however, *cannot* `requires` the unnamed module.
Module names must be known at compile time; the unnamed module has no name.

This asymmetry is the migration escape hatch.
If you have a large pre-Java-9 codebase, you can:

1. Put all the old JARs on the classpath (unnamed module).
2. Gradually modularize one JAR at a time by adding a `module-info.java` and moving it to the module path.
3. Old classpath code can still call new modularized code (unnamed module reads named modules); new modularized code cannot directly `requires` the old classpath code, but can still access it reflectively or through service loading.

::: {.tip}
**Wut:** An unnamed module can read all named modules.
Named modules cannot read the unnamed module.
This is a one-way door.
If your new modularized code needs to call a class that is stuck on the classpath, you are out of luck without either modularizing that dependency or using reflection with `--add-opens`.
:::

The unnamed module also acts as a compatibility shim for the entire pre-module ecosystem.
Most application developers running Java 9+ with a classpath-only setup have been in the unnamed module the whole time without ever noticing --- which is by design.

## Multi-Module Project Structure

\index{multi-module project}
\index{Maven!multi-module}

A typical Maven multi-module layout for a modular project looks like this:

```
songapp/                          <- root project
├── pom.xml                       <- parent POM
├── songlib/                      <- library module
│   ├── pom.xml
│   └── src/main/java/
│       ├── module-info.java      <- module com.gorgo.songlib
│       └── com/gorgo/songlib/
│           ├── api/
│           └── model/
├── player/                       <- application module
│   ├── pom.xml
│   └── src/main/java/
│       ├── module-info.java      <- module com.gorgo.player
│       └── com/gorgo/player/
└── cli/                          <- command-line frontend module
    ├── pom.xml
    └── src/main/java/
        ├── module-info.java      <- module com.gorgo.cli
        └── com/gorgo/cli/
```

The parent `pom.xml` lists the child modules:

```xml
<modules>
    <module>songlib</module>
    <module>player</module>
    <module>cli</module>
</modules>
```

Each child `pom.xml` declares a dependency on sibling modules the same way it declares any other Maven dependency.
Maven resolves the build order from the dependency graph.
The `module-info.java` in each module enforces the same dependency graph at the JVM level.

::: {.tip}
**Tip:** Maven's `<dependency>` declarations and `module-info.java`'s `requires` directives are parallel systems.
Maven handles build-time artifact resolution; `module-info.java` handles runtime encapsulation.
They should agree with each other --- if `module-info.java` says `requires com.gorgo.songlib`, the corresponding `pom.xml` should have a `<dependency>` on the `songlib` artifact.
:::

## Common Migration Pain Points

\index{migration!to JPMS}

Most of the pain in adopting JPMS comes from decades of code that relied on the old "everything is public" model.
Here are the four problems you will encounter and how to handle them.

### Strong Encapsulation of JDK Internals

\index{strong encapsulation}
\index{sun.*@\texttt{sun.*} packages}

Java 9+ denies access to `sun.*`, `com.sun.*`, and other JDK-internal packages from code outside the JDK modules.
If your code (or a library you depend on) used `sun.misc.Unsafe`, `sun.nio.ch.DirectBuffer`, or similar, you will get an `InaccessibleObjectException` or a compile error.

The correct fix is to replace the internal API with the supported equivalent.
For example, `sun.misc.Base64Encoder` should be replaced with `java.util.Base64` (available since Java 8).

When a replacement does not exist or you are blocked waiting for a dependency to fix itself, you can use a JVM command-line flag to temporarily punch a hole:

```
java --add-exports java.base/sun.nio.ch=ALL-UNNAMED --add-opens java.base/sun.nio.ch=ALL-UNNAMED -jar myapp.jar
```

`ALL-UNNAMED` grants access to the unnamed module (and thus to all classpath code).

::: {.tip}
**Trap:** `--add-exports` and `--add-opens` are escape hatches, not solutions.
The JDK team reserves the right to remove internal APIs entirely in future releases.
Use them only as temporary workarounds while you wait for a proper fix.
:::

### Split Packages

\index{split package}

A **split package** is a package whose classes are spread across two or more JARs.
For example, if JAR A contains `com.example.util.Foo` and JAR B contains `com.example.util.Bar`, those JARs share the package `com.example.util`.

The classpath tolerated this; the module system does not.
Two named modules cannot export the same package --- the module system will refuse to load.

The fix is to consolidate the split package into a single JAR, or shade one JAR into the other.
If the split package is in a third-party dependency, you may need to upgrade to a version that has fixed it or use the unnamed module (classpath) for those JARs.

### Reflection on Private Members

\index{reflection!private access}
\index{setAccessible@\texttt{setAccessible()}}

Frameworks like Spring, Hibernate, and Jackson have historically used `Field.setAccessible(true)` to populate private fields without requiring public setters.
Under JPMS, this requires the containing package to be `opens` to the framework's module.

The fix is to add an `opens` directive to your `module-info.java`:

```java
module com.gorgo.app {
    // Jackson needs to reflect on model classes to deserialize JSON
    opens com.gorgo.app.model to com.fasterxml.jackson.databind;
}
```

If you are migrating gradually and cannot yet add a `module-info.java`, you can use the JVM flag:

```
java --add-opens com.gorgo.app/com.gorgo.app.model=com.fasterxml.jackson.databind -jar myapp.jar
```

### Most Applications Do Not Need Full Modularization

\index{unnamed module!as migration strategy}

JPMS is primarily valuable for **library authors** who want to enforce API boundaries and prevent consumers from depending on internal implementation details.
For application code --- a web service, a batch job, a desktop app --- staying on the classpath with the unnamed module is often entirely appropriate.

You still benefit from JPMS in application code: the JDK itself is modular, and strong encapsulation of JDK internals applies regardless of whether your application has a `module-info.java`.
But you do not need to write one to get a working, correctly-functioning application.

::: {.tip}
**Tip:** If you are writing a reusable library that others will depend on, invest in a `module-info.java`.
If you are writing an application, the unnamed module is a fine, supported choice.
You can modularize incrementally --- there is no requirement to do it all at once.
:::

### A Complete Modular Example

Here is a minimal but complete modular library and consumer.
The library parses track titles; the consumer prints them.

Library module (`module-info.java`):

```java
module com.gorgo.songlib {
    exports com.gorgo.songlib.api;
}
```

Library class:

```java
package com.gorgo.songlib.api;

public class TrackTitle {
    private final String title;
    private final String artist;

    public TrackTitle(String title, String artist) {
        this.title  = title;
        this.artist = artist;
    }

    public String title()  { return title; }  // "Return of the Mack"
    public String artist() { return artist; } // Mark Morrison

    @Override
    public String toString() {
        return title + " --- " + artist;
    }
}
```

Consumer module (`module-info.java`):

```java
module com.gorgo.player {
    requires com.gorgo.songlib;
}
```

Consumer class:

```java
package com.gorgo.player;

import com.gorgo.songlib.api.TrackTitle;

public class Player {
    public static void main(String[] args) {
        var track = new TrackTitle("Return of the Mack", "Mark Morrison");
        System.out.println("Now playing: " + track);
    }
}
```

The `com.gorgo.player` module cannot reach anything in `com.gorgo.songlib` that is not under `com.gorgo.songlib.api`.
Any attempt to import from an unexported package fails at compile time with a module access error --- not a mysterious runtime failure.

## Key Points

- Before Java 9, every `public` class in every JAR was accessible from anywhere --- no encapsulation between JARs, no way to hide internal APIs.
- JPMS (Java Platform Module System) was introduced in Java 9 to enforce encapsulation at the JAR level, similar to linker visibility controls in C++.
- A module is declared by `module-info.java` at the source root; module names follow reverse-DNS convention.
- `requires` declares a dependency; your module cannot see types from modules it does not `requires`.
- `requires transitive` re-exports a dependency to your callers; use it only when the dependency appears in your public API.
- `requires static` is compile-time only (optional at runtime); used for annotation processors and compile-time checkers.
- `exports` makes a package's public types visible to all other modules; unexported packages are completely hidden.
- `exports ... to` is a qualified export visible only to specific named modules.
- `opens` allows deep reflective access (including private members) to a package; needed by frameworks like Spring, Hibernate, and Jackson.
- `opens ... to` restricts reflective access to specific modules --- prefer this over unqualified `opens`.
- `uses` and `provides ... with` integrate with `ServiceLoader` for service-provider discovery.
- The **unnamed module** holds all classpath code (JARs without `module-info.java`); it reads all named modules, but named modules cannot `requires` it --- the primary migration escape hatch.
- Common pain points: JDK internal API access (`--add-exports`/`--add-opens` as a temporary workaround), split packages (consolidate), reflection on private members (add `opens`).
- Full modularization is most valuable for library authors; application code is perfectly fine staying in the unnamed module.

1. **Think about it:** C++ controls symbol visibility with `-fvisibility=hidden` and `__attribute__((visibility("default")))`, which are enforced by the linker at link time.
Java's JPMS enforces module boundaries at both compile time and runtime.
What are the tradeoffs of each approach?
Consider a scenario where a caller bypasses the boundary at runtime --- which system makes that harder, and why?

2. **What does this do?**
The following two `module-info.java` files are compiled together.
Does the second module compile successfully?
If not, why not?

    ```java
    // module com.gorgo.lib
    module com.gorgo.lib {
        exports com.gorgo.lib.api;
        // com.gorgo.lib.internal is NOT exported
    }
    ```

    ```java
    // module com.gorgo.app
    module com.gorgo.app {
        requires com.gorgo.lib;
    }
    ```

    ```java
    // in com.gorgo.app
    package com.gorgo.app;

    import com.gorgo.lib.internal.Helper;   // attempt to use unexported package

    public class Main {
        public static void main(String[] args) {
            Helper h = new Helper();
        }
    }
    ```

3. **Calculation:** A module declares `requires transitive A`, `requires transitive B`, and `requires C`.
Module X declares `requires mymodule`.
How many modules does X gain access to through that single `requires`, and which ones?
