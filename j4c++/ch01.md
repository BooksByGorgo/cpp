# The Java Platform

Before you write a single line of Java, you need a mental model of what happens between your editor and a running program.
In C++, the answer is short: the compiler turns your source into native machine code for a specific target, and you run it directly.
Java takes a detour through a virtual machine, and understanding that detour explains many Java design decisions --- why there is no `#include`, why class files are portable, and why startup feels heavier than a native binary.

This chapter maps the Java toolchain from source to execution and introduces the build tools you will encounter in real projects.
It also covers Java's release cadence so you know which version to target.

## JVM, Bytecode, and the JIT

\index{JVM}
\index{bytecode}
\index{JDK}
\index{JRE}
\index{JIT}

In C++, `g++` or `clang++` produces an ELF binary (or Mach-O, or PE) containing machine instructions for one specific CPU architecture.
Move that binary to a different architecture and it will not run.

Java separates compilation from execution with an intermediate representation called **bytecode**.
\index{bytecode}
`javac` compiles your `.java` source files into `.class` files containing bytecode --- a compact instruction set for an imaginary stack-based machine called the **Java Virtual Machine** (JVM).
The `.class` files are architecture-neutral; the same file runs on x86-64, ARM64, or any other platform that has a JVM implementation.

The JVM does not just interpret bytecode forever.
It includes a **Just-In-Time** (JIT) compiler that profiles running code and compiles hot paths to native machine code at runtime.
Modern JVMs (HotSpot, GraalVM) use a tiered strategy: code starts interpreted, gets compiled by a fast but simple compiler (C1), and eventually gets compiled by a heavy optimizing compiler (C2) if it stays hot.
Peak throughput of JIT-compiled Java code is competitive with compiled C++.

### JDK, JRE, and JVM

\index{JDK!vs JRE}
\index{JRE}

These three acronyms get conflated constantly:

| Acronym | What it is | Analogy in C++ world |
|:--------|:-----------|:---------------------|
| **JVM** | The virtual machine that executes bytecode | The CPU + OS ABI |
| **JRE** | JVM + core class libraries; enough to *run* Java programs | A stripped runtime-only libc deployment |
| **JDK** | JRE + `javac`, `javadoc`, `jdb`, `jpackage`, and other dev tools | g++ + binutils + gdb |

Since Java 11, Oracle no longer ships a standalone JRE download.
You install the JDK and it contains everything.
The distinction lives on in documentation and in deployment discussions (you ship a JRE to production, not a JDK), but for development you always want the JDK.

::: {.tip}
**Tip:** Install the JDK, not just the JRE.
Without `javac` you cannot compile anything, and without tools like `jstack` and `jcmd` you cannot diagnose production problems.
:::

## `javac`, `java`, Classpath, and JAR Files

\index{javac}
\index{java (command)}
\index{classpath}

### Compiling and Running

The two commands you use daily are `javac` (the compiler) and `java` (the launcher).
Here is the minimal workflow.
Start with a file `Hello.java`:

```java
public class Hello {
    public static void main(String[] args) {
        // "Smells Like Teen Spirit" - Nirvana (1991)
        System.out.println("Here we are now, entertain us");
    }
}
```

Compile it:

```
javac Hello.java
```

This produces `Hello.class`.
Run it:

```
java Hello
```

Output:

```
Here we are now, entertain us
```

Notice: you pass the **class name** to `java`, not the filename.
No `.class` extension.
This is the first gotcha coming from C++, where you run a binary file directly.

Here is the compile/run workflow side by side with C++:

| Step | C++ | Java |
|:-----|:----|:-----|
| Source file | `hello.cpp` | `Hello.java` |
| Compile command | `g++ -o hello hello.cpp` | `javac Hello.java` |
| Compiler output | `hello` (native binary) | `Hello.class` (bytecode) |
| Run command | `./hello` | `java Hello` |
| Runs on | This machine only | Any JVM |

### Classpath

\index{classpath!definition}

The **classpath** tells the JVM where to look for `.class` files, much like `-L` and `-rpath` tell the linker where to find shared libraries, or like `LD_LIBRARY_PATH` at runtime.

When you have dependencies, you list them on the classpath:

```
java -cp .:lib/mylib.jar Main
```

`.` means the current directory (where your own `.class` files live).
`lib/mylib.jar` is a dependency.
On Windows, use `;` instead of `:` as the separator.

::: {.tip}
**Trap:** Forgetting `.` in the classpath is a classic beginner mistake.
If you omit it, the JVM cannot find your own class files even though they are right there in the current directory.
:::

### JAR Files

\index{JAR file}

A **JAR** (Java Archive) file is a zip archive of `.class` files (and resources) with a `META-INF/MANIFEST.MF` metadata file.
Think of it as the Java equivalent of a `.a` static library or a `.so` shared library --- except it contains bytecode, not native machine code, and the JVM loads it at runtime rather than the OS linker.

Create a JAR:

```
jar cf mylib.jar com/example/*.class
```

Run a JAR that has a `Main-Class` declared in its manifest:

```
java -jar myapp.jar
```

JAR files are what you publish to a Maven repository, what build tools download as dependencies, and what you ship to production.

::: {.tip}
**Tip:** You rarely create or manipulate JAR files by hand.
Your build tool (Maven or Gradle) handles it.
Understanding what a JAR is helps when you are reading build files or debugging classpath errors.
:::

## Maven and Gradle

\index{Maven}
\index{Gradle}
\index{build tool}

In the C++ world, `make` handles the build and you reach for `cmake` when projects grow.
External dependencies are managed separately --- `vcpkg`, `conan`, or by hand.
Java unifies build logic and dependency management in a single tool.
The two dominant options are **Maven** and **Gradle**.

### Maven

\index{Maven!pom.xml}

Maven is the older of the two (circa 2004) and uses **convention over configuration**: if you put your source files in `src/main/java` and your tests in `src/test/java`, Maven knows what to do with them without any explicit instructions.
The build file is `pom.xml` (Project Object Model), an XML file.

A minimal Maven project looks like this:

```
my-project/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── com/
                └── example/
                    └── App.java
```

A minimal `pom.xml`:

```xml
<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>my-project</artifactId>
  <version>1.0-SNAPSHOT</version>
</project>
```

Common Maven commands:

| Command | What it does |
|:--------|:-------------|
| `mvn compile` | Compile `src/main/java` |
| `mvn test` | Compile and run tests |
| `mvn package` | Build a JAR in `target/` |
| `mvn clean` | Delete `target/` |
| `mvn install` | Build and install to local repo (`~/.m2`) |

Dependencies are declared in `pom.xml` and Maven downloads them automatically from **Maven Central** (the public repository) into `~/.m2/repository`.
This is analogous to what `apt` or `brew` does for system packages, but scoped to your project.

### Gradle

\index{Gradle!build.gradle}

Gradle (circa 2012) uses a Groovy or Kotlin DSL instead of XML, giving you the full power of a programming language in your build file.
It is faster than Maven on large projects (incremental builds, a build daemon) and is the default for Android development.

A minimal `build.gradle` (Groovy DSL):

```groovy
plugins {
    id 'java'
}

repositories {
    mavenCentral()
}

dependencies {
    testImplementation 'org.junit.jupiter:junit-jupiter:5.10.0'
}
```

Common Gradle commands:

| Command | What it does |
|:--------|:-------------|
| `./gradlew build` | Compile, test, and package |
| `./gradlew test` | Run tests |
| `./gradlew clean` | Delete `build/` |
| `./gradlew jar` | Build the JAR |

The `./gradlew` script is the **Gradle wrapper** --- a small script committed to the repository that downloads and runs the correct Gradle version automatically.
You do not need Gradle installed globally.
This is a nice improvement over `cmake`, where everyone needs a compatible version installed.

::: {.tip}
**Tip:** When joining a Java project, look for `pom.xml` (Maven) or `build.gradle` / `build.gradle.kts` (Gradle) in the project root to understand which build tool is in use.
Running `mvn package` on a Gradle project does nothing, and vice versa.
:::

### Maven vs Gradle at a Glance

| Aspect | Maven | Gradle |
|:-------|:------|:-------|
| Config format | XML (`pom.xml`) | Groovy/Kotlin DSL |
| Convention | Strong (opinionated layout) | Flexible |
| Build speed | Slower on large projects | Faster (incremental, daemon) |
| Android default | No | Yes |
| Learning curve | Easier to start | More powerful, steeper curve |

For a new standalone project, either works fine.
In industry you will encounter both; knowing how to read both build files is worth the investment.

## Java Versioning and LTS Releases

\index{Java!versioning}
\index{LTS release}

C++ standardization moves slowly: C++11, C++14, C++17, C++20, C++23 --- roughly one major standard every three years.
Java moved faster in its early days (Java 1.0 through Java 8, spanning 1996--2014) and since Java 9 (2017) has shipped a new version **every six months**, in March and September.

Not every release is equal.
**Long-Term Support** (LTS) releases get commercial vendor support for years after their release.
Non-LTS releases are supported only until the next release six months later.

\index{LTS release!versions}

Current LTS releases:

| Version | Released | Notes |
|:--------|:---------|:------|
| Java 8 | 2014 | Still widely deployed; lambdas, streams |
| Java 11 | 2018 | First LTS after the 6-month cadence began |
| Java 17 | 2021 | Sealed classes, pattern matching preview |
| Java 21 | 2023 | Virtual threads, record patterns, `sequenced` collections |
| Java 25 | 2025 | Value classes preview |

::: {.tip}
**Tip:** Target an LTS release for production code.
Java 21 is the current recommended baseline for new projects.
Using a non-LTS release means you must upgrade every six months or lose security patches.
:::

::: {.tip}
**Wut:** Java maintains exceptionally strong backward compatibility.
Code compiled for Java 8 typically runs unmodified on Java 21.
This is unlike C++, where a major standard revision can silently change behavior (most infamously, `std::string` copy-on-write was removed in C++11).
:::

## Key Points

- `javac` compiles `.java` source files to `.class` bytecode files; the JVM executes them.
- Bytecode is architecture-neutral; the same `.class` file runs on any JVM.
- The JIT compiler profiles running bytecode and compiles hot paths to native machine code at runtime.
- JDK = development tools + JRE; JRE = JVM + core libraries; JVM = the virtual machine itself.
- The classpath tells the JVM where to find `.class` files and JARs; forgetting `.` is a common mistake.
- A JAR file is a zip of `.class` files, analogous to a `.a` or `.so` but containing bytecode.
- Maven (`pom.xml`) and Gradle (`build.gradle`) are the dominant build and dependency-management tools.
- Java ships a new version every six months; LTS releases (8, 11, 17, 21, 25) get long-term support.
- Target an LTS release for production; Java 21 is the current recommended baseline.

## Exercises

1. **Think about it:** The JIT compiler compiles bytecode to native machine code at runtime, after profiling which code paths are hot.
   How does this differ from C++ link-time optimization (LTO), and what does each approach trade off in terms of compilation overhead, portability, and peak throughput?

2. **What does this do?**

    ```
    javac Foo.java
    java -cp . Foo
    ```

    There is no `Foo.java` in the current directory, but there is a `Foo.class` from a previous compile.
    What happens when you run these two commands in sequence?
    What would happen if you ran only the second command?

3. **Calculation:** You have a Maven project with three dependencies, each packaged as a JAR.
   The JARs are 1 MB, 3 MB, and 500 KB in size.
   Your own compiled `.class` files total 200 KB.
   If you package everything into a single "fat JAR" (all dependencies bundled), approximately how large is the resulting file?

4. **Where is the bug?**

    ```
    javac Hello.java
    java Hello.class
    ```

    You compiled successfully, but the second command fails with an error.
    What is wrong and how do you fix it?

5. **Write a program:** Create a file `Platform.java` containing a class `Platform` with a `main` method that prints the Java version, the JVM vendor, and the operating system name using `System.getProperty("java.version")`, `System.getProperty("java.vendor")`, and `System.getProperty("os.name")`.
   Compile and run it with `javac` and `java`.
