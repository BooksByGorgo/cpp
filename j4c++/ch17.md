# Sealed Classes and Pattern Matching

C++ has no language mechanism to say "this is the complete set of types that can extend this base class."
You can use private constructors and friend declarations to approximate it, but the language gives you no compile-time guarantee and no way to make the compiler enforce exhaustiveness.
Java 17 introduced **sealed classes** to do exactly that: declare a closed hierarchy and let the compiler verify that every arm of a pattern-matching switch covers every case.
Combined with pattern matching for `instanceof` (Java 16) and full pattern-matching `switch` expressions (Java 21), sealed classes bring algebraic data type programming --- familiar from Haskell and Rust --- into mainstream Java.

This chapter covers sealed/permits hierarchies, pattern matching for `instanceof`, pattern-matching `switch` (including guards, null handling, and deconstruction patterns), unnamed patterns, and a realistic end-to-end example comparing the idiom to C++ `std::variant` + `std::visit`.

## Sealed Classes and the `permits` Clause

\index{sealed class}
\index{permits}
\index{sealed class!permits}

A **sealed class** (or sealed interface) uses the `sealed` keyword and names its permitted subclasses with `permits`:

```java
sealed class Shape permits Circle, Rectangle, Triangle {}
```

Every class in the `permits` list must:

- Directly extend the sealed class (one level only --- grandchildren need their own `permits`).
- Be declared `final`, `sealed`, or `non-sealed`.

```java
sealed class Shape permits Circle, Rectangle, Triangle {}

final class Circle    extends Shape { double radius; Circle(double r)  { radius = r; } }
final class Rectangle extends Shape { double w, h;   Rectangle(double w, double h) { this.w = w; this.h = h; } }
final class Triangle  extends Shape { double base, height; Triangle(double b, double h) { base = b; height = h; } }
```

The `final` keyword on each subclass means the hierarchy ends there.
If you want to allow further extension from a permitted subclass, mark that subclass `sealed` (with its own `permits`) or `non-sealed` (which reopens the hierarchy at that node).

::: {.tip}
**Wut:** `non-sealed` is a genuine Java keyword.
It exists specifically to let a permitted subclass opt back out of the closed hierarchy, which allows third-party code to extend it.
Using `non-sealed` on a permitted subclass does not break the parent's sealed guarantee for the other permitted types.
:::

### Compilation Unit Rules

All permitted subclasses must be visible to the compiler at the same time as the sealed class.
In practice this means they must be in the same source file, or in the same package with the subclass files compiled together (a single `javac` invocation or a Maven/Gradle build).
The compiler will reject a `permits` list whose members are not found.

### Comparison to C++

In C++ you have no equivalent mechanism.
The closest approaches are:

- A base class with a private constructor and `friend` declarations, preventing external inheritance.
- A `std::variant` listing all types explicitly.
- Documentation and code review.

None of these give the compiler enough information to warn about an unhandled type in a `switch`.
Java's sealed classes do.

## Pattern Matching for `instanceof`

\index{pattern matching!instanceof}
\index{instanceof!pattern matching}

Before Java 16, checking a type and using it required two lines:

```java
// old style
if (shape instanceof Circle) {
    Circle c = (Circle) shape;  // redundant cast
    System.out.println(c.radius);
}
```

Java 16 made `instanceof` a pattern-matching expression: it tests the type *and* binds a variable of that type in one step:

```java
// Java 16+ pattern matching
if (shape instanceof Circle c) {
    System.out.println(c.radius);  // c is Circle, in scope here
}
```

The binding variable `c` is in scope for the `if` body and can also appear in the `&&` chain that guards the condition:

```java
if (shape instanceof Circle c && c.radius > 0) {
    System.out.printf("Circle with positive radius: %.2f%n", c.radius);
}
```

Compare to C++20 with `std::variant` and `std::get_if`:

```cpp
if (auto* c = std::get_if<Circle>(&shape)) {
    std::cout << c->radius << "\n";
}
```

The Java form is cleaner for the polymorphic-object case; `std::get_if` shines for value-semantic variants.

::: {.tip}
**Tip:** Pattern-matching `instanceof` eliminates the cast and the redundant type-check.
If you find yourself writing `if (x instanceof Foo) { Foo f = (Foo) x; ... }`, replace it with `if (x instanceof Foo f) { ... }`.
:::

## Pattern Matching in `switch`

\index{pattern matching!switch}
\index{switch!pattern matching}

Java 21 made `switch` capable of matching on type patterns, building directly on sealed class hierarchies.
The compiler enforces exhaustiveness: if your `switch` does not cover every permitted subclass of a sealed type (or does not include a `default`), it will not compile.

```java
// "Torn" - Natalie Imbruglia (1997)
sealed interface Lyric permits Verse, Chorus, Bridge {}
record Verse(int number, String text)  implements Lyric {}
record Chorus(String text)             implements Lyric {}
record Bridge(String text, int bars)   implements Lyric {}

static String describe(Lyric lyric) {
    return switch (lyric) {
        case Verse   v -> "Verse %d: %s".formatted(v.number(), v.text());
        case Chorus  c -> "Chorus: "    + c.text();
        case Bridge  b -> "Bridge (%d bars): %s".formatted(b.bars(), b.text());
    };
}
```

Because `Lyric` is sealed and the three permitted types are all covered, no `default` is needed.
If you add `record Outro(String text) implements Lyric {}` to the hierarchy later, this `switch` becomes a compile error, which is exactly the behavior you want --- the compiler finds every call site that forgot to handle the new type.

### Guarded Patterns

\index{pattern matching!guard}
\index{when clause}

A `when` clause adds a boolean guard to a case arm:

```java
static String classify(Lyric lyric) {
    return switch (lyric) {
        case Verse v when v.number() == 1 -> "Opening verse: " + v.text();
        case Verse v                      -> "Verse %d".formatted(v.number());
        case Chorus c when c.text().length() > 50 -> "Long chorus";
        case Chorus c                     -> "Chorus";
        case Bridge b                     -> "Bridge";
    };
}
```

Arms are tried in order.
A more specific guard must come before the general case for the same type --- the compiler enforces this.

### Null Handling

\index{pattern matching!null}

Before Java 21, a `switch` on a `null` reference always threw `NullPointerException`.
Java 21 lets you handle `null` explicitly with a `case null` arm:

```java
static String safeDescribe(Lyric lyric) {
    return switch (lyric) {
        case null    -> "(no lyric)";
        case Verse v -> "Verse " + v.number();
        case Chorus c -> "Chorus";
        case Bridge b -> "Bridge";
    };
}
```

::: {.tip}
**Wut:** Without a `case null` arm, a pattern-matching `switch` throws `NullPointerException` when given `null`, just like the old-style `switch` did.
If `null` is a possible input, add `case null ->` explicitly.
:::

## Deconstruction Patterns

\index{deconstruction pattern}
\index{record!deconstruction pattern}

When switching on records, you can **deconstruct** the record directly in the case arm, binding its components without calling accessor methods:

```java
static double area(Shape shape) {
    return switch (shape) {
        case Circle(var radius)              -> Math.PI * radius * radius;
        case Rectangle(var w, var h)         -> w * h;
        case Triangle(var base, var height)  -> 0.5 * base * height;
    };
}
```

Here `Circle(var radius)` is a **deconstruction pattern**: it matches a `Circle` and simultaneously binds the `radius` component.
The component names in the pattern must match the record component names.

Deconstruction patterns can be nested.
If a record component is itself a record, you can deconstruct it inline:

```java
record Point(double x, double y) {}
record Line(Point start, Point end) {}

static double length(Line line) {
    return switch (line) {
        case Line(Point(var x1, var y1), Point(var x2, var y2)) -> {
            double dx = x2 - x1;
            double dy = y2 - y1;
            yield Math.sqrt(dx * dx + dy * dy);
        }
    };
}
```

## Unnamed Patterns and Variables

\index{unnamed pattern}
\index{unnamed variable}

When you do not need all the components of a deconstruction pattern, use `_` to discard the ones you do not care about (Java 21+):

```java
static boolean isVerse(Lyric lyric) {
    return switch (lyric) {
        case Verse _ -> true;   // matched, component discarded
        default      -> false;
    };
}
```

`_` can also appear multiple times in a single pattern to discard multiple components:

```java
record RGB(int r, int g, int b) {}

static boolean isPureRed(RGB color) {
    return switch (color) {
        case RGB(var r, _, _) when r == 255 -> true;
        default                             -> false;
    };
}
```

::: {.tip}
**Tip:** Use `_` when you need to match a type but do not need its data.
It is more expressive than `default` because it still participates in exhaustiveness checking.
:::

## Putting It All Together: Algebraic Data Types

\index{algebraic data type}
\index{expression problem}

The combination of sealed classes and pattern matching enables the **algebraic data type** (ADT) pattern, familiar from ML, Haskell, and Rust.
In C++ you reach for `std::variant` and `std::visit`:

```cpp
using Expr = std::variant<Num, Add, Mul>;

struct Num { int value; };
struct Add { std::shared_ptr<Expr> left, right; };
struct Mul { std::shared_ptr<Expr> left, right; };

int eval(const Expr& e) {
    return std::visit([](auto& node) -> int {
        using T = std::decay_t<decltype(node)>;
        if constexpr (std::is_same_v<T, Num>) return node.value;
        else if constexpr (std::is_same_v<T, Add>)
            return eval(*node.left) + eval(*node.right);
        else
            return eval(*node.left) * eval(*node.right);
    }, e);
}
```

The Java version with sealed records is more readable:

```java
// "Torn" - Natalie Imbruglia (1997): expressions torn apart
sealed interface Expr permits Num, Add, Mul {}
record Num(int value)             implements Expr {}
record Add(Expr left, Expr right) implements Expr {}
record Mul(Expr left, Expr right) implements Expr {}

static int eval(Expr e) {
    return switch (e) {
        case Num(var v)          -> v;
        case Add(var l, var r)   -> eval(l) + eval(r);
        case Mul(var l, var r)   -> eval(l) * eval(r);
    };
}

public class ExprDemo {
    public static void main(String[] args) {
        // (2 + 3) * 4  ==> 20
        Expr expr = new Mul(
            new Add(new Num(2), new Num(3)),
            new Num(4)
        );
        System.out.println(eval(expr));  // 20
    }
}
```

No cast, no `if constexpr`, no shared_ptr noise.
The compiler enforces that every `Expr` variant is handled.
Adding `record Neg(Expr operand) implements Expr {}` to the hierarchy immediately breaks every `eval`-style switch that forgot to handle it --- you get a compile error, not a runtime crash.

### The Expression Problem

\index{expression problem}

This pattern is sometimes called the solution to the **expression problem**: how do you add both new types and new operations to a type hierarchy without modifying existing code?

- OOP (regular class with virtual methods): easy to add new *types* (subclass and override), hard to add new *operations* (must touch every class).
- ADT with pattern matching: easy to add new *operations* (new function with a `switch`), hard to add new *types* (all `switch` sites break).

Sealed classes with pattern matching shift Java toward the ADT/functional side.
Use this pattern when the set of types is fixed and you expect to add new operations --- parsers, compilers, rule engines, and protocol message handlers are typical examples.

## Key Points

- A `sealed` class or interface restricts which classes can extend it, listing them in a `permits` clause.
- Every permitted subclass must be `final`, `sealed`, or `non-sealed`.
- Pattern-matching `instanceof` (`if (obj instanceof Foo f)`) tests type and binds a variable in one step, eliminating the redundant cast.
- Pattern-matching `switch` on a sealed type is exhaustiveness-checked by the compiler --- every permitted subtype must be covered.
- `when` clauses add boolean guards to case arms; more specific guards must appear before general ones.
- `case null ->` handles null inputs explicitly; without it, a pattern-matching `switch` throws `NullPointerException` on `null`.
- Deconstruction patterns (`case Point(var x, var y)`) bind record components directly in a case arm.
- The `_` wildcard discards components you do not need while still satisfying the type match.
- Sealed classes + pattern matching enable the algebraic data type idiom: a closed set of types matched exhaustively by functions --- the functional complement to OOP's virtual dispatch.
